### Q1 ⭐: MySQL 有哪些存储引擎？InnoDB 和 MyISAM 最核心的区别是什么？

**高分回答：**

"这个问题基本上面试都会问到，我直接说重点。

MySQL 支持多种存储引擎，常用的就是 **InnoDB** 和 **MyISAM**，还有老古董 **Memory** 和现在已经很少见的 **Archive**。

**最核心的区别——三个维度：**

| 区别 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | ✅ 支持 ACID | ❌ 不支持 |
| 锁粒度 | **行级锁** | 表级锁 |
| 外键 | ✅ 支持 | ❌ 不支持 |

但面试官真正想问的不仅仅是这些表面区别。我说句实话，**MyISAM 在 MySQL 8.0 以后基本可以告别了**——因为系统表都用 InnoDB 了。

还有几个容易被忽略的点：

- **聚簇索引 vs 非聚簇索引**：InnoDB 的数据和索引是存在一起的（聚簇索引组织表），MyISAM 的索引和数据是分开的。这个差异直接决定了查询性能。
- **全文索引**：MyISAM 原生就支持全文索引，InnoDB 直到 MySQL 5.6 才加上——不过现在也支持了。
- **自增锁**：InnoDB 的自增锁是 `AUTO-INC` 轻量级锁（可配置），比 MyISAM 的行锁更高效。

**线上建议：** 除非你的业务纯粹是只读、不用事务、数据量几百万这种查字典场景，否则一律选 InnoDB。MySQL 5.5 之后 InnoDB 就是默认引擎，不是没有道理的。

> 💡 追问：Memory 引擎什么时候会用？——临时表、中间计算结果缓存、低并发场景。但重启数据全丢，别拿它当正式存储。

### Q2 ⭐: 说说 InnoDB 的聚簇索引（Clustered Index），和普通索引有什么不同？

**高分回答：**

"这个问题能看出来一个人有没有真正理解 InnoDB 的底层存储结构。

**聚簇索引（Clustered Index）**

InnoDB 中，聚簇索引就是**数据本身**。表的主键就是一个聚簇索引，叶子节点存的是整行数据。

- 如果你显式定义了主键 → 主键就是聚簇索引
- 没定义主键 → 选第一个 NOT NULL UNIQUE 列
- 都没有 → InnoDB 自动生成 `ROW_ID`（6 字节，全局隐藏）

**普通索引（Secondary Index）**

叶子节点存的是**主键值**，不是数据行地址。这就引出了一个重要概念：**回表（bookmark lookup）**。

举个例子你就明白了：

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,    -- 聚簇索引
  name VARCHAR(50),
  age INT,
  INDEX idx_name(name)     -- 普通索引
);

SELECT * FROM user WHERE name = '张三';
```

执行步骤：
1. 在 `idx_name` 索引树上找到 '张三' 对应的主键 id
2. 拿着 id 回聚簇索引树查完整行

**这就是为什么尽量用主键查询——一次 B+ 树查找，不用回表。**

> 💡 加分点：如果查询的所有列都在普通索引里（覆盖索引），就不用回表。比如 `SELECT name FROM user WHERE name = '张三'`，直接在 `idx_name` 就能拿到 name 值，这就是**覆盖索引优化**，explain 里会显示 `Using index`。

### Q3 ⭐: B+ 树和 B 树的区别是什么？为什么 MySQL 选 B+ 树而不是 B 树？

**高分回答：**

"这道题是索引原理的必问题，很多人在网上看过答案但说不出所以然。

**B+ 树 vs B 树，核心区别就三条：**

| | B 树 | B+ 树 |
|--|------|-------|
| 数据存储 | 所有节点都存数据 | 只有叶子节点存数据 |
| 叶子节点 | 不互连 | **链表连接**（顺序访问） |
| 查询稳定性 | 不一定稳定（可能在非叶子就找到） | 每次都要到叶子，**查任何行都是 O(logN)** |

**为什么 MySQL 选 B+ 树？**

两个原因，都很硬核：

**1. 更大的扇出（fan-out）——减少 IO 次数**

B+ 树的非叶子节点只存索引 key 和指针，不存数据。MySQL 一页默认 16KB，假设 key 是 8 字节 + 指针 6 字节 = 14 字节，一页能存 `16384/14 ≈ 1170` 个索引项。

3 层的 B+ 树可以存：`1170 × 1170 × 16 = 约 2190 万` 条数据。也就是说对于 2000 万行的表，**查任何一条数据都只需要 3 次 IO**——这就是为什么千万级查询还能毫秒返回。

换成 B 树：非叶子也要存数据，一个节点能存的 key 数量大大减少，树更高，IO 更多。

**2. 叶子节点链表 —— 范围查询极快**

```sql
SELECT * FROM user WHERE age BETWEEN 20 AND 30;
```

B+ 树找到 20 的叶子节点后，沿着叶子链表向右遍历到 30 就行。B 树做不到这一点——你必须来回在树上下游走，随机 IO 多到崩溃。

> 💡 面试官可能会接着问：那 B+ 树每页 16KB 能调吗？——可以，`innodb_page_size` 可选 4K/8K/16K/32K/64K，但改完需要重建整个实例。建议用默认 16K，除非你有非常特殊的场景（比如 SSD 小页访问优化）。

### Q4 ⭐: 什么是联合索引？最左前缀原则是什么意思？

**高分回答：**

"联合索引（Composite Index）就是把多个列联合起来建一个索引，结构上还是 B+ 树，只是 key 由多个列拼接而成。

**最左前缀原则（Leftmost Prefix）：**

直接上例子：

```sql
-- 建联合索引
ALTER TABLE user ADD INDEX idx_name_age_city (name, age, city);

-- 能命中索引的查询（走最左前缀）
WHERE name = '张三'                    -- ✅ 只用了 name
WHERE name = '张三' AND age = 25       -- ✅ name + age
WHERE name = '张三' AND age = 25 AND city = '北京'  -- ✅ 完全匹配
WHERE name LIKE '张%'                  -- ✅ 前缀like匹配

-- 不能命中或部分命中的查询
WHERE age = 25                        -- ❌ 跳过了 name
WHERE city = '北京'                    -- ❌ 跳过了 name 和 age
WHERE name = '张三' AND city = '北京'   -- ⚠️ 能用到 name，但 city 用不了
```

**面试必说的核心：**

MySQL 的联合索引像一本"先按姓排、再按名排、再按城市排"的电话本——你不告诉我姓，我根本没法找。

更底层的理解是：B+ 树的 key 是按 `(name, age, city)` 这个顺序拼接的。判断能不能用索引，就是看查询条件里**有没有从最左边开始的连续前缀**。

**这里有个容易被忽略的坑：** WHERE name = '张三' AND city = '北京' 为什么只用到了 name？因为索引排序是 name → age → city，name 相同的行按 age 排，而 city 被跳过了——MySQL 在 name 定位后，需要用 age 才能继续走索引，但 age 不在条件里，所以只能 age 全扫，city 就用不上了。

> 💡 实战技巧：经常查 `WHERE name= AND city=` 但没有 age 的场景，可以建 `(name, city)` 索引而不是 `(name, age, city)`，或者用 MySQL 8.0 的**跳跃索引（Skip Scan）** 来优化部分场景。

### Q5 ⭐: 索引是不是越多越好？什么时候不应该建索引？

**高分回答：**

"这个问题面试官想听的是——你踩过坑。说真的，新人最容易犯的错误就是"凡是查询慢就加索引"。

**索引不是免费的：**

1. **写入变慢**——每次 INSERT/UPDATE/DELETE 都要维护索引树。一个表如果有 5 个索引，写一次就是 1 次数据操作 + 5 次索引维护。
2. **占用磁盘**——索引也是 B+ 树，也是要存磁盘的。特别是联合索引，大字段索引占的空间不小。
3. **优化器也会困惑**——索引太多，优化器选错索引的风险更大（选了一个次优索引，不如全表扫）。

**具体来说，这些场景不应该建索引：**

- **数据量小**——几千条的表全表扫比索引 IO 还快。MySQL 优化器会自己判断（`table_rows` 小的时候自动走全表扫）
- **区分度低的列**——比如性别（男/女），二分性太好，索引扫一遍和全表扫差不多
- **频繁更新的列**——比如大表的 `last_login_time`，每次登录都更新，索引不断分裂重组
- **很少查询的大字段**——比如 TEXT 类型的字段，多建个前缀索引就够了

**我说句实话：** 实际工作中，一个 OLTP 表的索引数量建议控制在 **5 个以内**。超过 5 个，每次上线评估索引改动都要花很大精力。

> 💡 加分回答：线上怎么判断索引该删？用 `sys.schema_unused_indexes` 视图！MySQL 8.0 提供这个视图可以直接查出哪些索引从来没被用过，配合 `performance_schema` 的表访问统计，就是你的索引清理清单。

### Q6 ⭐⭐: 执行计划（EXPLAIN）怎么看？说几个你经常看的字段。

**高分回答：**

"EXPLAIN 是 MySQL 调优的基本功。我每次线上慢查询排查，第一件事就是 `EXPLAIN`。

**我会重点看这几个字段：**

**1. type —— 访问类型，性能从好到差排序：**

```
system > const > eq_ref > ref > range > index > ALL
```

- `const`：主键或唯一索引等值查询，最多返回一行——最快
- `ref`：普通索引等值查询
- `range`：范围查询（`BETWEEN`、`>`、`<`、`IN`）
- `index`：扫全索引树（但不用回表）
- `ALL`：全表扫——**这是红线，SQL 上线的红线**

线上 SQL 的 type 至少要到 `range` 级别。

**2. key —— 实际使用的索引**
**3. rows —— MySQL 估算的需要扫描的行数**
**4. Extra —— 额外信息，重点关注这些：**

```
Using index        → ✅ 覆盖索引，不回表（好）
Using where        → ⚠️ 回表后在服务层过滤（正常但注意）
Using filesort     → ❌ 在内存排序，超出容量会写磁盘（慢）
Using temporary    → ❌ 用了临时表（GROUP BY 没用好索引）
Using index condition → ✅ 索引下推（ICP），MySQL 5.6+ 优化
```

**实战例子：**

```sql
-- 假如有一个慢查询
EXPLAIN SELECT * FROM order WHERE status = 1 ORDER BY create_time DESC\G
```

如果看到 `Using filesort`，说明 `status` 和 `create_time` 没建成联合索引。建一个 `(status, create_time)` 索引，filesort 就消失了。

> 💡 细节：`EXPLAIN FORMAT=JSON` 能看到更详细的信息，包括实际扫描行数、成本估算、ICP 是否用到等。`EXPLAIN ANALYZE`（MySQL 8.0.18+）能给出**实际执行时间**，比估算的 rows 准得多。

### Q7 ⭐⭐: 什么情况会导致索引失效？说说你遇到过的坑。

**高分回答：**

"这个问题我太有发言权了——线上踩过不少坑。

**最常见的索引失效场景：**

**1. 对索引列做了函数操作**

```sql
-- 失效
WHERE DATE(create_time) = '2026-05-24'
-- 应改为：
WHERE create_time >= '2026-05-24 00:00:00' AND create_time < '2026-05-25 00:00:00'
```

**2. 隐式类型转换**

```sql
-- phone 列是 VARCHAR 但传了数字 13800138000
WHERE phone = 13800138000   -- ❌ 类型不匹配，MySQL 会做隐式 CAST，索引失效
WHERE phone = '13800138000'  -- ✅ 
```

**3. 不等于、NOT IN 和 IS NOT NULL**

```sql
WHERE status != 1           -- 不走索引（不等于难定位）
WHERE id NOT IN (1,2,3)     -- 同上
WHERE name IS NOT NULL      -- 某些情况不走
```

**4. LIKE 通配符在前**

```sql
-- 失效
WHERE name LIKE '%张%'
-- 可以用（前缀匹配）
WHERE name LIKE '张%'
```

**5. OR 条件**

```sql
-- 如果 OR 两边的字段不是都有索引，SQL 可能不走索引
WHERE name = '张三' OR age = 25  -- 建议用 UNION 改写
```

**6. 优化器选择全表扫比索引快**

数据量太小、或者用了索引要扫 80%+ 的行（回表太多），优化器认为不如全表扫。这种情况可以用 `FORCE INDEX` 强制走，但建议先分析为什么数据分布这么差。

**踩过的坑：**

有一次线上 `2000 万` 行的大表，查询突然变慢。查了半天发现是业务代码里传了 `id = '123'`——id 是 bigint，但传的是字符串。MySQL 隐式转换后索引失效，全表扫了十几秒。改成一个数字，30 毫秒回来了。

> 💡 避坑指南：建表时就约定好传参类型，Java 里别想着"反正能自动转"——JPA/MyBatis 有时候会偷偷转类型。

### Q8 ⭐⭐: MySQL 有哪几种锁？行锁、表锁、间隙锁分别说清楚。

**高分回答：**

"MySQL 的锁机制面试必考，我按粒度从小到大说：

**1. 表级锁（Table Lock）**

- **表锁**：`LOCK TABLES ... READ/WRITE`，一般不手动用，MyISAM 才依赖
- **MDL（元数据锁）**：自动加的，ALTER TABLE 的时候会加 MDL 写锁，阻塞对这个表的所有 CRUD。线上大表 DDL 挂在那，后面的查询全堵了——这是一个经典的**生产事故场景**
- **意向锁**：InnoDB 特有的"预占声明"，比如要给行加 X 锁，先给表加 IX 锁。别人要加表锁时一看有意向锁，就知道表里可能有行级锁，不用全表遍历检查了

**2. 行级锁（Row Lock）——InnoDB 的核心优势**

行锁有三种实现：

```
Record Lock     → 锁住索引记录本身
Gap Lock        → 锁住记录之间的间隙
Next-Key Lock   → 上面两个合体 = Record Lock + Gap Lock
```

**3. 间隙锁（Gap Lock）——最容易踩坑**

间隙锁锁的是**索引记录之间的间隙**，目的是防止幻读。举个例子：

```sql
-- 假设 user 表 id 有 1, 3, 5, 8
-- 事务 A 执行：
SELECT * FROM user WHERE id BETWEEN 3 AND 5 FOR UPDATE;
-- 锁住了 id=3 和 id=5 这两行以及中间的间隙 (3,5)
-- 事务 B 要 INSERT id=4 会被阻塞
```

**这里有个坑：** 间隙锁是**范围判断**的，如果你查的是一个不存在的记录，它会锁更大的范围。比如：

```sql
-- 事务 A 查了不存在的 id=7
SELECT * FROM user WHERE id = 7 FOR UPDATE;
-- 🔴 实际锁了 (5, 8) 这个间隙，并发插入 id=6 或 id=7 都会被阻塞
```

**线上建议：** 间隙锁虽然是 RR 隔离级别的标准行为，但高并发下容易造成锁冲突。业务允许的话，将隔离级别降到 **RC（Read Committed）** 可以避免间隙锁，性能会好不少。MySQL 的默认 GTID 复制模式下 RC 完全没问题。

> 💡 加分点：MySQL 8.0 对间隙锁做了优化——`innodb_autoinc_lock_mode=2`（交错模式）下 INSERT 不再持有自增锁，减少了写并发冲突。

### Q9 ⭐⭐: MVCC 是什么？能说一下它的实现原理吗？

**高分回答：**

"MVCC（Multi-Version Concurrency Control）是多版本并发控制，它是 InnoDB **实现 RC 和 RR 隔离级别的核心机制**——不用加锁、读不阻塞写、写不阻塞读。

**MVCC 靠三个东西实现：**

**1. 隐藏列**

InnoDB 每行数据有三个隐藏列：

```
DB_TRX_ID  → 最近修改这行的事务 ID
DB_ROLL_PTR → 回滚指针（指向 undo log 中的上一个版本）
DB_ROW_ID  → 隐式自增 ID（没主键时用它）
```

**2. undo log（undo 日志）**

每修改一行，旧版本数据就写到 undo log。`DB_ROLL_PTR` 把当前行和它的历史版本串成了一个**版本链**。

**3. ReadView（一致性视图）**

当事务执行快照读（普通的 SELECT），就生成一个 ReadView，里面记录：

- `m_ids`：当前活跃的事务 ID 列表
- `min_trx_id`：活跃列表中最小的 ID
- `max_trx_id`：已分配的最大事务 ID + 1
- `creator_trx_id`：创建这个 ReadView 的事务自己的 ID

**判断规则（面试要能画出来）：**

```
DB_TRX_ID < min_trx_id    → ✅ 版本可见（已提交）
DB_TRX_ID >= max_trx_id   → ❌ 版本不可见（将来的事务）
DB_TRX_ID 在 m_ids 中     → ❌ 不可见（未提交的活跃事务）
DB_TRX_ID == creator_trx_id → ✅ 可见（自己改的）
```

**RC vs RR 的区别：**

- **RC**：每次 SELECT 都生成新的 ReadView
- **RR**：事务中**第一次 SELECT 生成 ReadView**，后面复用

这就是为什么 RR 能避免不可重复读（第二次读到的还是同一个 ReadView，看到的数据一样），而 RC 不行（每次都新 ReadView，能看到别的事务提交的数据）。

**我说句实话：** 很多人背了 MVCC 却说不清楚"版本链"到底是怎么串的。其实很简单——每次 UPDATE 不会直接覆盖老数据，而是生成一个新版本行，旧版本行通过 undo log 链起来。DELETE 也是"标记删除"（purge 线程真正清理）。这样就实现了多版本。

> 💡 追问：undo log 会一直保留吗？——不会。InnoDB 的 **purge 线程**会定期清理，当事务不再需要某个版本的 undo log 时（没有 ReadView 引用了），就删除。

### Q10 ⭐⭐: RR 隔离级别怎么解决幻读的？真的完全解决了吗？

**高分回答：**

"这个问题问得很细，很多面试者说"RR 解决了幻读"就停了，但面试官想听的是——**怎么解决的、有没有没解决的情况**。

**InnoDB 解决幻读靠的是 Next-Key Lock：**

假设 user 表 id 有 1, 3, 5：

```sql
-- 事务 A：
SELECT * FROM user WHERE id > 3 FOR UPDATE;
-- 不仅锁住了 id=5 这一行
-- 还锁住了 (3, 5) 和 (5, +∞) 两个间隙

-- 事务 B：INSERT INTO user (id=4, ...) → ❌ 被阻塞
-- 事务 B：INSERT INTO user (id=10, ...) → ❌ 也被阻塞
```

**所以 RR 下，幻读的「幻影行」根本插不进来。**

**但是——"完全解决"这个说法不严谨。** 有两种情况 RR 防不住：

**1. 当前读（SELECT ... FOR UPDATE / UPDATE / DELETE），但间隙锁没锁住**

比如条件走的是非唯一索引，间隙锁的范围可能比预期小。

**2. 注意区分"快照读"和"当前读"**

- `SELECT`（快照读）：靠 ReadView 机制，RR 下始终看到同一份数据
- `SELECT ... FOR UPDATE`（当前读）：需要最新的数据，会读已经提交的最新版本

**真正的完全解决只有 Serializable 隔离级别**——所有读都变成当前读，全部加锁。但代价是并发度极低，生产很少用。

**线上建议：** 如果你的业务场景有"先查后插"的需求，老老实实在 RR 下用 `SELECT ... FOR UPDATE` 或者 `INSERT ... ON DUPLICATE KEY UPDATE` 来做防重。

> 💡 加分点：MySQL 8.0 对幻读的处理在 `SELECT ... FOR UPDATE` 上更智能了——`NOWAIT` 和 `SKIP LOCKED` 可以让你跳过阻塞的行，在高并发秒杀场景非常有用。

### Q11 ⭐⭐⭐: InnoDB 的 Change Buffer 是什么？什么时候起效，什么时候没用？

**高分回答：**

"这个问题能看出来你理不理解 InnoDB 的**写入优化机制**，很多人甚至不知道 Change Buffer 的存在。

**Change Buffer 是什么？**

当你要修改的**二级索引（非唯一）页不在 buffer pool 中**时，InnoDB 不会立刻去磁盘读这个页再改，而是把修改记录到 Change Buffer 里。

等下次需要读这个页的时候，再把 Change Buffer 中的修改**合并（merge）**到索引页上——这叫 **延迟写入**。

**换个说法：把随机写变成顺序写，攒一批再干。**

**起效的场景（能显著提升性能）：**

- **插入/更新大量二级索引**——比如你往一张大表里批量插入数据，主键索引是聚簇的（按顺序写入），但 5 个二级索引全是随机写入。Change Buffer 把 5 次随机 IO 变成了"攒够一波再 merge"
- **数据量远大于内存**——buffer pool 放不下所有二级索引页，Change Buffer 减少磁盘读取

**没用的场景：**

- **唯一索引**——因为唯一索引修改时必须读磁盘确认唯一性，Change Buffer 不生效
- **主键索引**——聚簇索引用的不是 Change Buffer，而是自适应哈希索引等其他机制
- **索引页已经在 buffer pool 中**——已经在内存了，直接改就行，不需要缓存
- **表做大量 DDL 时**——Change Buffer 不会在 DDL 期间发挥作用

**参数配置：**

```ini
innodb_change_buffer_max_size = 25  # Change Buffer 占用 buffer pool 的最大百分比，默认 25%
innodb_change_buffering = all       # 可配置：all/none/inserts/deletes/changes/purges
```

**我说句实话：** 很多 DBA 知道 Change Buffer 但生产上很少调整。唯一值得关注的就是**写入密集的表如果全是非唯一索引**——可以考虑把 `change_buffer_max_size` 从 25% 调到 50%，尤其是那种"大量 INSERT 后很少读取"的场景（比如日志表）。

> 💡 追问：Change Buffer 和 Redo Log 什么关系？——先写 Change Buffer，然后在内存标记 dirty。刷盘时 Change Buffer 本身也是通过 redo log 做持久化的，所以 crash 恢复时不会丢。合并操作也会产生 redo log。

### Q12 ⭐⭐⭐: 一条 UPDATE 语句在 InnoDB 内部经历了什么？说清楚完整的执行流程。

**高分回答：**

"这个问题是源码级面试题。一条 `UPDATE user SET age=18 WHERE id=1` 在 InnoDB 内部经历了至少 7 个关键步骤，我按顺序说：

```sql
-- 假设原始数据：id=1, name='张三', age=20
UPDATE user SET age = 18 WHERE id = 1;
```

**Step 1: 解析器 → 优化器 → 执行器**

MySQL Server 层先解析 SQL，优化器选择用主键索引（id=1），执行器调用 InnoDB 接口。

**Step 2: 通过主键索引找到记录页**

- 检查 id=1 的页是否在 buffer pool
- 不在 → 从磁盘读入 buffer pool（**这里是一次随机 IO**）

**Step 3: 加锁**

- 主键 id=1 是唯一索引，加 **Record Lock**（不是 Next-Key Lock，唯一索引等值查找最多只会锁一行）
- 如果没走索引，会锁整张表或者大量行——线上事故的常见原因

**Step 4: 记录旧版本到 undo log**

```text
undo log 记录：{id=1, age=20}  → 供 MVCC 快照读和回滚
```

- `DB_TRX_ID` 更新为当前事务 ID
- `DB_ROLL_PTR` 指向刚刚在 undo log 中写入的旧版本

**Step 5: 在内存中修改数据页**

buffer pool 中的 page 改成 age=18，标记为 **dirty page**。

**Step 6: 写入 redo log（WAL —— Write-Ahead Logging）**

```text
redo log 记录：MLOG_REC_UPDATE, space_id, page_no, 偏移量, 新值
```

这个日志先写 **redo log buffer**，然后 `log buffer → OS cache → 磁盘文件`（取决于 `innodb_flush_log_at_trx_commit` 配置）。

**Step 7: 写入 binlog（Server 层）**

binlog 记录的是**逻辑 SQL**。注意：redo log 和 binlog 的写入通过**两阶段提交**保持一致性。

**两阶段提交（崩溃安全的关键）：**

```
1. InnoDB Prepare → 写 redo log，状态为 PREPARE
2. Server 写 binlog → 完成时记录 XID
3. InnoDB Commit → redo log 状态改为 COMMIT
```

如果第 2 步后崩溃——恢复时发现 redo log 是 PREPARE 且 binlog 有对应 XID → 提交完成。如果 binlog 没有 → 回滚。

这就是 **crash-safe** 的保证。

> 💡 追问：dirty page 什么时候写回磁盘？——Checkpoint 机制。当 redo log 快满、或 buffer pool 空间不足、或系统空闲时，触发刷脏页。Checkpoint 使得 redo log 可以被重用，也保证崩溃恢复时不需要重放所有日志。

### Q13 ⭐⭐⭐: 分库分表怎么做？ShardingSphere 和 MyCat 怎么选？

**高分回答：**

"面试官问这个，是想看你在**单库扛不住的时候怎么设计的**。

**什么时候必须分库分表？**

- 单表数据过 **千万级**，索引深度超过 3 层 B+ 树
- 单库连接数不够（比如 4000+ 连接）
- 写成为瓶颈（比如每秒写入 5 万+）

**分库分表的策略：**

**1. 垂直分库（按业务拆分）**

用户库、订单库、商品库——这是最自然的拆分最先该做的。

**2. 分表策略（核心）**

```
Hash 分片     → 根据用户 ID 取模，均匀分布
Range 分片    → 按时间/ID范围分段（方便归档，但可能热点）
一致性 Hash   → 减少扩缩容时的数据迁移
```

**3. 核心问题：跨分片查询**

```text
跨分片 JOIN    → ❌ 基本不支持，聚合层做
全局排序/分页  → ⚠️ 需要聚合后重新排序，代价大
分布式事务    → ⚠️ 建议用 Seata 或业务最终一致性
全局主键      → ✅ 雪花算法（Snowflake）或号段模式（Leaf）
```

**ShardingSphere vs MyCat 怎么选：**

| | ShardingSphere-JDBC | MyCat |
|--|-------------------|-------|
| 定位 | 客户端分片（嵌入应用） | 代理层分片（独立部署） |
| 协议 | 直连，不走额外网络 | JDBC 连接，走代理 |
| 性能 | 高（无网络跳转） | 中等（多了一层代理） |
| 连接数 | 多个分片多个连接 | 统一入口，连接数少 |
| SQL 兼容 | 好，ShardingSphere 5.x 支持的 SQL 多 | 一般，MyCat 2 有改进 |
| 运维 | 无额外部署 | 需要维护 MyCat 集群 |
| 学习成本 | 中等 | 较低 |

**我说句实话：** 我推荐 **ShardingSphere-JDBC**。原因是：

1. 没有中间代理，延迟低一个数量级
2. 作为 Spring 生态的一部分，配置和整合都很顺
3. MyCat 的分片算法不如 ShardingSphere 灵活
4. ShardingSphere 5.x 支持了分布式事务（XA/BASE）、读写分离、影子库等

**但是小团队或老旧项目：** 如果不想改代码，MyCat 做代理层更省事——应用层完全无感知。

> 💡 注意：分库分表是最后的手段。90% 的情况下，**分库 + 冷热分离 + 缓存** 已经能解决问题了。上来就分表，查个订单还得聚合，运维复杂度直接翻番。

### Q14 ⭐⭐⭐: 从 MySQL 角度看，AI 场景中数据存储有哪些挑战？你怎么设计一个 Embedding 向量存储方案？

**高分回答：**

"这个问题是 MySQL + AI 的交叉考点，很有实际价值。

**AI 场景下 MySQL 做存储的挑战：**

- **向量存储**——MySQL 原生不支持向量检索，只能把向量存成 BLOB/JSON，在应用层算相似度
- **高吞吐写入**——LLM 中间结果、用户会话日志、推理请求日志，都是几万 QPS 级别写入
- **半结构化数据**——LLM 的 prompt/response/思考链 这些字段，长度不定，格式不定
- **混合查询**——既要按标签匹配，又要向量相似度排序，MySQL 做这种混合查询效率很低
- **TTL 需求**——会话数据有生命周期，MySQL 需要定期 purge，压力不小

**那如果必须 MySQL + 向量，怎么设计？**

**方案一：MySQL 存元数据，向量存专用引擎（推荐）**

```sql
-- MySQL 只存业务元数据
CREATE TABLE knowledge_doc (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(255),
  content TEXT,
  category VARCHAR(50),
  vector_id VARCHAR(64) COMMENT '对应向量数据库中的 ID',
  create_time DATETIME,
  FULLTEXT idx_content (content)
);

-- 向量存在 Milvus/Qdrant/Pinecone
-- Java/Python 代码做混合查询：
-- 1. MySQL 全文搜索 + 标签过滤 → 获得 doc_ids
-- 2. 从向量库用 doc_ids 过滤 + 向量检索
-- 3. 合并结果排序
```

**方案二：MySQL + MySQL HeatWave（Oracle 云场景）**

MySQL HeatWave 支持向量存储和 ANN 搜索：

```sql
-- HeatWave 8.0.36+ 支持
SELECT id, title,
       VEC_DISTANCE(embedding, VEC_FromText('[0.12, 0.34, ...]')) AS distance
FROM knowledge_doc
ORDER BY distance
LIMIT 10;
```

**但如果你坚持只用 MySQL 社区版？**

可以用 BLOB 存向量，应用层做近似搜索：

```python
# Python 示例：MySQL + numpy 做近似检索（小规模）
import mysql.connector
import numpy as np

def search_similar(target_vec: list, limit: int = 10):
    cursor.execute("SELECT id, embedding FROM knowledge_doc")
    results = []
    for row in cursor.fetchall():
        db_vec = np.frombuffer(row[1], dtype=np.float32)
        sim = np.dot(target_vec, db_vec)  # 余弦相似度简化版
        results.append((row[0], sim))
    results.sort(key=lambda x: x[1], reverse=True)
    return results[:limit]
```

**这个方案有个致命问题：** 全表扫描算相似度，百万级数据一次查询要算几秒钟。**只适合几千条的小规模场景。**

**实际建议：** 对于 AI 应用，别强行让 MySQL 做向量检索。用 **分层架构**——MySQL 存业务数据，ES 做全文搜索，专用向量库建索引。各自发挥各自的长处。

> 💡 扩展点：MySQL 9.0 的 InnoDB 已经开始实验性支持 Vector 类型了！存储格式是 `VECTOR(1536)` 的二进制编码，还提供了 `VEC_DISTANCE_EUCLIDEAN` 和 `VEC_DISTANCE_COSINE` 函数——但到 GA 阶段可能还要等几个版本。

### Q15 ⭐⭐⭐: 假如线上 MySQL 突然 CPU 100%，你作为值班 DBA 怎么排查？

**高分回答：**

"这是一个典型的**生产应急场景**问题。我经历了至少 3 次类似的线上事故，说说标准排查流程。

**第一反应：别慌，按流程来。**

**Step 1: 快速定位是哪个进程在吃 CPU**

```bash
top -c               # 看哪个 MySQL 线程 CPU 最高
```

或者 MySQL 内部：

```sql
SHOW PROCESSLIST;
-- 重点关注 State 列：Sending data / Creating sort index / Locked 等
```

**Step 2: 抓慢查询**

```sql
-- 查看正在运行中最消耗 CPU 的查询
SELECT * FROM sys.statement_analysis 
ORDER BY avg_latency DESC 
LIMIT 10;

-- 或者直接
SELECT * FROM performance_schema.events_statements_current\G
```

找到高 CPU 的线程后：

```sql
-- 如果是紧急的大查询，先 kill 掉
SHOW PROCESSLIST;
-- 看到 Time 特别大或者 State 是 Creating sort index 的
KILL <thread_id>;
```

**Step 3: 分析根因（找到慢的 SQL）**

```sql
EXPLAIN ANALYZE <那个慢查询>\G
```

关注的典型场景：

| 现象 | 根因 |
|------|------|
| `type: ALL`（全表扫） | 没索引或索引失效 |
| `rows: 500万` | 查询没走对索引 |
| `Using temporary; Using filesort` | GROUP BY/ORDER BY 没用好索引 |
| `Locked` | 死锁或锁等待 |
| 大量 `Opening tables` | 表缓存满了 |

**Step 4: 看看是不是突增流量**

```bash
# 确认 QPS/TPS 是否暴涨
mysqladmin extended-status -i 1 | grep -E 'Questions|Threads_connected'
```

观察 `Threads_connected` 是否暴增，如果从 200 涨到 2000 连接数打满——那就是流量问题，不是 SQL 本身慢。

**Step 5: 持久化方案**

如果是索引问题：

```sql
-- 先记录慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒的记录
```

然后分析 **慢查询日志** + 确认索引 + 改 SQL 或加索引。

**如果上面都排查了还是 CPU 高：**

- **buffer pool 太小** → 磁盘 IO 频繁，CPU 大量花在 io wait 上
- **事务没有 COMMIT** → 大量行锁、undo log 膨胀
- **InnoDB 刷脏页太频繁** → `innodb_io_capacity` 配置不合理
- **全文索引扫描** → 全文索引对 CPU 消耗很大
- **并行复制堆积** → 备库延迟导致 IO 吃满

**我说句实话：** 排查 CPU 100% 最怕的心态是"性能优化=加索引"。我见过一个真实案例：排查了 3 小时，最终发现是同一个表 8 个 DDL 在排队，MDL 写锁把后面所有查询堵住了——`SHOW PROCESSLIST` 看到全是 `Waiting for table metadata lock`。加个索引有啥用？

> 💡 核心建议：在 server 端配上 **监控告警**——Prometheus + mysqld_exporter + Grafana，CPU、连接数、慢查询数、锁等待这些指标一定要有看板。问题发生前就能先看到趋势，等 CPU 100% 了才看就已经晚了。
