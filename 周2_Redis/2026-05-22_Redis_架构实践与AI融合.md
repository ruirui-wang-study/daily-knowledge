### Q1 ⭐: Redis 事务（MULTI/EXEC/WATCH）到底是不是事务？和数据库事务有什么区别？

**面试官想听什么：** 很多人张口就说"Redis 支持事务"，实际上 Redis 的事务和 MySQL 的事务完全不是一回事。面试官想看你能不能分清楚。

**高分回答：**

"说实话，Redis 的事务是个'阉割版'的事务。叫它事务其实有点误导人。

**Redis 事务的执行流程：**

```bash
MULTI        # 开启事务
SET key1 val1
SET key2 val2
GET key1
EXEC         # 执行事务
```

`MULTI` 和 `EXEC` 之间把所有命令排队，`EXEC` 时一并执行。

**Redis 事务的三个核心特性对比数据库事务：**

| 特性 | MySQL 事务 | Redis 事务 |
|------|-----------|-----------|
| **原子性** | ✅ 全成功或全回滚 | ⚠️ 不支持回滚——命令入队时语法错误会拒绝，运行时错误不中断（比如对一个 String LPUSH） |
| **一致性** | ✅ | ⚠️ 同上 |
| **隔离性** | ✅ MVCC | ✅ 单线程，天然隔离，但 WATCH 机制做乐观锁 |
| **持久性** | ✅ redo log | ⚠️ 取决于持久化配置（AOF everysec 最多丢 1 秒） |

**这里有三个关键差别，面试说出来就是加分：**

**1. Redis 事务不支持回滚。** 如果 `EXEC` 执行过程中某个命令失败（比如对一个 String 类型做 LPUSH），Redis 会继续执行后面的命令，不会回滚之前成功的操作。antirez 的原话是："Redis 命令失败通常是编程错误，应该在开发阶段发现。"

**2. WATCH 实现乐观锁。** 这是 Redis 事务的精髓：
```bash
WATCH stock:1001       # 监视这个 key
val = GET stock:1001   # 读取当前值
MULTI
SET stock:1001 val - 1
EXEC                   # 如果 stock:1001 在 WATCH 后被别的客户端改了，EXEC 返回 nil
```
WATCH 基于 CAS（Compare and Swap），但它检查的不是值，而是 **key 是否被修改过**。如果 `EXEC` 时发现监视的 key 被改过，整个事务就取消。

**3. 事务是"一次性批量执行"不是"交互式执行"。** 入队时不会检查命令的"运行时正确性"——比如你对一个不存在的 key 做 GET，Redis 在入队时不会报错，只有在 EXEC 执行时才会返回错误。

**总结：** Redis 事务更适合叫"批处理命令集 + 乐观锁"。它没有真正的原子性和回滚能力，但用好了能解决很多并发问题——比如库存扣减、秒杀等场景。"

> 💡 面试加分：能说出"Redis 事务 + Lua 脚本"的组合方案——"Lua 脚本天然具备原子性，比事务更强。如果要保证一组命令要么全成功要么全失败，用 Lua 脚本而不是 MULTI/EXEC。"

### Q2 ⭐: Lua 脚本在 Redis 里的正确使用姿势——EVAL 和 Script Load 有什么区别？

**高分回答：**

"Lua 脚本本质上是把一段逻辑注册到 Redis 服务端，让 Redis 在服务端执行，**所以它能保证原子性**——脚本执行期间不会有其他命令插入。

**两种执行方式：**

```bash
# 方式 1：EVAL - 每次传脚本内容
EVAL "return redis.call('GET', KEYS[1])" 1 mykey

# 方式 2：SCRIPT LOAD + EVALSHA - 预加载，传 SHA
SCRIPT LOAD "return redis.call('GET', KEYS[1])"
# 返回：sha1 哈希值，比如 "6b1bf486c81ceb..."
EVALSHA "6b1bf486c81ceb..." 1 mykey
```

**生产环境到底用哪种？**

我说句实话：**永远用 SCRIPT LOAD + EVALSHA**。原因很简单——如果每次都用 EVAL，网络传输脚本内容就是浪费。尤其在高并发场景下，脚本内容越大，浪费越明显。

但这里有个坑：如果 Redis 重启了，缓存的脚本就丢了，EVALSHA 返回 `NOSCRIPT` 错误。所以客户端得有个**兜底逻辑**：

```java
// Java + Jedis 的正确用法
public String evalScript(Jedis jedis, String scriptSha, List<String> keys, List<String> args) {
    try {
        return (String) jedis.evalsha(scriptSha, keys, args);
    } catch (JedisNoScriptException e) {
        // 脚本没加载过，回退到 EVAL
        return (String) jedis.eval(scriptSha, keys, args);
        // 注意：这里传的是 scriptSha 其实是 Lua 脚本内容
        // 实际上应该传脚本源码，这里为了示意
    }
}
```

**Lua 脚本在 AI 场景的妙用：**

```lua
-- 带 TTL 的限流脚本（结合 AI 模型的调用频率限制）
-- KEYS[1] = 限流 key, ARGV[1] = 窗口大小(秒), ARGV[2] = 阈值
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])

local current = redis.call('INCR', key)
if current == 1 then
    redis.call('EXPIRE', key, window)
end

if current > limit then
    return 0  -- 限流
end
return 1  -- 放行
```

**Lua 脚本的使用原则（面试加分）：**
1. 脚本尽量简短——长时间执行的脚本会阻塞 Redis 单线程
2. 不要用随机函数（如 `math.random`）——会导致主从数据不一致
3. KEYS 用数组传，别硬编码到脚本里——可读性差、复用性差
4. Redis 7.0 开始推荐用 **Functions** 替代 Lua 脚本——可以统一注册管理

> 💡 追问：Lua 脚本什么情况下会导致主从复制延迟？——如果脚本里写了 `TIME` 或者 `RANDOMKEY` 这种非确定性命令，主从执行结果可能不同，Redis 会把脚本本身复制到从节点执行，而非复制写命令。所以建议别在脚本里用非确定性命令。

### Q3 ⭐: Redis 的发布订阅（Pub/Sub）在微服务架构里有什么用？和消息队列的差别在哪？

**面试官想听什么：** 问 Pub/Sub 的核心是看你能不能分清"轻量级消息转发"和"消息队列"的边界。很多新人一说消息就想到 Pub/Sub，但真实场景里用它得谨慎。

**高分回答：**

"Redis Pub/Sub 本质上是一个**广播通道**——一个发布，所有订阅者都能收到。

```bash
# 订阅端（消费者）
SUBSCRIBE channel:order:paid

# 发布端（生产者） 
PUBLISH channel:order:paid "order_12345_paid"
```

**Pub/Sub 在微服务里的应用场景：**

1. **缓存失效通知**——多个微服务实例共享同一个 Redis 缓存，一个实例更新了数据，发个消息通知其他实例清除本地缓存
2. **配置变更广播**——配置中心更新配置后，广播通知所有服务重新加载
3. **实时消息推送**——聊天室的即时消息（不需要持久化的场景）
4. **哨兵故障通知**——哨兵切换 Master 后，会通过 Pub/Sub 通知客户端

**但它跟消息队列（Kafka/RocketMQ/RabbitMQ）有本质区别，面试时说出来就是加分：**

| 能力 | Redis Pub/Sub | 消息队列 |
|------|--------------|---------|
| **消息持久化** | ❌ 发了就没了，没订阅者就丢了 | ✅ 持久化到磁盘 |
| **回溯消费** | ❌ 不能 | ✅ 按 offset 回溯 |
| **消费者组** | ❌ 所有订阅者都收到全部消息 | ✅ 一条消息只被组内一个消费者消费 |
| **可靠投递** | ❌ 网络断开期间的消息全丢 | ✅ ACK + 重试 |
| **积压能力** | ❌ 消费跟不上会缓存积压...其实是会丢 | ✅ 积压到磁盘 |

**有个很要命的限制：** 如果某个消费者处理慢了，Redis 不会给你缓冲。Pub/Sub 用的是 **TCP 缓冲区**——如果缓冲区满了，Redis 直接断开连接。所以你没法用 Pub/Sub 处理"生产速度 > 消费速度"的场景。

**我的建议：** 微服务架构里大部分场景用消息队列，Pub/Sub 只用在"丢了无所谓 + 广播通知 + 即时"的场景。特别是 AI 场景里——比如模型更新通知、embeddings 刷新广播，用 Pub/Sub 挺合适，但做任务编排、异步落单这些必须用专业 MQ。"

> 💡 面试官可能追问：哨兵模式切换 Master 后，客户端怎么感知？——哨兵通过 Pub/Sub 的 `+switch-master` 频道通知客户端，客户端收到后需要更新连接信息。Jedis 的 JedisSentinelPool 就是监听这个频道实现的。

### Q4 ⭐: Spring Boot 整合 Redis 的最佳实践——CacheManager 配置 + 序列化有哪些坑？

**高分回答：**

"Spring Boot 整合 Redis 很简单，但**序列化**是最大的坑。很多人默认用 JdkSerializationRedisSerializer，结果存进去全是乱码，线上查数据还得写 Java 代码反序列化。

**正确的序列化配置：**

```java
@Configuration
@EnableCaching
public class RedisConfig {
    
    @Bean
    public RedisTemplate<String, Object> redisTemplate(
            RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);
        
        // 核心：用 JSON 序列化
        Jackson2JsonRedisSerializer<Object> jsonSerializer = 
            new Jackson2JsonRedisSerializer<>(Object.class);
        ObjectMapper om = new ObjectMapper();
        om.setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.ANY);
        om.activateDefaultTyping(
            LaissezFaireSubTypeValidator.instance,
            ObjectMapper.DefaultTyping.NON_FINAL
        );
        jsonSerializer.setObjectMapper(om);
        
        // String 序列化 key
        StringRedisSerializer stringSerializer = 
            new StringRedisSerializer();
        
        // key 用 String，value 用 JSON
        template.setKeySerializer(stringSerializer);
        template.setHashKeySerializer(stringSerializer);
        template.setValueSerializer(jsonSerializer);
        template.setHashValueSerializer(jsonSerializer);
        
        template.afterPropertiesSet();
        return template;
    }
    
    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration config = RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))  // 默认 30 分钟
            .serializeKeysWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(
                    new GenericJackson2JsonRedisSerializer()));
        
        return RedisCacheManager.builder(factory)
            .cacheDefaults(config)
            .build();
    }
}
```

**序列化的坑汇总：**

1. **JdkSerializationRedisSerializer**——Redis 里存的是 `\xac\xed\x00\x05sr\x00` 这种乱码，其他语言读不了，而且序列化后的体积大
2. **对象必须实现 Serializable**——否则直接报错
3. **加了类型信息后不能用 `opsForValue().increment()`**——因为存的是 JSON 字符串，Redis 没法对它做数值操作
4. **泛型擦除问题**——`Jackson2JsonRedisSerializer<List<String>>` 如果没有泛型信息，反序列化会变成 `List<LinkedHashMap>`

**@Cacheable 注解的使用：**

```java
@Service
public class AICacheService {
    
    @Cacheable(value = "ai:summary", key = "#text.hashCode()", 
               unless = "#result == null")
    public String getAISummary(String text) {
        // 调 AI 模型的代码
        return callAIModel(text);
    }
    
    @CacheEvict(value = "ai:summary", key = "#text.hashCode()")
    public void evictSummaryCache(String text) {
        // 清除某个文本的摘要缓存
    }
}
```

**冷知识：** 用 `@Cacheable` 时如果 value 包含冒号，Redis 的 key 会变成 `ai:summary::xxx`（两个冒号），因为 Spring 自动加了一个 `::` 分隔缓存名和 key。想要优化可以自定义 `RedisCacheManager` 的 `cacheKeyPrefix`。"

> 💡 面试官追问："如果你的 value 有多个不同的类型怎么用 JSON 序列化？"——用 `GenericJackson2JsonRedisSerializer`，它会在 JSON 里加一个 `@class` 字段存储全类名。但注意：类重命名或包名变了，反序列化就炸了。

### Q5 ⭐: Redis 布隆过滤器的几种实现方式和选型建议

**高分回答：**

"布隆过滤器是一个**概率型数据结构**——它说"这个 key 可能存在"可能是假的，但说"这个 key 肯定不存在"那一定不存在。核心就是：**用少量内存判断某个元素是否不在集合中**。

**Redis 里实现布隆过滤器的三种方式：**

**方式一：Redisson 的 RBloomFilter（推荐）**

```java
RBloomFilter<String> bloomFilter = redisson.getBloomFilter("bloom:user");
// 初始化：预计插入 100 万条，误判率 1%
bloomFilter.tryInit(1000000L, 0.01);

// 添加用户
bloomFilter.add("user:10086");

// 判断是否存在
boolean exists = bloomFilter.contains("user:10086");     // true
boolean notExists = bloomFilter.contains("user:999999"); // false 大概率
```

**方式二：Redis Stack 的 BF 模块**

```bash
# Redis Stack 自带布隆过滤器模块
BF.RESERVE bloom:user 0.01 1000000
BF.ADD bloom:user user:10086
BF.EXISTS bloom:user user:10086
```

**方式三：自己用 BitMap + 多个 Hash 函数实现**

```java
public class SimpleBloomFilter {
    private static final int[] SEEDS = {7, 11, 13, 31, 37, 61};
    
    public void add(String key) {
        for (int seed : SEEDS) {
            int hash = hash(key, seed);
            redisTemplate.opsForValue()
                .setBit("bloom:bits", hash, true);
        }
    }
    
    public boolean mightContain(String key) {
        for (int seed : SEEDS) {
            int hash = hash(key, seed);
            if (!redisTemplate.opsForValue()
                .getBit("bloom:bits", hash)) {
                return false; // 一个位为 false → 肯定不存在
            }
        }
        return true; // 所有位都为 true → 可能存在
    }
}
```

**布隆过滤器在 AI 场景的经典用途：**

**防止 AI 模型的重复请求：** 用户提交了文本 A 让模型生成摘要，下次再提交同样的文本 A，布隆过滤器直接返回"已处理过"，避免重复调用消耗 AI 算力。这可是真金白银！

**爬虫的去重：** 爬取网页喂给 RAG 知识库时，用布隆过滤器去重，避免存重复内容。

**实际选型建议：** 有 Redisson 依赖就直接用 `RBloomFilter`，没条件自己用 BitMap 手写也简单。注意布隆过滤器不支持删除操作（Counter Bloom Filter 可以删除，但复杂得多）。如果业务需要删除，考虑用 **Cuckoo Filter**（Redis Stack 也支持）。"

> 💡 布隆过滤器的"误判率"公式：`p = (1 - e^(-kn/m))^k`，其中 `k` 是 Hash 函数个数，`m` 是位数组长度，`n` 是预计插入量。面试说出来就是加分项。

### Q6 ⭐⭐: Redis Cluster 扩缩容怎么操作？数据迁移时服务会断吗？

**高分回答：**

"Cluster 扩缩容的核心操作是**迁移哈希槽**——把一部分槽从一个节点挪到另一个节点。Redis 支持在线迁移，**不会中断服务**。

**扩容流程（添加新节点）：**

```bash
# 1. 启动新节点
redis-server --port 6385 --cluster-enabled yes

# 2. 加入集群
redis-cli --cluster add-node 127.0.0.1:6385 127.0.0.1:6379

# 3. 重新分配槽
redis-cli --cluster rebalance 127.0.0.1:6379

# 或者手动迁移指定数量的槽
redis-cli --cluster reshard 127.0.0.1:6379
# 然后按提示输入要迁移的槽数和目标节点 ID
```

**迁移的核心机制——两阶段迁移：**

```
阶段一：MIGRATING 状态（源节点）
  → 客户端访问源节点，key 还在源节点 → 直接返回
  → 客户端访问源节点，key 已迁移 → 返回 ASK 重定向
  
阶段二：IMPORTING 状态（目标节点）
  → 客户端访问目标节点，key 还没迁过来 → 返回 ASK 让客户端去源节点
```

**数据迁移的具体过程：**

```bash
# Redis 内部使用 MIGRATE 命令迁移 key（原子操作）
MIGRATE 127.0.0.1 6385 "" 0 5000 KEYS key1 key2 key3
```

**迁移过程对客户端的影响：**

```java
// Smart Client（如 JedisCluster）的处理逻辑
while (true) {
    try {
        jedisCluster.get("someKey");
        break;
    } catch (JedisAskDataException e) {
        // 收到 ASK 重定向 → 去目标节点直连一次
        Jedis jedis = new Jedis(e.getTargetNode().getHost(), 
                                 e.getTargetNode().getPort());
        jedis.asking();  // 发送 ASKING 命令
        jedis.get("someKey");
        break;
    } catch (JedisMovedDataException e) {
        // 收到 MOVED 重定向 → 更新本地槽位映射表
        updateSlotMapping(e.getSlot(), e.getTargetNode());
        retry();
    }
}
```

**缩容就是反向操作：** 先把要移除的节点上的槽迁移到其他节点，再 `redis-cli --cluster del-node`。

**关键注意事项：**

1. **迁移期间会有短暂的性能抖动**——MIGRATE 命令是同步的，会阻塞源节点的单线程
2. **大 key 迁移是个坑**——MIGRATE 一个大 key 会阻塞 Redis 单线程几秒甚至几十秒。建议迁移前先 `UNLINK` 大 key
3. **批量迁移优化**：`redis-cli --cluster rebalance` 支持 `--cluster-pipeline` 参数，用 Pipeline 批量迁移 key，速度提升明显
4. **迁移过程中不要做其他集群操作**——比如同时发 FAILOVER，会导致不可预期的问题

> 💡 面试官追问："迁移过程中如果一个 key 恰好被客户端请求，会怎样？"——如果 key 还在源节点，源节点正常处理。如果 key 已经被迁移，源节点返回 ASK 重定向。客户端收到 ASK 后会去目标节点带上 ASKING 命令获取数据。整个过程对用户无感，只会多一次网络往返。

### Q7 ⭐⭐: 双写一致性——先更新 DB 还是先更新缓存？Cache Aside 模式怎么落地？

**面试官想听什么：** 这道题是 Redis 面试的必考题。面试官想听的不是标准答案，是你真正踩过坑的经验。

**高分回答：**

"先说共识：**缓存和数据库永远无法做到强一致**。我们要追求的是最终一致性，同时把不一致的窗口缩到最小。

**有几个错误的方案：**

❌ **先更新缓存，再更新 DB**——缓存更新成功了 DB 失败了，数据永久不一致。

❌ **先更新 DB，再更新缓存**——并发下有问题：线程 A 更新 DB=100，线程 B 更新 DB=200，线程 A 更新缓存=100，线程 B 更新缓存=200。最终 DB=200，缓存=200（运气好一致了）；但换个顺序就变成 DB=200，缓存=100。

**推荐的方案：Cache Aside（旁路缓存）模式**

```
读请求：先读缓存 → 没命中 → 读 DB → 写缓存
写请求：更新 DB → 删除缓存
```

```java
// 写操作
public void updateUser(User user) {
    // 1. 先更新数据库
    userDao.update(user);
    // 2. 再删除缓存（不是更新缓存！）
    redisTemplate.delete("user:" + user.getId());
}

// 读操作
public User getUser(Long id) {
    // 1. 先读缓存
    User user = redisTemplate.opsForValue().get("user:" + id);
    if (user != null) return user;
    
    // 2. 缓存没命中，读 DB
    user = userDao.findById(id);
    
    // 3. 写缓存（带过期时间，作为兜底）
    if (user != null) {
        redisTemplate.opsForValue().set(
            "user:" + id, user, 30, TimeUnit.MINUTES);
    }
    return user;
}
```

**为什么是删除缓存而不是更新缓存？**

我说句实话：**删缓存比更新缓存更安全**。更新缓存涉及复杂计算（比如用户信息要拼多个表），更新一个字段就要把整个对象重新算一遍。而且更新操作比删除操作更容易被并发穿插影响。删除缓存大不了下次读请求再重建。

**这个方案有没有漏洞？**

有。经典场景：读线程缓存未命中，读到 DB 旧值，此时写线程更新 DB 并删缓存，然后读线程把旧值写回缓存——导致缓存里是旧值。

但实际概率极低，因为**写操作删除缓存后，读操作写旧值的窗口非常小**。如果在乎这种极端场景，可以加延迟双删：

```java
public void updateUserWithDelay(User user) {
    // 1. 先删缓存
    redisTemplate.delete("user:" + user.getId());
    
    // 2. 更新 DB
    userDao.update(user);
    
    // 3. 延迟再删一次（异步）
    scheduledExecutor.schedule(() -> {
        redisTemplate.delete("user:" + user.getId());
    }, 500, TimeUnit.MILLISECONDS);
}
```

**我的生产实践：** 大部分场景 Cache Aside 就够用了。如果对一致性要求更高，可以用**订阅 binlog 同步**——用 Canal 监听 MySQL binlog 变更，同步更新 Redis。这样业务代码不用双写，一致性也更高。

> 💡 面试加分点："先删缓存还是后删缓存？"——我建议"先更新 DB，后删缓存"。因为如果先删缓存，刚好 DB 还没来得及更新，另一个请求读到了旧数据写回了缓存——你删了个寂寞。

### Q8 ⭐⭐: Redis 客户端连接池怎么配？连接泄漏怎么排查？

**高分回答：**

"连接池的核心参数不是越多越好，关键在于**按业务流量调参**。

**以 JedisPool 为例的最佳实践参数：**

```java
// 客户端连接池配置
JedisPoolConfig config = new JedisPoolConfig();

// 核心参数
config.setMaxTotal(20);           // 最大连接数（默认 8）
config.setMaxIdle(10);            // 最大空闲连接数
config.setMinIdle(5);             // 最小空闲连接数（预热用）

// 连接获取超时
config.setMaxWait(Duration.ofSeconds(2));  // 借不到连接的超时时间

// 连接检测
config.setTestOnBorrow(true);     // 借连接时检测（会多一次 PING）
config.setTestOnReturn(false);    // 还连接时不检测（减少开销）
config.setTestWhileIdle(true);    // 后台线程检测空闲连接（默认 30 秒一次）

// 连接泄漏兜底
config.setBlockWhenExhausted(true);  // 连接不够时阻塞等待
config.setJmxEnabled(true);         // 开启 JMX 监控
```

**几个关键参数的设定原则：**

**`maxTotal` 怎么算？**
```
maxTotal = 业务 QPS × 单次操作耗时(ms) / 1000
比如：QPS=5000，每次操作 2ms → maxTotal = 5000 × 2 / 1000 = 10
```
这只是理论值。线上建议 maxTotal 设为理论值的 2~3 倍作为 buffer。

**连接池和 Redis Cluster 的关系：**
Cluster 模式下，JedisCluster 内部为每个节点维护一个连接池。所以如果有 6 个节点，每个节点 maxTotal=10，总连接数最多 60。

**连接泄漏怎么排查？**

```bash
# 1. 看 Redis 层
redis-cli INFO clients
# connected_clients: 120    ← 如果这个值异常增大，说明连接泄漏了

# 2. 看连接来源（Redis 6.0+）
redis-cli CLIENT LIST
# 可以看到每个连接的 IP 和 idle 时间

# 3. 看应用层（Java）
jstack <pid> | grep "pool"  # 看连接池线程状态
# 或者用 JMX 看连接池指标
```

**常见连接泄漏原因：**
1. **用 Jedis 忘了 `close()`**——Jedis 实现了 Closeable，用完关闭会归还到连接池。最常用 try-with-resource
2. **异常路径没有释放**——try-catch 里的 finally 没写 close
3. **Response 对象没消费完**——如果用了 Pipeline，忘记 `sync()`，连接会卡住

```java
// 错误的写法
public void bad() {
    Jedis jedis = pool.getResource();
    jedis.get("mykey");
    // 忘！了！关！闭！
}

// 正确的写法
public void good() {
    try (Jedis jedis = pool.getResource()) {
        jedis.get("mykey");
    } // 自动 close，归还到连接池
}
```

> 💡 补充：Lettuce 相比 Jedis 的一个优势是连接复用——Lettuce 基于 Netty 的异步模型，一个连接可以并发处理多个请求，不像 Jedis 需要多个连接。高并发场景 Lettuce 连接数更少，资源开销更低。

### Q9 ⭐⭐: 用 Redis 实现分布式限流——滑动窗口和令牌桶的实现方案

**高分回答：**

"用 Redis 做分布式限流是常见方案，因为它是"共享状态"——不像本地限流只有单机有效。常见算法有**滑动窗口**和**令牌桶**两种。

**方案一：滑动窗口算法（ZSet 实现）**

```lua
-- 滑动窗口限流 Lua 脚本
-- KEYS[1]: 限流 key（比如 user:10086:api）
-- ARGV[1]: 窗口大小（秒）
-- ARGV[2]: 阈值
-- 返回: 0=限流 1=放行
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = redis.call('TIME')[1]  -- 获取 Redis 服务器时间

-- 清除窗口外的时间戳
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 当前窗口内的请求数
local count = redis.call('ZCARD', key)

if count >= limit then
    return 0  -- 限流
end

-- 记录本次请求
redis.call('ZADD', key, now, now .. ':' .. math.random())
redis.call('EXPIRE', key, window)
return 1  -- 放行
```

**方案二：令牌桶算法（更灵活的限流）**

```lua
-- 令牌桶限流 Lua 脚本
-- KEYS[1]: 令牌桶 key
-- ARGV[1]: 桶容量
-- ARGV[2]: 每秒生成令牌数
-- ARGV[3]: 当前时间戳（秒）
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 获取桶的当前状态
local bucket = redis.call('HGETALL', key)
local lastTime = 0
local tokens = capacity

if #bucket > 0 then
    lastTime = tonumber(bucket[2])
    tokens = tonumber(bucket[4])
end

-- 计算新生成的令牌
local elapsed = now - lastTime
local newTokens = elapsed * rate
tokens = math.min(capacity, tokens + newTokens)

-- 判断是否允许请求
if tokens < 1 then
    return 0  -- 限流
end

-- 消耗一个令牌
tokens = tokens - 1

-- 更新桶状态
redis.call('HMSET', key, 'lastTime', now, 'tokens', tokens)
redis.call('EXPIRE', key, 3600)
return 1  -- 放行
```

**滑动窗口 vs 令牌桶算法对比：**

| 特性 | 滑动窗口 | 令牌桶 |
|------|---------|--------|
| 突发流量 | ❌ 不允许突发 | ✅ 允许短时突发（桶里的积累） |
| 平滑度 | 窗口边界可能产生锯齿 | ✅ 平滑 |
| 内存占用 | 高（要存所有时间戳） | ✅ 低（只存两个变量） |
| 实现复杂度 | 低 | 中 |
| 适用场景 | 严格 QPS 控制 | 有突发流量的 API 限流 |

**我的建议：** AI 模型 API 限流用**令牌桶**——因为 AI 模型调用有时间波动性，令牌桶允许业务在低峰期"攒"一些预算，高峰期多调几次。网关层用滑动窗口——更均匀地控制入口流量。"

> 💡 面试加分：提到**漏桶算法**——"漏桶不管流量多凶猛，输出速率固定，适合保护下游系统。但缺点是即使系统空闲也无法加速处理。我一般优先用令牌桶，因为更灵活。"

### Q10 ⭐⭐: Redis 的 Java 客户端选型——Jedis vs Lettuce vs Redisson，怎么选？

**高分回答：**

"这是每个用 Redis 的 Java 项目都要做的选择。说句实话：**没有哪个最好，只有哪个最适合**。

**三者的定位完全不同：**

| 特性 | Jedis | Lettuce | Redisson |
|------|-------|---------|----------|
| **模型** | BIO 同步阻塞 | Netty NIO 异步 | Netty + 高级封装 |
| **连接复用** | 一个连接一个线程 | ✅ 一个连接多请求 | ✅ 同左 |
| **线程安全** | ❌ 不安全 | ✅ 安全 | ✅ 安全 |
| **性能** | 中（连接数多时好） | ✅ 高（连接复用） | 中（有抽象开销） |
| **Spring Boot 默认** | ❌ | ✅（2.0 之后） | ❌ |
| **高级功能** | 基础 CRUD | 响应式 + 异步 | ✅ 分布式锁、限流、布隆过滤器 |
| **API 复杂度** | 最简 | 中等 | 最高 |

**选型建议：**

**选 Jedis 的场景：**
- 项目简单，只需要基本的 get/set
- 连接数可控（几十个够用）
- 团队习惯同步编程

**选 Lettuce 的场景：**
- 高并发、需要连接复用（一个连接处理上千请求）
- 响应式编程（WebFlux）
- Spring Boot 2.x+ 默认就是 Lettuce，不用白不用

**选 Redisson 的场景：**
- 需要分布式锁、限流器、布隆过滤器、计数器等高级功能
- 不想自己手写 Lua 脚本
- 需要各种分布式数据结构（RMap、RSet、RQueue）

**我的实践经验：**
一般项目我用 **Lettuce + Redisson** 组合——Lettuce 做基础数据操作，Redisson 做分布式锁和限流。Lettuce 的异步能力在高并发场景下优势明显。

**Jedis 有个大坑：** 它不是线程安全的，每个线程需要从连接池借一个独立的连接。如果并发大，连接池打满就直接把线程堵住了。Lettuce 就没有这个问题——因为它基于 Netty，单连接是线程安全的。

**Redisson 的坑：** 封装太深了，出了问题不好排查。比如分布式锁的 watch dog 机制自动续期，如果你没理解它的设计，可能遇到意想不到的锁超时。"

> 💡 面试官追问："Spring Boot 2.0 后默认用 Lettuce 替换了 Jedis，为什么？"——因为 Lettuce 基于 Netty 的异步非阻塞架构，连接复用能力强，更适合 Spring 的响应式编程模型。而且 Lettuce 在连接池满的时候不会阻塞，而是返回失败或等待，对系统更友好。

### Q11 ⭐⭐⭐: Redis dict 源码分析——渐进式 rehash 到底是怎么实现的？

**高分回答：**

"Redis 的 dict（哈希表）是 Hash 和 Set 数据类型的底层实现。它的核心设计就是**渐进式 rehash**——rehash 不是一次性完成的，而是分摊到每次操作中。

**源码关键数据结构：**

```c
// dict.h
typedef struct dict {
    dictType *type;          // 类型特定函数
    void *privdata;          // 私有数据
    dictht ht[2];            // 两个哈希表：ht[0] 和 ht[1]
    long rehashidx;          // rehash 进度，-1 表示没在 rehash
    int16_t pauserehash;     // 暂停 rehash 计数
} dict;

typedef struct dictht {
    dictEntry **table;       // 哈希表数组
    unsigned long size;      // 哈希表大小
    unsigned long sizemask;  // 大小掩码，等于 size - 1
    unsigned long used;      // 已用节点数
} dictht;
```

**渐进式 rehash 的完整流程：**

```
阶段一：触发 rehash
  ht[0].used / ht[0].size >= 1（触发扩容）或 <= 0.1（触发缩容）
  → 为 ht[1] 分配空间：扩容为 2^n 倍，缩容为原来的 1/2
  
阶段二：设置进度标志
  → rehashidx = 0，表示从第 0 个 bucket 开始

阶段三：逐步迁移（每次操作搬一部分）
  → 每次执行增删改查操作时，触发 _dictRehashStep：
    - 从 ht[0][rehashidx] 开始，把非空的 bucket 迁移到 ht[1]
    - rehashidx++，跳过空 bucket（最多空 10 个）
    - 每次迁移 1 个 bucket（或按定时任务批量迁）
  
阶段四：空闲时批量处理
  → serverCron 定时任务里：
    - 每次执行 1ms 的 rehash
    - 如果 ht[0].used > 100，每次迁移 100 个 bucket
    - 保证不阻塞主线程

阶段五：完成
  → ht[0] 的所有 bucket 迁移完毕
  → 释放 ht[0]，ht[1] 变成新的 ht[0]
  → rehashidx = -1
```

**关键细节：**

```c
// dict.c - 每次增删改查通过 _dictRehashStep 触发
// dictAdd, dictDelete, dictFind... 等操作都会触发
int dictAdd(dict *d, void *key, void *val) {
    // 渐进式 rehash：每次新增操作迁移一个 bucket
    if (dictIsRehashing(d)) _dictRehashStep(d);
    
    // ... 正常添加逻辑
}

// _dictRehashStep 调用 dictRehash
int dictRehash(dict *d, int n) {
    int empty_visits = n * 10;  // 最多跳过 n*10 个空 bucket
    while (n-- && d->ht[0].used != 0) {
        while (d->ht[0].table[d->rehashidx] == NULL) {
            d->rehashidx++;
            if (--empty_visits == 0) return 1;  // 空 bucket 太多就不继续了
        }
        // 把 ht[0] 上的这个 bucket 全部移到 ht[1]
        dictEntry *de = d->ht[0].table[d->rehashidx];
        while (de) {
            uint64_t h = dictHashKey(d, de->key) & d->ht[1].sizemask;
            // 头插法插入到 ht[1]
            dictEntry *next = de->next;
            de->next = d->ht[1].table[h];
            d->ht[1].table[h] = de;
            d->ht[0].used--;
            d->ht[1].used++;
            de = next;
        }
        d->ht[0].table[d->rehashidx] = NULL;
        d->rehashidx++;
    }
    return d->ht[0].used == 0;  // 返回 1 表示迁移完成
}
```

**渐进式 rehash 的优点（面试时说出来加分）：**
1. **不阻塞主线程**——10GB 的 dict 如果一次性 rehash，Redis 要卡几十秒
2. **读操作如何处理？**——rehash 期间读 ht[0] 和 ht[1] 都要查，找不到才返回空
3. **写操作如何处理？**——新增永远写到 ht[1]，让 ht[0] 只减不增，最终变为空
4. **扩容阈值是 1（used/size = 1），缩容阈值是 0.1**——但这是数据库模式的阈值。Redis 做缓存时可以用 `activedefrag` 参数调节

> 💡 说到这，面试官如果感兴趣可以深挖一句："Redis 的 dict 为什么采用链地址法而不采用开放寻址法？"——因为链地址法在大量 key 被删除时只需要释放链表节点，而开放寻址法删除麻烦（需要标记删除或移动后续元素）。Redis 经常有大量 key 过期删除，链地址法更适合。

### Q12 ⭐⭐⭐: Redis 6.0 的多线程 IO 模型——为什么命令执行还是单线程？

**高分回答：**

"这是个特别容易答混的问题。很多人听说 Redis 6.0 引入了多线程，就以为"Redis 变成多线程了"——其实不是。

**先说清楚：Redis 6.0 之前的单线程模型瓶颈在哪？**

```
单线程模型：
  读取请求 → 解析命令 → 执行命令 → 写回响应
  ↑________________________________________| 循环
  
瓶颈在哪？**在『读取请求』和『写回响应』这两个 IO 阶段**。
```

Redis 执行命令很快（纯内存操作，微秒级），但**网络 IO 是阻塞的**——从 socket 读数据、往 socket 写数据都需要时间。当并发连接数上万时，单线程在 IO 上花的比例越来越高。

**Redis 6.0 引入的多线程 IO：**

```
多线程 IO 模型：

  主线程（命令执行）：
    ↓
  IO 线程池（N 个线程，默认 3 个）：
    线程1: 负责从一批 socket 中读取请求 → 放队列
    线程2: 负责从下一批 socket 中读取请求 → 放队列  
    线程3: 负责把响应写回 socket
```

```c
// networking.c - 多线程 IO 的核心配置
#define IO_THREADS_MAX_NUM 128       // 最大 IO 线程数
server.io_threads_num = 4;          // 实际使用配置（建议 4，Redis 作者说的）
server.io_threads_active = 1;       // 是否启用多线程 IO

// io-threads-do-reads yes  ← 配置文件中启用读线程
```

**流程拆解：**

```
读阶段（多线程）：
  1. 主线程调用 aePoll，等待 epoll 事件
  2. 有事件后，主线程把可读的 fd 分配给 IO 线程
  3. IO 线程并行读取数据到缓冲区
  4. 主线程等待所有 IO 线程完成
  5. 主线程解析命令、执行命令（还是单线程！）

写阶段（多线程）：
  6. 主线程把计算结果写入缓冲区
  7. 主线程分配可写的 fd 给 IO 线程
  8. IO 线程并行写回客户端
```

**关键点：真正的瓶颈在哪？**

我测过一些数据：Redis 6.0 多线程 IO 在**纯 PING 测试**下 QPS 从单线程的 8 万涨到了 20 万 +。但在实际业务中（10KB 以上的 value），命令执行本身占的时间变多了，IO 线程的收益就没那么明显。

**还有几个容易被忽略的点：**

1. **IO 线程数不是越多越好。** 官方建议 4 就够了。超过 8 反而因为线程上下文切换导致性能下降
2. **IO 线程只处理网络读写。** 命令的解析和执行依然是单线程——这是为了保持业务的"原子性"和简单性
3. **多线程 IO 默认是关闭的。** 需要在 `redis.conf` 里手动开启：`io-threads 4` 和 `io-threads-do-reads yes`
4. **IO 线程不会处理多 key 命令。** 比如 MSET、MGET 这种多条命令批量操作，仍然由主线程串行处理

**总结一句就够：** Redis 6.0 不是把 Redis 变成多线程了，而是**给单线程的执行器配了几个专门做 IO 的帮手**。"

> 💡 面试加分：能说出"Redis 7.0 之后进一步优化了多线程 IO，在 CPU 密集型工作负载下性能提升更明显。但核心原则没变——命令执行永远是单线程的。"

### Q13 ⭐⭐⭐（AI 融合）: 设计一个基于 Redis + AI 的语义缓存系统（Semantic Cache）

**面试官想听什么：** 这道题考察的是你能否把"传统缓存"和"AI 场景"结合起来。传统缓存基于 key 完全匹配，但 AI 场景里用户的输入可能语义相似，缓存可以复用。

**高分回答：**

"**语义缓存**的意思是：用户 A 问'Redis 单线程为什么快'，用户 B 问'Redis 为什么性能这么好'——语义相似，可以返回同一个 AI 回答，省一次模型调用。**这不是精确 key 匹配，而是语义相似度匹配**。

**架构设计：**

```
                    ┌─────────────────────┐
                    │    Embedding 模型    │
                    │  （text-embedding）  │
                    └────────┬────────────┘
                             │ 生成向量
                             ▼
用户提问 ──→ 语义检索 ──→ ┌─────────────────────┐
                         │   Redis Stack       │
                         │   Vector Search     │
                         │   (余弦相似度 >0.9) │
                         └────────┬────────────┘
                                  │
                     ┌────────────┴────────────┐
                     │ 命中          未命中     │
                     ▼                         ▼
               返回缓存结果               调用 AI 模型
                                          ↓
                                     结果写入 Redis
```

**核心实现：**

```python
import redis
import numpy as np
from sentence_transformers import SentenceTransformer

class SemanticCache:
    def __init__(self, redis_url="redis://localhost:6379"):
        self.r = redis.from_url(redis_url)
        self.model = SentenceTransformer("all-MiniLM-L6-v2")  # 轻量 embedding 模型
        
    def _get_embedding(self, text: str) -> np.ndarray:
        """生成文本的向量表示"""
        return self.model.encode(text, normalize_embeddings=True)
    
    def get(self, query: str, threshold: float = 0.92) -> str | None:
        """
        语义缓存查询
        - 把用户 query 转成向量
        - 在 Redis 里做向量搜索（余弦相似度）
        - 找到相似度超过 threshold 的结果直接返回
        """
        query_vec = self._get_embedding(query)
        
        # Redis Stack 的向量搜索（Redis 7.4+ / Redis Stack）
        result = self.r.ft("idx:semantic_cache").search(
            f"*=>[KNN 1 @embedding $vec AS score]",
            query_params={"vec": query_vec.tobytes()},
            return_fields=["response", "score"],
            dialect=2
        )
        
        if result.docs:
            score = float(result.docs[0].score)
            if score >= threshold:
                print(f"[语义缓存命中] 相似度: {score:.3f}")
                return result.docs[0].response
        
        return None
    
    def set(self, query: str, response: str, ttl: int = 3600):
        """
        写入语义缓存
        - 生成 query 的 embedding
        - 存到 Redis，同时建立向量索引
        """
        query_vec = self._get_embedding(query)
        cache_key = f"semantic:{hash(query)}"
        
        # 建立向量索引（第一次运行，后续省略）
        try:
            self.r.ft("idx:semantic_cache").create(
                [TextField("query"), TextField("response"),
                 VectorField("embedding", "FLAT", {
                     "TYPE": "FLOAT32",
                     "DIM": 384,
                     "DISTANCE_METRIC": "COSINE"
                 })]
            )
        except:
            pass  # 索引已存在
        
        self.r.hset(cache_key, mapping={
            "query": query,
            "response": response,
            "embedding": query_vec.tobytes()
        })
        self.r.expire(cache_key, ttl)


# 使用示例
cache = SemanticCache()

# 用户提问
query = "Redis 单线程为什么这么快"

# 先查语义缓存（相似度 > 0.92 算命中）
cached = cache.get(query)
if cached:
    print(f"返回缓存: {cached}")
else:
    # 调 AI 模型
    response = call_llm(query)
    # 写缓存
    cache.set(query, response)
    print(f"AI 回答: {response}")
```

**语义缓存的面试核心考点：**

1. **阈值怎么定？** 太高（0.98）命中率低，太低（0.8）容易返回答非所问。建议 0.92~0.95 起步，根据业务调优
2. **TTL 的策略？** AI 回答不像数据缓存——知识问题可以存久一点（几小时到一天），但时效性问题的缓存要短（几分钟）
3. **淘汰策略？** 语义缓存的 key 比较大（含向量 + 回答），内存消耗快。建议加上 LRU 淘汰 + 预热常用问题
4. **缓存雪崩？** 所有相似问题命中了同一个缓存 key——这是好事，不浪费。但如果是"热点问题"的缓存失效，所有人都要重新调 AI，最好加上互斥锁

> 💡 说的再多一点：如果用的是 Redis 7.4+，原生支持向量搜索，不需要额外装 Redis Stack。如果用老版本，可以用 Redis 的 ZSet 自己实现近似向量搜索——但说句实话，精度和性能差距很大，有条件的直接上 Redis Stack。

### Q14 ⭐⭐⭐（AI 融合）: 用 Redis 做 AI 应用的 Session 管理——如何支撑百万级在线用户？

**高分回答：**

"AI 应用（如大模型对话、Agent 应用）的 Session 管理跟传统 Web 应用完全不同——**每个 session 可能携带几十到几百 KB 的上下文**（历史对话、Agent 状态、工具调用结果）。

**不能单纯像传统 Web session 那样存：**

1. 传统 Session 存个 userId + 登录状态（~100 bytes）
2. AI Session 要存 10 轮以上的对话历史（~10KB ~ 100KB）
3. 如果用户多、对话长——内存撑不住

**我的设计：分层 Session 存储**

```
Session 结构拆解:
┌─────────────────────────────────────────┐
│  元信息（Redis String / Hash）            │
│  - userId, model, createdAt, ttl         │   (< 1KB)
├─────────────────────────────────────────┤
│  上下文快照（Redis String / HASH）        │
│  - systemPrompt, tools manifest          │   (< 5KB; 更新少)
├─────────────────────────────────────────┤
│  对话历史（Redis List 或 Stream）        │
│  - 用户消息 turn1 ~ turnN                │   (可变大小)
├─────────────────────────────────────────┤
│  Agent 中间状态（Redis Hash / JSON）     │
│  - 工具调用结果、状态机当前节点等         │   (更新频繁)
└─────────────────────────────────────────┘
```

**具体代码实现：**

```java
@Service
public class AISessionManager {
    
    private final StringRedisTemplate redis;
    
    // 会话元信息
    public void createSession(String sessionId, AISession session) {
        redis.opsForHash().putAll(
            "session:meta:" + sessionId,
            Map.of(
                "userId", session.getUserId(),
                "model", session.getModel(),
                "createdAt", String.valueOf(System.currentTimeMillis()),
                "contextLength", "0"
            )
        );
        redis.expire("session:meta:" + sessionId, 24, TimeUnit.HOURS);
    }
    
    // 追加对话轮次（List 存储，每个元素是一轮对话）
    public void appendTurn(String sessionId, ChatTurn turn) {
        String turnJson = JSON.toJSONString(turn);
        redis.opsForList().rightPush(
            "session:history:" + sessionId, turnJson);
        
        // 控制对话轮次上限（防无限膨胀）
        long size = redis.opsForList().size(
            "session:history:" + sessionId);
        if (size > 50) {
            // 把最老的对话压缩成摘要
            String oldestContext = compressToSummary(
                redis.opsForList().leftPop(
                    "session:history:" + sessionId));
            redis.opsForValue().append(
                "session:compact:" + sessionId, oldestContext);
        }
        
        // 更新 TTL（每次活跃都续期）
        redis.expire("session:history:" + sessionId, 
            24, TimeUnit.HOURS);
    }
    
    // Agent 工具调用栈（Hash 存储，更新频繁）
    public void updateToolState(String sessionId, 
                                String toolName, String result) {
        redis.opsForHash().put(
            "session:tools:" + sessionId, toolName, result);
    }
    
    // 重建完整上下文（推理前调用）
    public String buildFullContext(String sessionId) {
        // 1. 元信息
        Map<Object, Object> meta = redis.opsForHash()
            .entries("session:meta:" + sessionId);
        
        // 2. 对话历史（最近 10 轮）
        List<String> history = redis.opsForList()
            .range("session:history:" + sessionId, -10, -1);
        
        // 3. 压缩的摘要（如果打开了历史压缩）
        String compressed = redis.opsForValue()
            .get("session:compact:" + sessionId);
        
        // 4. 当前工具状态
        Map<Object, Object> toolStates = redis.opsForHash()
            .entries("session:tools:" + sessionId);
        
        // 拼成 prompt 给 LLM
        return buildPrompt(meta, history, compressed, toolStates);
    }
}
```

**百万级用户的实践要点：**

1. **分片策略**：按 sessionId 哈希分片到不同的 Redis 节点。别把所有 session 塞到一个大实例里
2. **淘汰策略**：给所有 session key 设置合理的 TTL（比如 1 小时不活跃自动清理）
3. **历史压缩**：对话超过 20 轮，就把最早的若干轮用 LLM 压缩成摘要。这叫"滑动窗口 + 摘要压缩"
4. **读写分离**：读取 session 走从节点，写入走主节点
5. **冷热分离**：最近 2 小时内活跃的 session 在 Redis 里热存，超过 24 小时不活跃的 session 序列化到磁盘/对象存储

> 💡 面试加分：在 AI 场景下，Session 不仅仅是存储，还涉及"上下文窗口管理"——LLM 的 context window 是有限的（比如 128K tokens）。超越窗口长度的会话应该做摘要总结然后截断旧数据。这个过程如果用 Redis 的 Lua 脚本实现上下文压缩，就是架构亮点。"

### Q15 ⭐⭐⭐（综合设计）: 用 Redis 设计一个高频实时 Feed 流系统

**面试官想听什么：** Feed 流是一个经典的高并发设计题，需要综合运用 Redis 的各种数据结构。面试官想看你能不能打通全链路。

**高分回答：**

"Feed 流常见的两种模式——**推模式**和**拉模式**。我结合 Redis 说一个**推拉结合**的方案。

**先说需求：** 一个内容平台，用户可以关注其他创作者，关注后能在首页看到他们的最新内容。要求高并发、低延迟、能支撑千万级用户。

**推模式（Fanout on Write）：**

用户 A 发了一条内容，Redis 直接推送给所有粉丝的 Feed 列表里。

```bash
# 用户 A 发了一条动态 ID=10086
# 先拿到 A 的所有粉丝
粉丝集合: {"user:B", "user:C", "user:D"}

# 往每个粉丝的 Feed list 里 push
LPUSH feed:user:B 10086
LPUSH feed:user:C 10086  # 如果 A 有 100 万粉丝，这里要 push 100 万次
LPUSH feed:user:D 10086
```

优点：读快（用户看 Feed 直接 LPOP 就行）。缺点：大 V 发内容时，写扩散太恐怖了。

**拉模式（Fanout on Read）：**

用户打开 Feed 时，从用户关注的每个创作者的列表中拉取最新内容，在内存中合并排序。

```bash
# 用户 B 打开 Feed
# B 关注了 {A, C, D}
# 从这三个人的时间线里取最新 10 条
LRANGE user:A:timeline 0 9
LRANGE user:C:timeline 0 9
LRANGE user:D:timeline 0 9
# 在应用内存里 merge 排序，取 Top 10
```

优点：写入快，大 V 发内容无压力。缺点：读的时候可能要从几十上百个关注列表里拉取，延迟高。

**我的方案——推拉结合：**

```

创作者发内容
    │
    ├── 粉丝 < 10万 → 推模式（写入粉丝 Feed）
    │
    └── 粉丝 ≥ 10万（大 V）→ 拉模式（粉丝自己拉）
    
普通用户读 Feed:  
    1. 拿关注的"推模式创作者"的最新内容（直接读自己的 Feed list）
    2. 拿关注的"拉模式创作者"的最新内容（逐个人拉 list）
    3. 在内存中按时间合并，取 Top 20
```

**核心的 Redis 数据设计：**

```bash
# 1. 用户发的内容按时间线存储（ZSet）
ZADD timeline:user:10086 1716048000 "post:10086"

# 2. 粉丝关系（Set）
SADD follower:user:10086 user:B user:C user:D

# 3. 普通用户的 Feed 列表（List，最多存 500 条）
LPUSH feed:user:B post:10086
LTRIM feed:user:B 0 499  # 只保留最近 500 条
EXPIRE feed:user:B 86400  # 一天后自动清理

# 4. 大 V 标记
SET isBigV:user:10086 1  # 粉丝超过阈值的大 V

# 5. 用户在 feed 中已读的最大 id（去重用）
# 用 Hash 存用户对某个关注者的已读时间戳
HSET read:offset:user:B user:10086 1716048000
```

**完整流程代码：**

```java
// 发布内容（推拉结合）
public void publishPost(String userId, String postId, long timestamp) {
    // 如果用户发的是"普通"内容，直接推到所有粉丝
    boolean isBigV = redisTemplate.opsForValue()
        .get("isBigV:" + userId) != null;
    
    if (!isBigV) {
        // 推模式：往所有粉丝的 feed 列表里塞
        Set<String> followers = redisTemplate.opsForSet()
            .members("follower:" + userId);
        for (String follower : followers) {
            redisTemplate.opsForList()
                .leftPush("feed:" + follower, postId);
            redisTemplate.opsForList()
                .trim("feed:" + follower, 0, 499);
        }
    }
    
    // 无论如何，内容都要写入创作者的时间线
    redisTemplate.opsForZSet()
        .add("timeline:" + userId, postId, timestamp);
}

// 读取 Feed（合并排序）
public List<String> getFeed(String userId, int page, int size) {
    // 1. 获取用户关注的创作者
    Set<String> followings = redisTemplate.opsForSet()
        .members("following:" + userId);
    
    List<Post> allPosts = new ArrayList<>();
    int offset = page * size;
    
    for (String author : followings) {
        // 2. 判断是大 V 还是普通作者
        boolean isBigV = redisTemplate.opsForValue()
            .get("isBigV:" + author) != null;
        
        if (!isBigV) {
            // 推模式的粉丝：直接读自己 feed list
            List<String> posts = redisTemplate.opsForList()
                .range("feed:" + userId, offset, offset + size - 1);
            // 解析 posts 得到时间
        } else {
            // 拉模式大 V：读 author 的时间线
            long lastRead = getLastReadOffset(userId, author);
            Set<String> posts = redisTemplate.opsForZSet()
                .rangeByScore("timeline:" + author, 
                    lastRead + 1, Double.MAX_VALUE, 0, size);
        }
        
        // 3. 收集到有序列表
        allPosts.addAll(posts);
    }
    
    // 4. 按时间排序取 Top N
    allPosts.sort((a, b) -> Long.compare(b.getTimestamp(), a.getTimestamp()));
    return allPosts.subList(0, Math.min(size, allPosts.size()));
}
```

**为什么这么做能抗住千万级用户？**

- **普通用户（占 99%）**：他们的粉丝少，用推模式，写扩散成本低
- **大 V（占 1%）**：粉丝多，用拉模式，避免写风暴
- **缓存时间线**：每个人的时间线只存 500 条最近的，超过的从 DB 里回溯
- **冷热分离**：活跃用户的 Feed 热存在 Redis，不活跃用户 1 天后自动过期
- **异步写扩散**：推模式不要求实时，可以异步通过 MQ 批次推送，进一步削峰

> 💡 补充一句：这个方案是 Twitter 早期就用的方案（叫 Fanout-on-write with pull for celebrities）。你能说出这个名字，面试官就知道你研究过真实业界方案。"
