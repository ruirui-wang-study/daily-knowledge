## 1. Redis Stream 是什么？和 List 做消息队列比有什么优势？

**回答：**

Stream 是 Redis 5.0 引入的消息队列数据类型，说直白点——它就是弥补 List 做 MQ 的所有缺点的。

List 做消息队列用 `LPUSH + BRPOP`，最核心的问题有几个：

1. **消息不支持多消费**——一个消息被一个消费者取走就没了
2. **没有 ACK 机制**——消费者取了消息挂了，消息就丢了
3. **没法回溯历史消息**——消费过就没了
4. **没有消费者组的概念**——不能做到一条消息只被组内一个消费者消费

Stream 从根本上解决了这些问题。核心概念就三个：**消息**、**消费者组**、**消费者**。

```bash
# 生产者：往 stream 里加消息
XADD mystream * sensor-id 1234 temperature 19.8
# 返回："1716150000000-0"  — 自动生成的毫秒级时间戳ID

# 消费者组
XGROUP CREATE mystream mygroup $
# $ 表示从最新消息开始消费

# 消费者从组里读消息
XREADGROUP GROUP mygroup consumer-1 COUNT 1 BLOCK 5000 STREAMS mystream >
# > 表示只读没分配给其他消费者的消息

# 确认消费成功
XACK mystream mygroup 1716150000000-0
```

**关键区别一张表说清楚：**

| 能力 | List + BRPOP | Stream |
|------|-------------|--------|
| 消息不丢 | ❌ 取了就删 | ✅ Pending List，可重试 |
| 消费者组 | ❌ | ✅ |
| 回溯历史 | ❌ | ✅ XRANGE |
| 消息 ID | 无 | ✅ 自动生成时间戳ID |
| ACK 确认 | ❌ | ✅ |

> 💡 小贴士：面试官问你"Redis 能做消息队列吗"，你千万别只说"用 List"，说"5.0 之后用 Stream，支持消费者组和 ACK 机制，可以替代部分 MQ 场景"，这才是专业回答。当然，Stream 毕竟是内存里的，持久化比不上 Kafka/RocketMQ，量级上 10 万/秒以内可以，再大请上专业 MQ。

## 2. Redis Pipeline 批量操作，到底能提升多少性能？和 mget 有什么区别？

**回答：**

先说结论：Pipeline 提升的不是 Redis 执行速度，而是**网络往返时间（RTT，Round-Trip Time）**。

假设一次网络往返是 1ms（同机房差不多这个量级），执行 get 操作本身只要 10μs。如果一个个发 1000 个 get：

- 不用 Pipeline：1000 × (1ms + 10μs) ≈ 1 秒
- 用 Pipeline：1ms + 1000 × 10μs ≈ 11ms

**性能提升接近 100 倍**，是不是很夸张？

```java
// 不用 Pipeline
for (String key : keys) {
    redisTemplate.opsForValue().get(key); // 每次都要网络往返
}

// 用 Pipeline
List<Object> results = redisTemplate.executePipelined(
    (RedisCallback<String>) connection -> {
        for (String key : keys) {
            connection.get(key.getBytes());
        }
        return null;
    }
);
```

**Pipeline vs mget：**
- `mget` 是单条命令批量获取，**原子执行**，返回结果顺序对应 key 顺序
- Pipeline 是客户端批量发送命令，**非原子的**，可以批量执行不同类型命令（get/set/exists 混着来）
- 场景不同：取多个 key 用 mget，做复杂批处理用 Pipeline

这里有个坑：Pipeline 批量太大时，客户端会积压大量未响应，可能导致 OOM 或连接超时。生产上建议**控制批量大小**（比如 500~1000 条一批）。

> 💡 小贴士：Redis Cluster 模式下用 Pipeline，如果 key 在不同节点，Pipeline 会拆分成到不同节点的请求。`mget` 也一样——Cluster 下 `mget` 命令是兼容的，Redis 会自动路由到不同节点拉取，但跨 slot 操作不支持原子性。

## 3. Redis 的 SCAN 命令和 KEYS 命令有什么区别？生产环境怎么用？

**回答：**

直接先说结论：**生产环境永远别用 `KEYS` 命令**。

`KEYS *` 会阻塞 Redis 单线程，如果 key 有几百万，直接卡死几秒甚至几十秒。线上出过太多事故了——有人半夜跑了个 `KEYS *`，Redis 阻塞了几秒，所有请求超时，服务雪崩。

`SCAN` 是替代方案，游标式遍历，每次返回少量数据（默认 10 条），**不阻塞**：

```bash
SCAN 0 MATCH user:* COUNT 100
# 返回：游标 + 一批 key
# 1) "123"  ← 下次用的游标，0 表示遍历结束
# 2) 1) "user:1001"
#    2) "user:2003"
#    ...
```

有几种变体：
- `SSCAN` → Set
- `HSCAN` → Hash
- `ZSCAN` → ZSet

```java
// 生产环境安全遍历的写法
String cursor = "0";
do {
    ScanOptions options = ScanOptions.scanOptions()
        .match("user:*")
        .count(100)
        .build();
    Cursor<String> scan = redisTemplate.scan(options);
    while (scan.hasNext()) {
        String key = scan.next();
        // 处理 key...
    }
    cursor = scan.getCursor();
    scan.close();
} while (!cursor.equals("0"));
```

有个容易被忽略的点：`SCAN` 返回的 key **可能重复**，因为游标遍历过程中可能有 key 新增/删除。所以消费端要做好**去重**。

> 💡 小贴士：面试可以提一下 `SCAN` 的 COUNT 参数——它不是精确返回多少条，是"尽力返回 N 条"。底层是按哈希槽遍历的，每个槽位可能返回多条也可能 0 条。想遍历全部 key 直接用 `SCAN 0` 分页就行。

## 4. Redis 的键空间通知（Keyspace Notification）是什么？能用来做什么？

**回答：**

键空间通知是 Redis 提供的一种**事件订阅**机制——当某个 key 发生变化（过期、删除、修改等），Redis 会自动向指定频道发一条消息。

```bash
# 1. 先开启功能（默认是关闭的）
CONFIG SET notify-keyspace-events Ex
# E = 键事件, x = 过期事件

# 2. 订阅过期通知（客户端代码）
```

开启方式是在 redis.conf 或运行时设置 `notify-keyspace-events`，参数组合：

| 字符 | 含义 |
|------|------|
| K | 键空间通知（key 维度） |
| E | 键事件通知（event 维度） |
| g | 通用命令（DEL/EXPIRE/RENAME） |
| $ | 字符串命令 |
| x | 过期事件 |
| e | 驱逐事件（内存淘汰） |

实战场景：**延迟任务**、**订单超时取消**、**缓存预热**。

```java
// 监听 key 过期事件，实现订单自动取消
@Configuration
public class RedisKeyExpiredListener extends KeyExpirationEventMessageListener {
    
    public RedisKeyExpiredListener(RedisMessageListenerContainer listenerContainer) {
        super(listenerContainer);
    }
    
    @Override
    public void onMessage(Message message, byte[] pattern) {
        String expiredKey = message.toString();  // 过期的 key
        if (expiredKey.startsWith("order:timeout:")) {
            String orderId = expiredKey.replace("order:timeout:", "");
            cancelOrder(orderId);  // 取消订单
        }
    }
}
```

**注意几个坑：**
1. 通知是**至少一次**，不是精确一次——可能收到重复通知，要做好幂等
2. 如果 Redis 本身挂了，通知会丢失——这个机制只适合"丢了也无所谓"的场景
3. 过期事件只在 key **被 Redis 主动删除**时触发（惰性删除不会触发），且不保证时效性——如果大量 key 同时过期，可能延迟

> 💡 小贴士：Redis 的键空间通知本质上用的是 Pub/Sub，消息不持久。所以在面试时说"可以用过期事件做订单超时关闭"时，要自觉补一句"如果要求高可靠，还得用 RocketMQ/Kafka 的延迟队列"——面试官就爱听这种知道底线在哪的回答。

## 5. Redis 的 Sort 命令和 Sorted Set 的比较和应用场景

**回答：**

`SORT` 命令挺古老的，2.0 之前就有，很多人面试都忽略它，但其实在一些特定场景下很有用。

`SORT` 可以**对 List、Set、ZSet 进行排序**，甚至是跨 key 排序：

```bash
# 存用户年龄
SET user:1001:age 25
SET user:1002:age 30
SET user:1003:age 22

# List 存用户 ID
LPUSH user:ids 1001 1002 1003

# 根据年龄排序，取 ID
SORT user:ids BY user:*:age GET user:*:name
# 返回按年龄排序的用户名
```

**Sort vs Sorted Set 到底用哪个？**

说实话，**90% 的场景用 ZSet**，因为 ZSet 的排序是**维护好的**，`SORT` 是**每次排序**，性能差很多。

```bash
# ZSet 天然有序
ZADD ranking:score 25 "user:1001"
ZADD ranking:score 30 "user:1002"
ZADD ranking:score 22 "user:1003"

ZREVRANGE ranking:score 0 2 WITHSCORES
# 自动就是按分数排序的结果，复杂度 O(log(N)+M)
```

什么时候才用 `SORT`？
- 数据存在不同的 key 里，需要**跨 key 引用排序**
- 排序的"外键"数据是动态的，不适合存到 ZSet 里

但说句实话——`SORT` 在 Redis 6.0 之后被标记为**可废弃**了（复杂度 O(N+M*log(N))，数据量大时是灾难），除非你是维护老项目，否则新项目直接用 ZSet 或业务层排序。

> 💡 小贴士：`SORT` 有个参数 `ALPHA` 可以按字典序排序字符串，`LIMIT` 可以做分页。但性能上有个坑：`SORT` 默认会排序所有元素再截取，即使有 LIMIT。所以大数据集上别用 SORT 做分页，用 ZSet。

## 6. Redis 大 Key 和热 Key 怎么发现？怎么处理？

**回答：**

**大 Key** 和 **热 Key** 是 Redis 生产环境最常见的两个问题。先说两者的区别：

- **大 Key**：value 太大（String > 10KB）或集合元素太多（List/Set/ZSet/Hash > 万级别）
- **热 Key**：某 key 的 QPS 极高，单片 Redis 扛不住

**怎么发现大 Key：**

```bash
# 方法1：redis-cli --bigkeys（最常用）
redis-cli --bigkeys -h 127.0.0.1

# 方法2：memory usage 命令（精准分析单个 key）
MEMORY USAGE user:1001:profile

# 方法3：scan + debug object（线上最安全的方案）
SCAN 0 COUNT 1000
# 对返回的 key 逐个 debug object
```

**大 Key 的危害：**
- 读写大 key 会阻塞 Redis 单线程
- 大 key 的删除也可能阻塞（4.0 之后可以用 `UNLINK` 异步删除）
- 内存不均——Cluster 模式下某些节点内存打满

**大 Key 的处理：**
- String 大 key：拆分为多个小 key（按字段拆分或按分片）
- 集合类型：拆分为多个集合，比如 Hash 按 field 分片
- 或者换思路——数据转移到其他存储（ES、HBase）

**热 Key 怎么发现：**
- 客户端侧统计（最佳方案）：在 Jedis/Redisson 层面记录 key 的访问频率
- Redis 6.0+ 的 `hotkeys` 子命令（但 `redis-cli --hotkeys` 比较吃性能，线上慎用）
- proxy 层统计（如果用了 Redis proxy 如 Codis/Twemproxy）

**热 Key 的处理：**

```java
// 策略1：本地缓存 + Redis 多级缓存（最常见）
// Guava/Caffeine 做 JVM 缓存，热 Key 直接从本地拿
LoadingCache<String, Object> localCache = Caffeine.newBuilder()
    .maximumSize(10000)
    .expireAfterWrite(1, TimeUnit.SECONDS)
    .build(key -> redisTemplate.opsForValue().get(key));

// 策略2：打散到多个 key（把热 key 的副本分散到多个分片）
// 比如 key "hot_product_1001" 热点太高，拆成 10 个副本
for (int i = 0; i < 10; i++) {
    String key = "hot_product_1001:" + i;
    redisTemplate.opsForValue().set(key, value, 60, TimeUnit.SECONDS);
}
// 读的时候随机选一个副本
```

> 💡 小贴士：面试中能说出"Caffeine 本地缓存 + Redis 分布式缓存"这个方案的，比只说 Redis 的要高一个段位。本地缓存的 TTL 你定多长？1 秒就够——扛住了热点即可，不需要强一致性。同时本地缓存要注意 JVM 内存上限，别把堆撑爆了。

## 7. Redis 内存碎片率是怎么回事？怎么监控和优化？

**回答：**

Redis 用 `INFO memory` 可以看到几个关键指标：

```
used_memory: 838860800      # 实际数据占用的内存（字节）
used_memory_rss: 1048576000 # 操作系统分配给 Redis 的内存（RSS）
mem_fragmentation_ratio: 1.25  # RSS / used_memory
```

**碎片率 = RSS / used_memory**，它告诉你有多少内存实际没用到但被占着。

**各种碎片率对应的处理：**

| 碎片率 | 含义 | 怎么办 |
|-------|------|--------|
| 1.0 - 1.5 | ✅ 正常范围 | 不用管 |
| > 1.5 | 🔴 碎片偏高 | 开启自动碎片整理或重启 |
| < 1.0 | ⚠️ 内存不足（swap 了） | 赶紧加内存或扩集群 |

碎片产生的原因：
1. **频繁删除和修改**——Redis 分配的内存不会立刻归还给 OS，内部产生了空洞
2. **内存分配器**——Redis 默认用 jemalloc，它有自己的内存分配策略，小内存释放后可能不会还给 OS
3. **数据分布不均**——存了大 key 然后删了，空出来一大块

**优化方案：**

```bash
# 方案1：开启自动碎片整理（Redis 4.0+, 生产中可用但别设太高）
CONFIG SET activedefrag yes
CONFIG SET active-defrag-ignore-bytes 100mb    # 碎片超过 100MB 开始整理
CONFIG SET active-defrag-threshold-lower 10    # 碎片率超过 10% 开始
CONFIG SET active-defrag-cycle-min 25           # CPU 占用最小 25%
CONFIG SET active-defrag-cycle-max 75           # CPU 占用最大 75%

# 方案2：手动重启（最快但需要主从切换）
# failover + 重启，内存重新分配，碎片率降到 1.0+

# 方案3：定期做 flush 后重新写入（适合缓存场景）
```

> 💡 小贴士：有个很多面试官会问的点——`info memory` 里的 `mem_fragmentation_ratio` 如果小于 1，不是好现象，说明 OS 在给 Redis swap，性能已经开始跳水了。另一个容易被忽略的指标是 `evicted_keys`——如果这个数在涨，说明内存淘汰策略正在被频繁触发，该加内存或加节点了。

## 8. Redis 主从复制的断线重连机制——psync2 优化了什么？

**回答：**

Redis 主从复制经历了从 `sync`（全量同步）→ `psync`（部分同步）→ `psync2`（支持重启后的部分同步）三个版本。

**psync（Redis 2.8）**：
断线重连后，从节点发送 `PSYNC ? -1`，主节点回复要不要全量同步。

核心是两个东西：
- **run_id**：主节点重启后 run_id 变，从节点必须全量同步
- **repl_backlog_buffer**：环形缓冲区，默认 1MB，存最近执行的写命令。断线后如果 backlog 还在且有偏移量，可以做增量同步

**psync2（Redis 4.0）**：
关键的优化是：**主节点重启后，原来的从节点变成主节点，也能支持部分同步**。

怎么做到的呢？psync2 引入了 **repl_id 和 repl_offset 的持久化**——主从切换时，新的主节点继承了旧主的 repl_id，从节点如果存了偏移量，就不用全量同步。

```bash
# 查看复制状态
INFO replication
# role:master
# replid: 3c4a5b6c7d...   # 当前 replication ID
# replid2: 1a2b3c4d5e...   # 上一个 replication ID（psync2 关键）
# second_repl_offset: 12345 # 上一个 replid 对应的偏移量
```

**psync2 为什么重要**——因为实际生产中主从切换非常频繁，没有 psync2，每次切换都要全量同步，几 GB 的 RDB 传输几次就炸了。

**怎么避免全量同步：**
- `repl-backlog-size` 设大一点，默认 1MB 太小。计算公式：`backlog = 主节点每秒写入量 × 预估断线时间`
- 如果每秒写入 1MB，预估断线 10 分钟，backlog 得 600MB
- 太大了也别夸张，内存有限

> 💡 小贴士：面试官问"主从复制全量同步的流程"，标准回答：①从节点发送 psync ②主节点 bgsave 生成 RDB ③主节点开始缓存写命令到 backlog ④传输 RDB ⑤从节点清空自己数据，加载 RDB ⑥主节点把 backlog 中的增量命令发给从节点。能把这六步背出来，面试官就觉得你彻底懂了。

## 9. Redis 集群的 Gossip 协议和故障检测机制

**回答：**

Redis Cluster 节点间不通过中心化的注册中心通信，而是通过 **Gossip 协议**——八卦协议，像八卦消息一样，从一个人传到另一个人。

**消息类型**：

| 消息类型 | 作用 |
|---------|------|
| PING | 定期随机挑几个节点，检测对方活着没 |
| PONG | 回复 PING，顺便捎带自己知道的其他节点状态 |
| MEET | 新节点加入集群时发，让对方把你加进来 |
| FAIL | 某个节点挂了，广而告之 |

**故障检测流程：**

1. **主观下线（PFAIL）**：
   节点 A 给节点 B 发 PING，超时没收到 PONG → A 标记 B 为 PFAIL（主观下线）

2. **客观下线（FAIL）**：
   A 把 B 的 PFAIL 信息通过 Gossip 广播出去。当集群中**超过半数**的主节点都认为 B 挂了 → B 被标记为 FAIL（客观下线）

3. **故障转移**：
   如果 B 是一个主节点，它的从节点发起选举。Raft 风格的投票——比如 slot 的"授权"机制，从节点获得大部分主节点投票就能升级为主。

**Cluster bus 端口**：
注意 Redis Cluster 有两个端口——服务端口（比如 6379）和集群总线端口（16379）。Gossip 消息走**集群总线端口**，用二进制协议，不经过 RESP 协议，性能更高。

```bash
# 手动标记节点下线（紧急场景）
CLUSTER FAILOVER [FORCE | TAKEOVER]
```

> 💡 小贴士：Gossip 协议的"最终一致性"有一句口诀——"每一轮，每个节点随机选 3~5 个节点发 PING"。所以一个节点挂了，其他节点最多几秒到十几秒就能感知到。但有个细节：如果网络分区，两个部分各认为对方挂了，就出现了"脑裂"。Redis Cluster 通过 **quorum** 机制解决——数据只能写入多数派的节点，少数派不接受写入。

## 10. Redlock 分布式锁算法深度剖析——它真的安全吗？

**回答：**

Redlock 是 Redis 的作者 antirez 提出的分布式锁算法，目的是在**多个 Redis 实例**（互相独立的 master，不是 Cluster）上实现更可靠的锁。

**基本流程：**
1. 获取当前时间（毫秒）
2. 依次向 N 个（通常 5 个）独立的 Redis master 节点加锁，加锁的超时时间要远小于锁的 TTL（比如加锁超时设为 10ms，锁 TTL 设为 10s）
3. 计算过去的时间，如果成功加锁超过半数（≥ 3/5）且总耗时 < 锁 TTL，则加锁成功
4. 加锁成功后，锁的有效时间 = TTL - 耗时

**核心代码：**

```java
// 用 Redisson 实现（不建议自己手写，坑太多）
Config config = new Config();
config.useSentinelServers()
    .addSentinelAddress(
        "redis://node1:6379", 
        "redis://node2:6379", 
        "redis://node3:6379"
    );
RedissonClient redisson = Redisson.create(config);

RLock lock = redisson.getLock("myLock");
try {
    // 尝试加锁，最多等 100 秒，10 秒后自动解锁
    if (lock.tryLock(100, 10, TimeUnit.SECONDS)) {
        // 执行业务逻辑
    }
} finally {
    lock.unlock();
}
```

**说句实话——Redlock 到底安不安全？**

这个问题业界争议很大，知道内情的人会告诉你：

**反方（Martin Kleppmann 观点）**：
- 依赖系统时钟——如果你的 Redis 节点发生时钟跳跃（NTP 回拨），锁的超时判断就出问题
- 简单的单 Redis 主从切换时，从节点还没同步数据就升主了，锁丢了
- 更建议用 **ZooKeeper** 来做强一致锁

**正方（antirez 反驳）**：
- 时钟问题可以用**物理时钟 + 保护措施**规避
- 大多数场景下，Redis 的延时足够低，Redlock 的安全性"足够好"

**我的建议：**
- **99% 的场景**：单 Redis master + Redisson 就够了——可以用主节点加锁，即使主挂了直接报错不给锁，也别为了可用性牺牲一致性
- **真的要求严格一致性**（金融场景）：请上 ZooKeeper / etcd，别折腾 Redlock
- **缓存场景**：连分布式锁都不需要，用本地锁 + 乐观锁就够了

> 💡 小贴士：面试官如果让你手写一个分布式锁，千万别上去就是 SETNX + EXPIRE 两步——存在死锁风险（SETNX 成功了 EXPIRE 没设上）。正确写法是 `SET key value NX EX 10`，一步到位，原子操作。这就是传说中的"正确的 Redis 分布式锁"。写到这一步就够了，再加 Redlock 就是加分项。

## 11. Redis 事件驱动源码分析——aeEventLoop 是怎么工作的？

**回答：**

Redis 为什么是单线程但能扛十几万 QPS？秘密就在它的**事件驱动模型**上。源码在 `ae.c` 里，整个模型围绕一个结构体：

```c
// ae.c - 事件循环核心结构
typedef struct aeEventLoop {
    int maxfd;                    // 最大文件描述符
    long long timeEventNextId;    // 时间事件 ID 生成器
    aeFileEvent events[AE_SETSIZE];      // 注册的 IO 事件
    aeFiredEvent fired[AE_SETSIZE];      // 已触发的 IO 事件
    aeTimeEvent *timeEventHead;   // 时间事件链表头
    int stop;                     // 停止标志
    void *apidata;                // epoll/kqueue 的具体数据
} aeEventLoop;
```

**两种事件类型：**

**1. 文件事件（IO 事件）**：
用 IO 多路复用（Linux 上首选 **epoll**，macOS 用 kqueue）监听 socket 事件。

```c
// 注册一个读事件
aeCreateFileEvent(server.el, fd, AE_READABLE, readQueryFromClient, NULL);
```

当 epoll_wait 返回后，Redis 遍历 `fired` 数组，依次调用回调函数（如 `readQueryFromClient` → 解析命令 → `call()` 执行 → `addReply` → 写回客户端）。

**2. 时间事件（定时任务）**：
周期执行的任务，比如 `serverCron`——每秒执行 10 次（100ms 一次），负责：
- 清理过期 key（定期删除）
- 检查持久化状态
- 更新统计信息
- 主从重连检查

```c
// 注册周期性时间事件
aeCreateTimeEvent(server.el, 1, serverCron, NULL, NULL);
```

**一次事件循环的完整流程：**

```
1. 调用 beforesleep()  —— 写回客户端缓冲区
2. aeApiPoll()          —— epoll_wait 等待事件（可设超时）
3. 处理文件事件         —— 读/写 socket
4. 处理时间事件         —— 执行到期的 serverCron
5. 回到 1
```

> 💡 小贴士：源码层面有个特别巧妙的点——`aeApiPoll` 的超时时间是由**最近的时间事件**决定的。如果 50ms 后有个时间事件要执行，epoll_wait 就只等 50ms，保证了定时任务的精确性。你如果能说出这个细节，面试官绝对眼前一亮。

## 12. Redis RESP3 协议和 RESP2 有什么区别？客户端缓存是什么？

**回答：**

**RESP（Redis Serialization Protocol）** 是 Redis 的通信协议。Redis 6.0 引入了 **RESP3**，这是 2.0 以来最大的协议升级。

**RESP2 的问题：**
- 类型太少——就 5 种类型：Simple String、Error、Integer、Bulk String、Array
- 客户端不知道返回是否"完整"——比如 `HGETALL` 返回一个数组，客户端得自己按"奇偶位"解析成键值对
- 没有**推送能力**——只能客户端请求，服务端响应

**RESP3 新增的类型：**

| RESP3 类型 | 作用 |
|-----------|------|
| Null | 明确的 null，不再搞 `$-1\r\n` |
| Map | 直接把 key-value 结构发过来，客户端不用自己解析 |
| Set | 明确的集合类型 |
| Push | **服务端主动推送数据给客户端** |
| Big Number | 大整数，常用于计数场景 |
| Boolean | true/false |

最牛的新特性是 **客户端缓存（Client-side caching）**：

```bash
# 客户端订阅 key 的变化
CLIENT TRACKING ON OPTIN
# 再读 key
GET mykey
# Redis 会记住这个客户端在关注 mykey
# 当 mykey 被修改/删除时，Redis 主动发 Invalidation 消息
+UNSUBSCRIBE mykey
```

**客户端缓存的工作原理：**
1. 客户端读 key，数据缓存在**客户端本地内存**（比如 50MB 的 LRU 缓存）
2. Redis 服务端维护一个映射表：`client_id → [key1, key2, ...]`
3. 当某个 key 被修改，Redis 主动给关心这个 key 的客户端发"Invalidation"消息
4. 客户端收到后，从本地缓存中移除这个 key

**性能提升有多大？**
实测：热点 key 的读延迟从 1ms（网络往返）降到 < 0.01ms（本地内存），且 Redis 服务端的 QPS 压力直接减半。

```java
// Lettuce 支持客户端缓存（Redis 6.0+）
RedisClient client = RedisClient.create("redis://localhost");
StatefulRedisConnection<String, String> conn = client.connect();

// 启用跟踪
conn.setAutoFlush(true);
conn.async().get("mykey");  // 自动纳入跟踪

// 服务端 key 变化时，Lettuce 自动清除本地缓存
```

> 💡 小贴士：RESP3 是向后兼容的——Redis 6.0 同时支持 RESP2 和 RESP3，用 `HELLO 3` 协议切换。但客户端也得升级，老版本 Jedis 不支持 RESP3，Lettuce 5.x 开始支持。面试时可以说"RESP3 最大的价值是让 Redis 从一个请求-响应模型变成了一个双向通信的实时数据层"。

## 13. Redis 7 的新特性盘点——哪些值得关注？

**回答：**

Redis 7.0（2022 年 4 月发布）是近年来最大的版本更新之一，7.2/7.4 也有不少实用改进。说几个面试能拿分的：

**Redis 7.0 (2022)：**

**1. Redis Functions**——Lua 脚本的替代品
以前写 Lua 脚本用 `EVAL`，每次传到 Redis 服务端编译一次。Functions 让你**一次性注册脚本**到 Redis 中：

```bash
# 注册一个函数
FUNCTION LOAD "#!lua name=mylib\nredis.register_function('hgetall_to_json', function(keys, args) local r = redis.call('HGETALL', keys[1]) return r end)"

# 调用注册的函数
FCALL mylib hgetall_to_json 1 myhash
```

好处是：可复用、可管理、支持版本控制，不像 EVAL 那样每次都要传脚本内容。

**2. ACL v2——更精细的权限控制**
以前的 ACL 只能控制命令级别，v2 支持**键模式匹配**：

```bash
# 只允许访问 user: 开头的 key
ACL SETUSER appuser ~user:* +@read ~user:* +@write

# 禁止访问敏感命令
ACL SETUSER readonly +@read -FLUSHDB -FLUSHALL -CONFIG
```

**3. sharded Pub/Sub——集群模式下的发布订阅**
以前 Redis Cluster 不支持 Pub/Sub 的**水平扩展**——一条消息会在所有节点广播。7.0 的 sharded Pub/Sub 让消息只在一个 slot 内广播，解决了集群下 Pub/Sub 的线性增长问题。

**Redis 7.2 (2023)：**
- **Auto-failover 改进**——Cluster 中的副本自动提升速度更快
- **新的统计指标**——`INFO CLIENTS` 能看到更多客户端信息

**Redis 7.4 (2024)：**
- **向量搜索原生支持**——Redis Stack 的向量搜索能力合并到核心
- **新的数据类型支持**——完善 JSON 和 TimeSeries

> 💡 小贴士：面试官问到"Redis 新版本"，能说出 Functions、sharded Pub/Sub 和 ACL v2 就够了。再加一句"Redis 7.4 原生支持向量搜索，意味着小规模 RAG 应用不需要额外引入向量数据库"，这是加分回答，说明你在关注 Redis 在 AI 场景的应用。

## 14. 用 Redis + AI 做实时特征存储（Feature Store），怎么设计？

**回答：**

在 AI 场景中，很多模型需要**实时特征**——比如推荐系统需要用户最近 5 分钟的点击行为、风控模型需要当前设备的特征标签。这些数据放在 HBase 太慢，放在 MySQL 扛不住，Redis 是最合适的中间层。

**方案设计：**

```
                    ┌──────────────────┐
                    │   特征计算服务    │
                    │  (Flink/Spark)   │
                    └────────┬─────────┘
                             │ 写入特征
                             ▼
                    ┌──────────────────┐
                    │   Redis 特征层    │
                    │  (Hash + ZSet)   │
                    └────────┬─────────┘
                             │ 读取特征（微秒级）
                             ▼
              ┌─────────────────────────┐
              │  模型推理服务 (AI)       │
              │  在线推理 / Batch 推理   │
              └─────────────────────────┘
```

**具体的 Redis 数据结构设计：**

```java
// 1. 实时用户行为特征（用 ZSet 存最近行为，时间戳做 score）
redisTemplate.opsForZSet().add(
    "feature:user:click:" + userId,
    JSON.toJSONString(clickEvent),
    System.currentTimeMillis()
);
// 只保留最近 100 条
redisTemplate.opsForZSet().removeRange(
    "feature:user:click:" + userId, 0, -101
);

// 2. 用户画像特征（用 Hash 存多字段）
redisTemplate.opsForHash().putAll(
    "feature:user:profile:" + userId,
    Map.of(
        "age_group", "25-34",
        "city", "北京",
        "device", "iPhone16",
        "last_active_hour", String.valueOf(LocalDateTime.now().getHour())
    )
);
// TTL 控制特征时效性
redisTemplate.expire("feature:user:profile:" + userId, 3600, TimeUnit.SECONDS);

// 3. 模型特征向量（String 存 embedding）
// 用户 embedding，从离线计算好写到 Redis
redisTemplate.opsForValue().set(
    "feature:emb:user:" + userId,
    embeddingBytes,
    Duration.ofHours(1)
);

// 4. 在线推理：一次性读出所有特征
@GetMapping("/recommend")
public List<Item> recommend(@RequestParam String userId) {
    // Pipeline 批量读取特征（毫秒级搞定）
    List<Object> features = redisTemplate.executePipelined(
        (RedisCallback<String>) conn -> {
            conn.zRange("feature:user:click:" + userId, 0, -1);
            conn.hGetAll("feature:user:profile:" + userId);
            conn.get("feature:emb:user:" + userId);
            return null;
        }
    );
    
    // 组装特征 -> 调用模型 -> 返回推荐结果
    List<ClickEvent> clicks = parseClicks(features.get(0));
    Map<String, String> profile = parseProfile(features.get(1));
    float[] emb = parseEmbedding(features.get(2));
    
    return recommendationModel.recommend(clicks, profile, emb);
}
```

**几个关键设计考量：**

1. **TTL 分级**：用户实时行为短（5-10分钟）、画像特征长（1小时）、离线计算的 embedding 最长（1天）
2. **Pipeline 批量读**：一个推理请求可能要读 5~10 个特征，用 pipeline 批量读取，网络开销一次就够了
3. **降级方案**：如果 Redis 挂了，从 HDFS/对象存储中读离线副本，牺牲实时性换取可用性

> 💡 小贴士：如果面试官追问"离线特征和实时特征怎么协同"，你可以说跟 Feature Store 的架构一样——离线 Batch 算出预设特征写到 Redis，Flink 实时计算增量特征更新到 Redis，推理时把两者拼起来。这样既不会所有特征都走实时（太贵），也不会所有特征离线（时效性差）。

## 15. 设计一个高并发秒杀系统——Redis 如何扛住百万 QPS？

**回答：**

秒杀是 Redis 最经典的面试题。完整方案涉及六个关键步骤，缺一不可。

**先上架构图理解全局：**

```
用户 → Nginx（限流 + 静态分离）
    → 网关层（令牌桶限流，削峰）
        → Redis 集群（库存扣减 + 请求去重）
            → MQ 异步落单（削峰填谷）
                → 数据库异步写入订单
```

**Redis 部分的防守代码：**

```java
// 1. 基于 Lua 脚本的原子扣库存
// Redis 里存：seckill:stock:1001 = 100（库存量）
// seckill:user:1001:set = Set（已抢购用户，用于一人一单）

String script = """
    -- 参数：KEYS[1]=库存key, KEYS[2]=用户去重set, KEYS[3]=用户ID
    local stock = redis.call('GET', KEYS[1])
    if not stock or tonumber(stock) <= 0 then
        return -1  -- 卖完了
    end
    
    -- 一人一单校验
    local isMember = redis.call('SISMEMBER', KEYS[2], KEYS[3])
    if isMember == 1 then
        return -2  -- 重复抢购
    end
    
    -- 扣库存 + 记录用户
    redis.call('DECR', KEYS[1])
    redis.call('SADD', KEYS[2], KEYS[3])
    return 1  -- 成功
""";

Long result = redisTemplate.execute(
    new DefaultRedisScript<>(script, Long.class),
    Arrays.asList("seckill:stock:1001", "seckill:user:1001:set", userId)
);

// result == 1 → 抢到了 → 丢 MQ 异步落单
// result == -1 → 卖完了
// result == -2 → 你已经抢过了
```

**一个完整的秒杀方案分层：**

| 层级 | 做什么 | 怎么防冲击 |
|------|-------|-----------|
| **浏览器端** | 按钮置灰 | 防重复请求 |
| **CDN** | 静态资源、秒杀倒计时 | 防静态流量打到后端 |
| **Nginx** | 限流（单 IP 每秒 5 次） | 防刷单 |
| **网关层** | 令牌桶，2000 QPS | 削峰 |
| **Redis** | 原子扣库存，去重 | 扛实时扣减 |
| **MQ** | 异步落单 | 削峰填谷 |
| **DB** | 最终一致写订单 | 抗住即可 |

**几个容易被忽略的点：**

1. **库存预热**：不要直接扣 DB，先把库存塞到 Redis，Redis 扛不住之前 DB 根本不会被打到
2. **库存持久化**：Redis 写完库存就完事了？别——Redis 挂了库存恢复不了，要异步写个副本到 DB
3. **静态化秒杀页**：前端一秒杀，别让用户刷新页面打到服务器，HTML/CSS/JS 全放 CDN
4. **兜底策略**：如果真的 Redis 扛不住了，直接降级——Nginx 层返回"活动太火爆"，给个友好的失败页

> 💡 小贴士：面试回答秒杀系统的核心一句话："前端拦截 + 后端限流 + Redis 原子扣库存 + MQ 异步落单"。如果你能把这个链路完整串起来，面试官就知道你有全局架构的能力了。
