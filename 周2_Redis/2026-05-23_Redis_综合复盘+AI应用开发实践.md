### Q1 ⭐: 快问快答——Redis 的五种基本数据类型分别是什么？说一个最常用的场景就行。

**高分回答：**

"简单直接过一遍：

| 类型 | 底层实现 | 一句话场景 |
|------|---------|-----------|
| **String** | SDS（动态字符串） | 缓存、计数器、分布式锁 |
| **Hash** | dict（哈希表）+ ziplist | 存对象，比如用户信息，比 String + JSON 省内存 |
| **List** | quicklist（双端链表） | 消息队列、最新消息列表、时间线 |
| **Set** | intset + dict | 去重、标签系统、共同好友 |
| **ZSet** | skipList + dict | 排行榜、延时队列、限流滑动窗口 |

**面试官最想看你说出什么？** 不是背类型，而是知道**底层数据结构怎么切换**。比如 Hash 什么时候用 ziplist、什么时候用 dict——当 field 数量少于 `hash-max-ziplist-entries`（默认512）且每个 field 的值小于 `hash-max-ziplist-value`（默认64字节）时用 ziplist，否则转 dict。这个转换是**不可逆**的。

> 💡 追问点：Sorted Set 底层为什么用 skipList 而不是平衡树？——跳表实现简单，区间查询友好，而且插入/删除不需要 rebalance。

### Q2 ⭐: Redis 过期键是怎么删除的？不会把内存撑爆吗？

**高分回答：**

"这个问题问的是 Redis 的过期策略，我分成三个维度来说：

**1. 惰性删除（lazy expiration）**——每次访问 key 时检查是否过期，过期就删。优点是 CPU 友好，缺点是过期 key 可能一直占着内存没人管。

**2. 定期删除（active expiration）**——`server.hz` 默认每秒 10 次，每次随机取 `ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP`（默认 20）个带过期时间的 key，检查并删除。如果过期比例超过 25%，就继续再取一批，最多执行 25% 的 CPU 时间片。

**3. 内存淘汰（eviction）——兜底方案。** 如果上面的策略都没来得及删，内存满了咋办？那就看 `maxmemory-policy` 配置：

```
noeviction       → 满内存不写新数据，直接报错
allkeys-lru      → 所有 key 按 LRU 淘汰（最常用）
volatile-lru     → 只在设置了过期时间的 key 中 LRU 淘汰
allkeys-lfu      → 按访问频率淘汰
volatile-ttl     → 优先淘汰快过期的
```

**这里有个面试高频坑：** 惰性删除+定期删除，是不是就不怕过期 key 堆积了？不是。如果一个 key 设置了过期时间但再也没有被访问过，而且定期删除轮训始终没扫到它——这个 key 就会一直存在直到内存淘汰触发。所以别完全依赖过期机制清数据，对于大批量过期 key，建议用 **SORTED SET + 定时任务** 主动清理。

> 💡 加分点：Redis 7.0 引入了 `active-expire-effective-similarity`，优化了定期删除的写回延迟问题。

### Q3 ⭐: RDB 和 AOF 选哪个？有没有都用上的方案？

**高分回答：**

"面试官问这个，大概率是想看你有没有**线上经验**。纸上谈兵的会说 RDB 快、AOF 可靠，有经验的会告诉你：**全都要，但要配好参数。**

**RDB（快照持久化）**
- 优点：文件紧凑，恢复快，适合做灾备
- 缺点：丢数据——`save 900 1` 意味着 15 分钟内如果只有 1 次写入，不触发快照，这 15 分钟的数据全丢

**AOF（追加日志）**
- 优点：日志粒度细，最多丢 1 秒数据（`appendfsync everysec`）
- 缺点：文件体积大，恢复慢

**生产标准方案：两者都开，AOF 做实时保障，RDB 做快速恢复和灾备。**

```bash
# redis.conf 推荐配置
appendonly yes
appendfsync everysec      # 每秒刷盘，最多丢 1 秒
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

save 900 1                # 15 分钟 1 次变更
save 300 10               # 5 分钟 10 次变更  
save 60 10000             # 1 分钟 10000 次变更
```

**还有个坑：** 很多人不知道 AOF 什么时候会被加载。Redis 启动时，**优先加载 AOF**——如果 `appendonly yes`，Redis 会从 AOF 恢复数据，忽略 RDB 文件。只有 AOF 关掉或者 AOF 文件不存在时才会用 RDB 恢复。所以别以为开了两个就能同时读。

> 💡 追问点：AOF 重写（rewrite）的触发条件是什么？——`auto-aof-rewrite-percentage 100` 意味着当前 AOF 文件比上次重写后增长了 100% 就触发。子进程做 fork + copy-on-write，主进程继续写命令到重写缓冲区，等子进程完成后再把缓冲区内容追加进去。

### Q4 ⭐: Redis 主从同步的完整流程是什么样的？全量同步做了几次 bgsave？

**高分回答：**

"这个我会分全量同步和增量同步两个阶段来说。

**全量同步（第一次或者断连太久）：**

```
1. Slave 发送 PSYNC ? -1（问主库要全量数据）
2. Master 执行 bgsave 生成 RDB 快照 —— 这是第一次 bgsave
3. 同时 Master 启动 replication buffer，缓存新写入的命令
4. 把 RDB 发给 Slave
5. Slave 清空自身数据，加载 RDB
6. Master 把 replication buffer 里的增量命令发给 Slave
7. Slave 执行这些增量命令
```

**这里有个很多人搞错的地方：** 全量同步期间，Master 会做**两次** bgsave 吗？不会。只有**一次** bgsave。那个 replication buffer 就是在 RDB 生成期间缓存的写入，等 RDB 发完后作为增量补发。

**增量同步（repl_backlog 机制）：**

```
Slave 发送 PSYNC {run_id} {offset}
Master 检查 offset 是否还在 repl_backlog_buffer 范围内
如果在 → 返回 CONTINUE，发增量数据
如果不在 → 返回 FULLRESYNC，触发全量同步
```

**生产关键参数：**

```bash
repl-backlog-size 128mb     # 默认 1MB，建议调大到 128MB-512MB
repl-backlog-ttl 3600       # 没有 Slave 连接时，保留缓冲区 1 小时
```

`repl_backlog_size` 太小，Slave 断连一会儿就得全量同步，复制风暴就是这么来的。

> 💡 追问：主从复制风暴怎么解决？——多个 Slave 同时连同一个 Master 做全量同步。方案：用树状拓扑，Slave 下面再挂 Slave；或者用 Sentinel 控制同时重连的 Slave 数量。

### Q5 ⭐: Redis 实现分布式锁，讲一个生产可用的方案。

**高分回答：**

"如果要我面试这个题，我会直接上 Java 生产标准方案——**Redisson 的实现**，因为这就是业界共识。

**最基础的实现（单机 Redis 可用）：**

```bash
SET lock:order:1001 uuid_value NX EX 30
```

- `NX`：key 不存在才设置成功
- `EX 30`：自动过期 30 秒，防死锁
- `uuid_value`：每个客户端唯一标识，用来安全释放

**释放锁必须用 Lua 脚本保证原子性：**

```lua
-- unlock.lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**面试加分点——Redisson 的可重入锁 + WatchDog 自动续期：**

```java
RLock lock = redissonClient.getLock("lock:order:1001");
// 默认锁超时 30s，WatchDog 每 10s 检查一次，自动续期
lock.lock(10, TimeUnit.SECONDS); 

try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

**说出 WatchDog 的机制就是加分：** 加锁成功后，后台开一个定时任务，每 `lockWatchdogTimeout / 3`（默认 10 秒）检查一次锁还在不在，在就续期到 30 秒。如果客户端崩了，WatchDog 停掉，锁到期自动释放。

**RedLock 多节点锁——面试说两句就行，不要上来就用：**

```java
RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
```

RedLock 在实际生产中用得不多——因为它依赖大多数节点可用，而且时钟跳跃（clock jump）会导致问题。**Redis 作者 antirez 自己都承认 RedLock 有争议。** 大多数场景单机 Redis + 主从切换时的锁丢失风险，用业务兜底（比如数据库乐观锁）就够了。

> 💡 追问：锁超时了业务还没做完怎么办？——WatchDog 自动续期。或者用 `lock.lock(30, TimeUnit.SECONDS)` 指定自定义超时时间，避免无限续期。

### Q6 ⭐⭐: 缓存穿透、缓存击穿、缓存雪崩，讲清楚区别和各自怎么解决。

**高分回答：**

"这三个是所有面试缓存必问的，如果能把**产生原因和解决方案**都说清楚，面试官基本就满意了。

**缓存穿透（查一个不存在的数据）：**

问题：请求一个既不在缓存也不在数据库的 key，每次请求都打到数据库。

解决方案：
- **布隆过滤器**：请求来了先问布隆过滤器，不存在直接返回 404，不查 DB
- **缓存空值**：DB 查询结果为 null 时，也缓存一个空结果，设置短过期时间（比如 30 秒），防短时大量穿透
- **参数校验**：比如 ID 必须是正整数，非法参数直接 reject

**缓存击穿（热点 key 突然过期）：**

问题：一个热点 key 正好过期，大量请求同时打过来，都发现缓存没有，全部去查 DB。

解决方案：
- **互斥锁**：发现缓存失效时，只让一个线程去 DB 查询，其他线程 wait
- **逻辑过期**：缓存不设置物理过期时间，而是存一个逻辑过期时间字段。后台异步线程定期刷新
- **热点数据不过期**：真正的热点数据直接不设过期时间，配合后台更新

**缓存雪崩（大量 key 同时过期 / Redis 挂了）：**

问题：大量 key 设了相同的过期时间，同时过期，请求全部打到 DB。

解决方案：
- **过期时间加随机值**：`expire = base + random(1~300)`，防集体过期
- **本地缓存**：Redis 挂了，还有本地缓存（Caffeine/Guava 等）顶着
- **限流降级**：Sentinel/Hystrix 限流，保护后端 DB
- **Redis 高可用**：主从 + Sentinel/Cluster，挂了自动切换

**三者的核心区别用一句话总结：**

| 场景 | 问题根因 | 核心解决 |
|------|---------|---------|
| 穿透 | 查不存在的数据 | 布隆过滤器 |
| 击穿 | 热点 key 过期 | 互斥锁/逻辑过期 |
| 雪崩 | 大量 key 同时过期 / 实例挂 | 过期随机化 + 本地缓存 + 高可用 |

> 💡 加分点：能说出"布隆过滤器的误判率怎么算"——`k 个哈希函数，m 位数组，n 个元素，误判率 ≈ (1 - e^(-kn/m))^k`。但也得说它的局限：不支持删除（除非用 Counting Bloom Filter）。

### Q7 ⭐⭐: Redis Cluster 的数据分片原理——一致性哈希还是哈希槽？槽是怎么分配的？

**高分回答：**

"Redis Cluster **不是用一致性哈希**，用的是 **16384 个哈希槽（hash slot）**。

**分片规则：**

```
slot = CRC16(key) % 16384
```

每个 Master 节点负责一段连续范围的槽。比如 3 个节点：

```
Node A: 0~5460
Node B: 5461~10922
Node C: 10923~16383
```

**为什么用 16384 个槽而不是更多？**

Redis 作者在 github 上回答过：`CRC16` 输出 16 位，理论上可以分 65536 个槽。但 16384 个槽的心跳消息只占 2KB（16384 bits / 8 / 1024 = 2KB），传起来快。槽太多，心跳消息就得更大，浪费带宽。

**为什么不用一致性哈希？**

一致性哈希会引入虚拟节点来均分数据，多一层抽象，实现复杂。16384 个固定槽位方案**更简单直白**，而且槽的迁移粒度可控——一次移一个槽，影响最小。

**槽迁移过程：**

```
1. 在目标节点执行 CLUSTER SETSLOT {slot} IMPORTING
2. 在源节点执行 CLUSTER SETSLOT {slot} MIGRATING
3. 源节点遍历槽里的 key，逐个 MIGRATE 到目标节点
4. 迁移完成后发 CLUSTER SETSLOT {slot} NODE {nodeId}
5. 所有节点通过 gossip 协议得知新路由
```

**MIGRATE 命令的坑：** 它是**同步**操作——迁移一个 key 会阻塞源节点直到迁移完成。如果单槽里有上百万个 key，这个槽的迁移会非常慢。所以实际做 re-sharding 之前，最好先通过 `redis-cli --cluster reshard` 评估一下数据量，或者业务低峰期操作。

> 💡 追问：smart 客户端怎么知道 key 在哪个节点？——客户端缓存了 slots mapping，先算 `CRC16 % 16384` 再查本地映射表。如果请求的节点返回 `MOVED` 重定向，客户端更新本地缓存。如果返回 `ASK`，表示槽正在迁移，客户端先发 `ASKING` 再访问目标节点。

### Q8 ⭐⭐: 趁热打铁——Redis 底层的数据结构面试常考哪些？说说 SDS 和跳表。

**高分回答：**

"面试里问到 Redis 底层，一定要能说出**动态字符串 SDS、跳表 skipList、压缩列表 ziplist、快表 quicklist、整数集合 intset** 这五个。我挑两个最重要的说：

**SDS（Simple Dynamic String）——C 字符串的升级版**

C 语言的 char[] 有几个痛点：求长度得遍历 O(n)；`strcat` 不安全，可能缓冲区溢出；二进制不安全（遇到 `\0` 就断了）。

SDS 怎么改的：

```c
struct sdshdr {
    int len;      // 已用长度
    int free;     // 剩余空间
    char buf[];   // 字节数组
};
```

- `sds.len` 直接 O(1) 获取长度
- **空间预分配**：修改后如果长度 < 1MB，分配 `len + free` 的额外空间（`free = len`）；如果 >= 1MB，额外分配 1MB。目的是减少内存重分配次数
- **惰性空间释放**：缩短字符串不会立即释放内存，只是改 `len`，等真正需要再释放

**跳表（skipList）——ZSet 的核心**

为什么用跳表而不是平衡树？四个字：**实现简单**。

```
Level 3: ──────────────────────────────────────
Level 2: ──────●─────────●───────────●────────
Level 1: ──●─────●──●─────●──●──●─────●──●───
Level 0: ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─●
```

查找过程就像"跳着走"——从最高层开始，如果 next 节点的值小于 target，就往前走；如果大于，就降一层继续。**平均 O(log n)，最差 O(n)**。

**跳表的工程细节（说出来就是加分）：**

- 每个节点的层高通过随机函数决定（抛硬币），概率 50% 升一层
- 最大层数 64（Redis 7.0），32（Redis 6.0 之前）
- Redis 的跳表还实现了**后退指针**和**跨度记录**（span），方便从尾到头遍历和直接按排行取元素

```c
typedef struct zskiplistNode {
    sds ele;                    // 成员值
    double score;               // 分值（排序依据）
    struct zskiplistNode *backward;  // 后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;            // 到下一节点的跨度（用于 ZRANK）
    } level[];
} zskiplistNode;
```

> 💡 追问：压缩列表（ziplist）和快表（quicklist）有什么区别？——ziplist 是一块连续内存，所有元素紧挨着存，省内存但修改可能连锁更新。quicklist 是"ziplist 组成的双端链表"，一个 quicklistNode 就是一个 ziplist，适合 List 类型频繁的头部/尾部操作。

### Q9 ⭐⭐: Redis 单线程为什么这么快？6.0 又为什么引入多线程？

**高分回答：**

"这个问题面试官想听的不是'单线程快'——而是**单线程在哪些场景快、哪些场景慢**。

**单线程为什么快（三个核心原因）：**

1. **纯内存操作**——内存访问延迟 ≈ 100ns，磁盘 IO ≈ 10ms，差了 10 万倍。这是根本原因。

2. **IO 多路复用**——Redis 用 epoll（Linux）/ kqueue（macOS）处理连接。单线程可以同时监控多个 socket 的事件，用 `select/poll/epoll` 的事件驱动模型避免阻塞。

3. **避免了锁竞争**——单线程意味着没有线程切换开销、没有同步锁、没有上下文切换。`INCR` 就是原子操作，不用加锁。

**单线程的瓶颈在哪：**

- **CPU 不是瓶颈**——Redis 真的单线程跑就能打到 10w+ QPS，一般瓶颈是网络带宽或内存
- **慢查询是真正的杀手**——一个 `KEYS *` 可能阻塞几十万请求

**6.0 为什么引入多线程 IO：**

答案很简单：**网络 IO 处理变成了瓶颈。**

"Redis 说到底是 CPU 密集还是 IO 密集？网络 IO 密集。单线程处理网络读写时，如果一次请求的数据量大（比如 `MGET` 批量读），读入和写出的网络 IO 会卡住整个事件循环。

6.0 的改进是**多线程只处理网络 IO，命令执行还是单线程**：

```
主线程（事件循环）
│
├─ 接收客户端连接
├─ 解析命令、执行命令、返回结果
│
IO 线程池（默认为 3，加上主线程共 4 个线程）
│
├─ 从 socket 中读数据到输入缓冲区
├─ 从输出缓冲区写数据到 socket
```

这样网络 IO 的耗时从主线程剥离了，命令执行还是单线程，所以不需要担心并发安全问题。

**配置方式：**

```bash
io-threads 4           # 默认为 3（IO 线程数），总线程数 = io-threads + 1（主线程）
io-threads-do-reads yes  # 默认 no，需要手动开启读线程
```

> 💡 追问：IO 线程数一般设多少？——经验值是 4~8（加主线程）。设太多线程上下文切换反而变慢。而且 CPU 核心少的机器（比如 2 核）开多线程 IO 可能适得其反。

### Q10 ⭐⭐: Redis 事务、Lua 脚本、管道（Pipeline）——这三者有什么区别？什么时候用哪个？

**高分回答：**

"这个问题很多面试官喜欢问，因为如果你能分清楚这三者，说明你对 Redis 的执行模型理解到位了。

**直接用一张表格对比：**

| 特性 | MULTI/EXEC 事务 | Lua 脚本 (EVAL) | Pipeline |
|------|----------------|----------------|----------|
| **原子性** | ❌ 单命令失败继续执行 | ✅ 整个脚本原子执行 | ❌ 只是批量发送 |
| **回滚** | ❌ 不支持 | ❌ 失败就停，不回滚 | ❌ 不支持 |
| **执行位置** | 服务端批量执行 | 服务端原子执行 | 客户端批量发送 |
| **条件逻辑** | ❌ 不支持 if/else | ✅ 支持完整逻辑 | ❌ 不支持 |
| **网络往返** | 1 次请求（MULTI...EXEC）| 1 次 EVAL 请求 | n 个命令合并发送，1 次往返 |
| **结果可依赖** | 全部返回 | 返回脚本结果 | 所有结果按序返回 |

**面试官想听到的具体场景选择：**

```
1. 有条件判断、有循环 → Lua 脚本（比如限流、分布式锁释放）
2. 只想批量无依赖地发一批命令 → Pipeline（比如批量 SET，不需要原子性）
3. 想用 WATCH 做乐观锁 → 事务（MULTI/EXEC/WATCH）
4. 需要原子执行且带业务逻辑 → Lua 脚本
```

**举个例子——同样的功能用三种方式实现：**

```bash
# 场景：扣减库存，如果库存 > 0 则减 1

# 方式 1：事务 + WATCH
WATCH stock:001
val = GET stock:001
if val > 0
    MULTI
    DECR stock:001
    EXEC
else
    UNWATCH
end

# 方式 2：Lua 脚本（原子，无竞态）
EVAL "
    local stock = redis.call('GET', KEYS[1])
    if tonumber(stock) > 0 then
        return redis.call('DECR', KEYS[1])
    else
        return -1
    end
" 1 stock:001

# 方式 3：Pipeline（不适用于这个场景，因为没法做条件判断）
# Pipeline 适合：批量查询、批量写入
```

**我的建议：** 生产环境优先用 Lua 脚本——它既保证了原子性，又能写复杂逻辑。Pipeline 适合纯批量读写场景。事务（MULTI/EXEC）我基本只在需要 WATCH 乐观锁时才用。

> 💡 追问：Pipeline 一次发多少个命令合适？——经验值 100~500 个一批。太少浪费往返，太多一次内存占用过大，影响其他请求。而且 Pipeline 返回的结果是**无序对应**的——发送顺序和返回顺序一一对应，发的时候要自己记着。

### Q11 ⭐⭐⭐: Redis 在 AI 应用开发中扮演什么角色？不只是一个缓存吧？

**高分回答：**

"这个问题特别好，Redis 在 AI 系统里远不止一个缓存。我说几个我实际见过的方案：

**角色 1：语义缓存（Semantic Cache）**——基于 Redis Stack 的向量检索能力

AI 对话中，用户的问题很多时候是重复的或高度相似的。每次重复调用 LLM 既慢又费钱。用 Redis 做语义缓存：

```
用户提问 → 向量化（Embedding）→ Redis 向量搜索找最相似的历史问题
         ├─ 相似度 > 阈值（比如 0.95）→ 直接返回缓存答案
         └─ 相似度 < 阈值 → 调 LLM → 结果存入 Redis（问题向量+答案）
```

这个方案能减少 30%~50% 的 LLM 调用，对 C 端产品来说成本节省很明显。

**角色 2：会话状态管理——AI Agent 的多轮记忆**

Agent 对话不是一问一答完事，它需要保持上下文。Redis Hash / String 存用户会话状态是最常见的：

```
user:{userId}:session  →  存当前对话的 token 数、topic、状态机位置
user:{userId}:history  →  List 存最近 N 轮的消息摘要（窗口管理）
user:{userId}:tools    →  Set 存当前 session 已使用的工具列表
```

TTL 设置 30 分钟——用户 30 分钟没互动自动清理，既省内存又符合使用习惯。

**角色 3：限流和配额管理**

AI 产品面临的最大问题之一：用户滥用 API。Redis 的滑动窗口限流+Lua 脚本做精细化控制：

```lua
-- AI API 限流：每分钟最多 20 次，每次请求扣 1 个 token
local key = KEYS[1]  -- "ratelimit:{userId}:{minute}"
local maxTokens = tonumber(ARGV[1])
local now = tonumber(ARGV[2])

redis.call('ZREMRANGEBYSCORE', key, 0, now - 60)
local count = redis.call('ZCARD', key)

if count < maxTokens then
    redis.call('ZADD', key, now, now .. ':' .. math.random())
    redis.call('EXPIRE', key, 120)
    return 1  -- 允许请求
else
    return 0  -- 限流
end
```

**角色 4：Prompt 模板缓存 + 模型上下文缓存**

复杂的 AI 应用需要多轮 prompt 拼接，Redis 可以做 prompt 模板的缓存、以及中间推理结果的缓存。比如 Embedding 的结果缓存：

```bash
# 相同的文本，不要反复调 Embedding API
SET embedding:{md5(text)} "{embedding_vector}" EX 86400
```

这个在 RAG 场景下特别有用——相同的文档片段被多次查询时，Embedding 不用重复算。

**总结：** Redis 在 AI 系统里 = 缓存层 + 状态管理层 + 向量检索层 + 限流层。**一套 Redis Stack 全搞定。**

> 💡 追问：Redis 做向量检索和专门的向量数据库（Milvus/Pinecone）比有什么优劣？——Redis 胜在轻量和集成方便（不用再维护一套基础设施），适合中小规模（<1000 万向量）。大厂或者海量向量场景还是得上专门向量数据库。

### Q12 ⭐⭐⭐: 用 Redis Stack 的向量检索做语义缓存——具体怎么实现？

**高分回答：**

"这个我得先确认一下：你有 Redis Stack 或者 RediSearch 模块吗？（面试官点头）好，我来说具体实现。

**第一步：创建向量索引**

```bash
FT.CREATE semantic_cache_idx ON HASH PREFIX 1 "cache:"
SCHEMA
  question TEXT WEIGHT 1.0
  answer TEXT WEIGHT 0.0
  embedding VECTOR FLAT 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE
  timestamp NUMERIC SORTABLE
```

**第二步：写入缓存（LLM 返回结果后）**

```python
import redis
import numpy as np
from openai import OpenAI

r = redis.Redis(host='localhost', port=6379)
client = OpenAI()

def cache_llm_response(question, answer):
    # 1. 生成 Embedding（这里假设用的是 OpenAI text-embedding-3-small，1536 维）
    response = client.embeddings.create(
        input=question,
        model="text-embedding-3-small"
    )
    embedding = response.data[0].embedding
    
    # 2. 存入 Redis
    key = f"cache:{hash(question)}"
    r.hset(key, mapping={
        "question": question,
        "answer": answer,
        "embedding": np.array(embedding, dtype=np.float32).tobytes(),
        "timestamp": time.time()
    })
    r.expire(key, 86400)  # 24 小时过期
```

**第三步：查询缓存（先去 Redis 找）**

```python
def query_with_cache(question, threshold=0.92):
    # 1. 对用户问题生成 Embedding
    response = client.embeddings.create(
        input=question,
        model="text-embedding-3-small"
    )
    query_vec = response.data[0].embedding
    
    # 2. 向量检索——找最相似的问题
    result = r.ft("semantic_cache_idx").search(
        Query("*=>[KNN 1 @embedding $vec AS score]")
        .return_fields("question", "answer", "score")
        .sort_by("score")
        .paging(0, 1)
        .dialect(2),
        query_params={"vec": np.array(query_vec, dtype=np.float32).tobytes()}
    )
    
    if result.total > 0:
        doc = result.docs[0]
        similarity = 1 - float(doc.score)  # COSINE 距离转相似度
        if similarity >= threshold:
            return doc.answer, True  # 命中缓存
    
    return None, False  # 未命中
```

**第四步：结合 LLM 调用**

```python
def chat_with_cache(question):
    cached_answer, hit = query_with_cache(question)
    if hit:
        print("✅ 缓存命中！跳过 LLM 调用")
        return cached_answer
    
    # 未命中，调 LLM
    real_answer = call_llm(question)
    cache_llm_response(question, real_answer)
    return real_answer
```

**这里有几个考量点：**

- **阈值怎么定**：0.92~0.95 比较合适。太低了容易答非所问，太高了命中率低。建议上线后灰度观察
- **Embedding 模型选择**：`text-embedding-3-small` 性价比高，`text-embedding-3-large` 更准但贵一些
- **时效性**：某些问题答案会变（"今天BTC价格"），这种可以设短 TTL 或不缓存。建议在 question 里加关键词标记
- **缓存淘汰**：LRU 淘汰。如果缓存满了，Redis 的 `allkeys-lru` 自动淘汰最不常用的

> 💡 追问：缓存命中后怎么确认答案不过期？——两个维度：一是 TTL，给时间敏感的问题短 TTL；二是加 tag 机制，比如 `cache:price:{symbol}:{timestamp}`，带时间戳的可以做版本管理。

### Q14 ⭐⭐⭐: 一个 AI Agent 系统需要管理百万级用户会话状态——Redis 的架构怎么设计？

**高分回答：**

"这是个很有挑战的问题。百万级在线 Agent 用户，每个用户多轮对话，状态数据量很大。我说一个我在生产用的方案。

**需求分析先：**

```
每个用户：会话上下文 ≈ 20~50KB（最近 10 轮对话摘要）
百万同时在线：50GB+
状态更新频次：每次 Agent 推理轮次都会更新
TTL 要求：30 分钟无操作自动回收
```

**方案设计：**

**1. 数据模型分层**

```
# 热数据——Redis 内存
user:{uid}:session       → Hash（当前 session 的元数据）
  ├─ status: "thinking" | "waiting" | "done"
  ├─ tokens_used: 4289
  ├─ current_tool: "search_web"
  └─ start_time: 1716451200

user:{uid}:context:recent → List（最近 5 轮对话，每轮一个 JSON）
  - TTL: 30min

# 温数据——存到本地或 Redis 的 SSD（如果用了 Redis on Flash）
user:{uid}:context:full  → String（完整对话历史 JSON）
  - TTL: 24h，超时后归档到 MySQL/对象存储
```

**2. 多级存储策略**

```
热（Redis 内存）：当前活跃 Session，30 分钟无交互淘汰
温（Redis Flash/SSD）：同用户一天内的历史，按需回捞
冷（MySQL/对象存储）：超过 24 小时的历史，做缩略摘要
```

**3. 如何抗百万 QPS**

```python
# 批量处理——减少网络往返
pipeline = redis_client.pipeline()
for uid in active_users:
    pipeline.hgetall(f"user:{uid}:session")
results = pipeline.execute()

# 会话压缩——减少内存占用
import zlib
compressed = zlib.compress(json.dumps(context).encode())
redis_client.set(f"user:{uid}:context:full", compressed, ex=86400)

# 二级缓存——本地缓存兜底
# 用 Caffeine 做本地热点 Session 缓存（LRU 10000 个），减少 Redis 查询
```

**4. 高可用和容灾**

```
读写分离：主库写 Session 状态，从库读上下文
Sentinel/Cluster 高可用：哨兵自动切换
降级策略：Redis 挂了就从本地缓存+MySQL 恢复会话
限流保护：每个用户的 Session 操作限频（防止一个用户打爆 Redis）
```

**5. 扩展方案（百万级 -> 千万级）**

```
按用户 ID 哈希分片：user_hash % N → N 个 Redis Cluster
或者直接上 Redis Cluster，利用 16384 个槽自动分片
Cluster 下要注意：MGET 跨槽需要额外处理
```

> 💡 追问：Session 状态一致性怎么保证？——Agent 执行是多步的，中间状态写到 Redis。如果 Agent 中间挂了，需要从 Redis 读上次状态恢复。用 `WATCH` 或者 Lua 脚本保证状态转换的原子性。推荐把状态机逻辑写到 Lua 脚本里。

### Q15 ⭐⭐⭐: 综合设计——一个 AI 知识库问答系统的缓存架构，给我画完整方案。

**高分回答：**

"好，这个问题把本周 Redis 的知识点串起来了。我说一个完整的端到端方案。

**系统背景：** 企业内部知识库问答 Bot，支持 10 万个文档、1000+ 企业客户、每天数百万次查询。用户提问后，系统做 RAG（检索增强生成），从知识库检索相关文档，交给 LLM 回答。

**缓存架构分四层：**

```
用户请求
    │
    ▼
┌─────────────────────────────┐
│  Layer 1: 本地缓存 (Caffeine)│  ← <1ms，热点问题直接返回
│  热点问题 Top 1000，LRU    │
└──────────┬──────────────────┘
           │ 未命中
           ▼
┌─────────────────────────────┐
│  Layer 2: 语义缓存 (Redis)  │  ← <5ms，语义相似问题命中
│  向量索引 + 精确匹配        │
│  TTL: 24h / 按标签区分      │
└──────────┬──────────────────┘
           │ 未命中
           ▼
┌─────────────────────────────┐
│  Layer 3: 文档检索 (Redis)  │  ← <20ms，RAG 检索
│  Redis Stack 全文+向量检索  │
│  存储文档 Chunks + 向量     │
└──────────┬──────────────────┘
           │ 检索完成
           ▼
┌─────────────────────────────┐
│  Layer 4: LLM 调用          │  ← 500ms~5s，最终回答
│  (OpenAI / 本地模型)        │
└──────────┬──────────────────┘
           │ 返回结果同时写回缓存
           ▼
        响应给用户
```

**每个层的详细设计：**

**Layer 1——本地缓存（Caffeine）：**

```java
Cache<String, String> hotCache = Caffeine.newBuilder()
    .maximumSize(1000)
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .recordStats()
    .build();
```

命中率一般 10~20%，但胜在快——<1ms，完全无网络开销。

**Layer 2——语义缓存（Redis Stack）：**

```
Key: cache:{md5_question}  → 已经回看过 Q12 的实现
额外策略：
  - 短 TTL（10min）for 时效性问题（"今天业绩"）
  - 长 TTL（24h）for 知识性问题（"什么是 MVP"）
  - 缓存旁路：HR 相关问题的语义缓存单独建索引
```

**Layer 3——文档检索（Redis Stack 全文+向量混合检索）：**

```bash
FT.CREATE knowledge_docs_idx ON HASH PREFIX 1 "doc:"
SCHEMA
  title TEXT WEIGHT 5.0
  content TEXT WEIGHT 1.0
  embedding VECTOR FLAT 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE
  category TAG
  create_time NUMERIC SORTABLE
```

检索时做混合查询：

```python
# 混合检索：全文过滤 + 向量排序
query = Query("@category:{tech} @content:分布式系统")
    .hybrid_fields("embedding", query_vector)
    .add_return("__embedding_score")
    .dialect(2)
    .paging(0, 5)
```

**Layer 4——LLM 调用和缓存写入：**

LLM 回答写回 Layer 1 + Layer 2。配合**异步写入**，不阻塞主流程。

**缓存更新策略（上线要考虑的）：**

```
- 知识库文档更新 → 主动失效相关缓存 + 重算向量
- 缓存预热 → 上线前跑历史 Top 1000 问题预热
- 缓存淘汰 → Redis allkeys-lfu，低频问题自动淘汰
- 监控指标 → 缓存命中率、缓存大小、缓存延迟 P99
```

**系统容量估算：**

```
10 万文档 × 每个文档分 5 个 Chunk = 50 万向量
每个向量 1536 维 × 4 字节 = 6KB × 50 万 ≈ 3GB
加上问答缓存 ≈ 5GB
每天数百万请求，Redis 完全扛得住
```

**总结：** 这个方案用多级缓存解决了 AI 知识库的核心痛点——减少 LLM 调用次数、降低响应延迟、控制成本。Redis 在其中同时承担了语义缓存、向量检索、全文检索三重角色。

> 💡 追问：如果文档量上到 1000 万呢？——Redis 的向量索引是纯内存的，1000 万 × 6KB ≈ 60GB，成本会很高。这时候建议把 Layer 3 的检索切到 Milvus/Qdrant 这类专门向量数据库，Redis 只做 Layer 2 的语义缓存和 Layer 4 的会话管理。分层设计的好处就是每一层可以独立替换。
