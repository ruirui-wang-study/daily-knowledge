### Q1: Redis 是什么？和 Memcached 比有什么区别？

**面试官想听什么：** 不是背定义，是有过选型经验，能说出各自适合什么场景。

**高分回答：**

"Redis 是一个内存级 key-value 数据库，但它的功能远不止缓存。和 Memcached 比，差距是全方位的：

**数据类型上，** Memcached 就支持 String，Redis 有 5 种基本类型加 3 种高级结构。这意味着你可以用 Redis 的 List 做消息队列、用 ZSet 做排行榜、用 HyperLogLog 做 UV 统计——这些在 Memcached 里都得业务自己实现。

**持久化上，** Memcached 重启数据全丢，Redis 有 RDB 和 AOF 两种持久化方案，可以做到秒级恢复。所以 Redis 能做数据库而 Memcached 只能是缓存。

**功能特性上，** Redis 支持 Lua 脚本、事务、发布订阅、Lua 扩展——这些在 Memcached 里完全没有。

我说句实话：现在国内面试基本上不问 Memcached 了，但如果你能主动说出这个对比，说明你经历过那个时代，技术选型有深度。"

> 💡 面试官可能追问："既然 Redis 功能这么多，为什么还有人用 Memcached？"——答案：纯缓存场景 Memcached 多线程模型更简单，内存利用率在某些场景更高（没有 Redis 的额外数据结构开销）。

### Q2: Redis 支持哪几种数据类型？各自底层是怎么实现的？

**高分回答：**

"五种基本类型加三种高级结构。

**基本类型：**

**String** — 最基础，底层是 SDS（Simple Dynamic String），比 C 的 char* 多了长度字段，O(1) 长度获取，而且预分配空间减少了内存 realloc。

**List** — 底层是 quicklist，由多个 ziplist 节点组成。这么说吧，元素少的时候用 ziplist 省内存，元素多了转成 linkedlist 好操作。quicklist 就是把两个优点结合了。

**Hash** — 小数据量用 ziplist，超过阈值转 dict（哈希表）。ziplist 就是连续内存块，省空间；dict 就是 Java 的 HashMap 那套——链地址法解决冲突，渐进式 rehash。

**Set** — 底层是 dict，key 存 value，value 全是 null。所以 Set 的查询是 O(1)。

**ZSet** — 最复杂，底层是 ziplist + skiplist 的组合。小数据量用 ziplist，大数据量用 skiplist。跳表是 Redis 的特色实现，后面有题专门说。

**三种高级结构：**

**HyperLogLog** — 12KB 内存能统计 2^64 个元素的基数，误差 0.81%。代价是只能做基数统计，不能查具体有哪些元素。

**BitMap** — 就是位数组，适合做签到、活跃用户统计这种二值场景。一个月的签到用一个 31 位的 bit 就存下了。

**Geo** — 底层用 ZSet 存地理坐标，用 GeoHash 算法把经纬度编码成可以比较的字符串。"

> 💡 面试加分点："你说 ziplist 转 dict/skiplist 的阈值是多少？"——答：Hash 默认 512 个元素且每个元素不超过 64 字节；ZSet 默认 128 个元素且每个元素不超过 64 字节。能说出具体数字说明你真的看过源码。

### Q3: Redis 是单线程的，为什么能这么快？

**面试官想听什么：** 别只说"因为单线程避免了锁竞争"，面试官听腻了。要说出更多维度。

**高分回答：**

"这个问题很多人只答了一个面。我拆开说：

**一、内存操作。** 100ns 级别的内存访问，比 10ms 级别的磁盘快了 10 万倍。这是根本原因，不谈这个就谈单线程是本末倒置。

**二、IO 多路复用。** Redis 用 epoll/kqueue 处理网络请求，单线程可以同时处理上万个连接——来了事件才处理，没事件就空转，不浪费 CPU。

**三、单线程的面试加分点。** 单线程带来三个好处：没有锁竞争、没有上下文切换开销、数据访问天然线程安全。但注意——**Redis 从 6.0 开始引入多线程处理网络 IO**，核心命令执行还是单线程。

**四、数据结构是精心设计的。** 比如 SDS 空间预分配、跳表的 O(logN) 查询、ziplist 的紧凑内存布局——每一处都抠到了极致。

这里有个容易被忽略的点：Redis 单线程模型最大的限制不是性能，而是**不能执行耗时操作**。一条慢查询能卡住后面所有请求。所以生产环境必须监控 slow log，任何操作超过 10ms 就要排查。"

> 💡 面试扣分点："Redis 单线程所以每条命令是原子性的"——对，但更准确地说：单个命令是原子的，Lua 脚本也是原子的，但 pipeline 和事务不是。

### Q4: Redis 的持久化机制有哪些？RDB 和 AOF 怎么选？

**高分回答：**

"两种持久化方案，我按生产侧重点说。

**RDB — 快照方式。** 
- 优点：文件紧凑，恢复快，适合做备份和灾备。
- 缺点：会丢两次快照之间的数据。比如 5 分钟一次快照，第 4 分钟 Redis 挂了，这 4 分钟的数据全丢。
- 触发方式：手动 bgsave、配置自动触发、主从首次同步。

这里有个容易被忽略的点：RDB 是**fork 子进程**执行的，写时复制（COW）机制决定了——如果 fork 后父进程大量写数据，内存占用会翻倍。线上遇到过一次大 instance RDB 导致的内存飙升告警。

**AOF — 追加日志。** 
- 优点：最多丢 1 秒的数据（配置 everysec），几乎不丢。
- 缺点：文件比 RDB 大很多，恢复慢。
- AOF 重写机制：也是 fork 子进程把内存里的数据重写成一个新的 AOF 文件，避免 AOF 无限膨胀。

**生产怎么选？**

我一般这么配：**两者都开**。RDB 做快速恢复和灾备，AOF 保证数据不丢。注意 AOF 的刷盘策略选 everysec——always 太慢（每条写都刷盘），no 又可能丢太多。everysec 是性能和安全的平衡点。"

> 💡 面试官追问："AOF 重写时有新写入怎么办？"——AOF 重写期间父进程继续处理请求，同时把增量写入到一个 buffer，重写完成后把 buffer 的内容追加到新 AOF 文件末尾，再原子替换旧文件。

### Q5: Redis 的过期策略是怎么实现的？已过期的 key 什么时候真正被删除？

**高分回答：**

"过期策略是**惰性删除 + 定期删除**的组合，两个配合才能打满覆盖。

**惰性删除 —** key 被访问时检查是否过期，过期就删掉再返回空。优点是省 CPU——不是所有过期 key 都会被访问，那就省了。

**定期删除 —** 每 100ms 跑一次，随机挑 20 个设置了过期时间的 key，删掉过期的。如果过期比例超过 25%，再抽一轮，最多 16 轮。这里的设计很巧妙——不会一直删下去，每次最多跑 25ms，防止耗死 CPU。

但这里有个坑：**如果大量 key 同时过期，而它们又没被访问，惰性删除不会触发；定期删除一次只能扫 20 个，根本删不完。** 结果就是 Redis 内存里堆满了已过期但没被删的 key。

这就引出了内存淘汰策略——当内存满了，Redis 开始清理。所以**过期删除 ≠ 内存回收**，两者是不同机制在管。

我说句实话：线上出过问题——批量设置的缓存 key 用了相同的过期时间，到点 Redis RT 飙高。后来给过期时间加了随机范围（比如 3600±600 秒），避免缓存雪崩。"

> 💡 能说出"定期删除每 100ms 执行一次 + 随机抽取 20 个 key"这些具体数字，说明真的看过 Redis 源码，面试官会印象深刻。

### Q6: 谈谈 Redis 的穿透、击穿、雪崩。分别怎么解决？

**高分回答：**

"这三个必须分清楚，因为解决方案完全不同。面试答混了就掉分。

**缓存穿透 —** 查一个不存在的数据（比如查 uid=-1），缓存里没有，DB 里也没有，每次请求都打到 DB。
- 解法：布隆过滤器（Bloom Filter）做第一道过滤。或者缓存空值——查询 DB 为空就缓存一个空值，设置短过期时间，比如 30 秒。
- 注意：布隆过滤器有误判率，说"可能不存在"就一定不存在，但说"可能存在"也可能不存在。不能删数据的场景慎用。

**缓存击穿 —** 一个热点 key 刚好过期，大量并发请求同时打到 DB。
- 解法：互斥锁。第一个请求拿锁去查 DB 重建缓存，其他请求等缓存重建好再读。但这个方案会影响吞吐，所以还有个方案——**逻辑过期**，不设置物理过期时间，而是存一个逻辑过期时间字段，线程异步去刷新。

**缓存雪崩 —** 大量 key 同一时间过期，或者 Redis 挂了，大量请求打到 DB。
- 解法：过期时间加随机偏差，防止同时过期。Redis 做高可用（哨兵/集群）。再加上本地缓存兜底（Caffeine 层），Redis 挂了还有本地缓存扛住。

**我的真实做法：**
我一般三层缓存——本地缓存 → Redis 缓存 → DB。Redis 正常时走 Redis，Redis 挂了本地缓存还能扛 3 秒，这 3 秒足够哨兵完成主从切换了。"

> 💡 面试加分点：能说出"布隆过滤器的实现可以用 Guava 的 BloomFilter 或 Redis 的 bit 自建"——"我实际用的是 Redisson 的 RBloomFilter，基于 Redis bit 实现的分布式布隆过滤器。"

### Q7: Redis 分布式锁怎么实现？RedLock 有没有坑？

**高分回答：**

"先说最简单的实现：

```lua
-- 加锁
SET lock_key unique_value NX PX 30000
-- 解锁（用 Lua 保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

核心四点：SET NX 保证互斥、PX 加自动释放防死锁、unique_value 保证只能解锁自己的锁、Lua 脚本保证解锁原子性。

**RedLock** 是 Redis 官方提出的多节点分布式锁算法——向超过半数（N/2+1）的 Redis 节点获取锁，都拿到才算加锁成功。听起来很完美，但我说实话——**实际生产用得不多**。

原因：一是复杂度上来了，得维护多个 Redis 实例；二是 Martin Kleppmann 那篇著名的文章分析过 RedLock 的 bug——GC 暂停或时钟跳跃会导致锁失效，而且这个概率在实际环境中并不低。

我的建议：大部分业务场景 SET NX + Lua 解锁就够了。如果真需要强一致性，不如上 etcd 或 ZooKeeper 的锁——CP 系统的锁天生就比 AP 系统可靠。"

> 💡 面试加分点：能说出 RedLock 至少需要 3 或者 5 个独立节点，以及 Redisson 的 RLock 是对 RedLock 的 Java 实现。还能提一嘴 RedLock 的"时钟依赖"问题，面试官会刮目相看。

### Q8: Redis 主从复制的原理是什么？全量复制和增量复制的过程说清楚。

**高分回答：**

"主从复制分两个阶段：全量复制和增量复制。

**全量复制（初次连接或断连太久）：**
1. Slave 发 PSYNC 请求，带 master_run_id 和 offset
2. Master 发现不匹配，返回 FULLRESYNC，开始 bgsave 生成 RDB
3. 同时 Master 把增量写命令缓存到 replication buffer
4. Slave 把 RDB 加载到内存
5. Master 把 buffer 里的增量命令发给 Slave
6. Slave 执行增量命令，追上 Master 的进度

这里有个容易被忽略的点：**RDB 传输期间 Master 的写压力**。如果你家 Master 上有个 10GB 的实例，bgsave 需要 fork 子进程，一旦 fork 了写入量又大，内存可能翻倍。所以大实例做全量复制时监控要盯紧。

**增量复制（断连后重连）：**
- 用 backlog buffer 实现。Master 维护一个固定大小的环形 buffer（默认 1MB），记录最近执行的写命令。
- Slave 重连后发自己的 offset，如果 offset 还在 backlog 里，直接同步增量；如果 offset 被覆盖了，只能全量复制。
- 所以骨干网带宽足的可以把 backlog 调大到 100MB+，减少全量复制的概率。

我线上一次踩坑：一个 Slave 因为网络抖动重连，刚好 offset 被 backlog 覆盖了，触发了全量复制。全量复制期间 Master CPU 飙高，影响了线上业务。后来把 backlog 从 1MB 调到了 50MB。"

> 💡 面试官追问："主从复制是异步的吗？"——默认是异步。所以 Master 写入后挂了，Slave 还没来得及同步的数据就丢了。从 2.8 开始支持 WAIT 命令，可以等 N 个 Slave 同步完再返回，但会影响写入性能。

### Q9: Redis 哨兵模式是怎么工作的？说清楚主观下线、客观下线、Leader 选举。

**高分回答：**

"哨兵是个独立的守护进程，一般部署奇数个（3 个起步），负责三件事：监控、选主、通知。

**主观下线（SDOWN）：** 一个哨兵发现 Master 超过指定时间（默认 30 秒）没响应，就标记为主观下线。这里是"一个人觉得"。

**客观下线（ODOWN）：** 如果标记了主观下线，这个哨兵会向其他哨兵发询问（is-master-down-by-addr）。当超过半数（quorum）的哨兵都确认 Master 挂了，才标记为客观下线。这里是"大家投票决定"。

**Leader 选举：** 这里的 Leader 不是新的 Master，而是哨兵集群内部选一个"带队"的哨兵。用的是 Raft 算法的简化版——谁先发起投票谁有优势，拿到半数以上的票就当选 Leader。

**选新 Master 的规则：** Leader 从 Slave 里选一个。
1. 淘汰断连的 Slave
2. 淘汰优先级低的（slave-priority 值大的）
3. 淘汰复制进度落后的
4. 最后选 run_id 最小的

有个容易踩的坑：哨兵切换期间 Redis 不可用。如果只有 3 个哨兵，挂一个，剩下两个互发信息就能工作。但如果挂两个（包括 Master），只剩 1 个哨兵就达不到 quorum 的要求，不会做切换。所以哨兵至少要 3 个节点，最多能容忍挂 1 个。"

> 💡 能说出"哨兵切换时客户端也要感知"说明有实战经验——Redisson 客户端内置了哨兵感知逻辑，Jedis 需要自己配 Sentinel 连接池。

### Q10: Redis 集群模式（Cluster）的数据分片是怎么做的？请求重定向流程是什么？

**高分回答：**

"Redis Cluster 用**哈希槽**做数据分片，总共 16384 个槽。

**分配方式：** 每个节点负责一段连续的槽。比如 3 节点集群：Node1 管 0~5460，Node2 管 5461~10922，Node3 管 10923~16383。

**请求路由：**
1. 客户端算 key 的 CRC16，对 16384 取模
2. 如果槽在本节点，直接处理
3. 如果不在，返回 MOVED 重定向 + 目标节点地址
4. 客户端缓存槽位映射表，下次直接访问

**那为什么槽数是 16384 不是 65536？** 这个问题有点意思：16384 个槽用 2KB 就能用位图表示。如果槽太多心跳包会变大，网络开销就上来了。63 字节的心跳包能承载 16384 个槽的信息，如果换成 65536 得 256 字节，翻了好几倍。

**还有个容易被忽略的点：Cluster 不支持多 key 操作**——除非这些 key 在同一个槽。想用 cluster 做多 key 操作必须用 hash tag：把 key 写成 `{user}:name` 和 `{user}:age`，CRC16 只算花括号里的内容，保证它们落到同一个槽。"

> 💡 面试加分点：能说出集群模式对客户端要求高——"Smart Client"（如 JedisCluster、Lettuce）会在本地缓存槽位映射。这是面试官想听到的深度。

### Q11: 跳表（Skiplist）是什么？Redis 为什么用跳表实现 ZSet 而不是红黑树或 B+ 树？

**高分回答：**

"这个问题很经典，能看出你是不是真的理解数据结构。

**跳表就是"带索引的链表"。** 链表查找是 O(n)，太慢。跳表在每 N 个节点上多加一层指针，让你可以"跳着走"。每层数据量是下一层的 1/N，所以跳层查找一次能跳过 N 个节点。

ZSet 的实现：小数据量用 ziplist，元素超过 128 个或者单个元素超过 64 字节就转跳表。跳表中每个节点同时保存 member 和 score 信息。

**为什么不用红黑树？**
Redis 创始人 antirez 说过原因：
1. **跳表实现更简单。** 红黑树的插入删除涉及旋转和变色，bug 率远高于跳表。
2. **范围查询更方便。** 跳表想查 score 在 100 到 200 之间的元素，从顶层往下找起始节点然后沿着底层遍历就行。红黑树虽然也能做范围查询，但实现复杂度高得多。
3. **平均性能都不差。** 跳表插入删除清一色 O(logN)，和红黑树差不多。

**为什么不用 B+ 树？**
B+ 树是为磁盘 IO 优化的——每个节点存很多数据，减少树的高度。Redis 是纯内存操作，不需要通过节点合并来减少磁盘 IO。跳表在内存中更节省空间。

我说句实话：如果你去面试说"Redis 用跳表因为比红黑树实现简单"，面试官不太满意。能补上**范围查询友好 + 纯内存不需要 B+树的磁盘优化**这两点，才是满分。"

> 💡 能画个跳表图就更好了：4 层索引的跳表，从顶层开始找。面试现场用手在桌上比划也行——面试官会欣赏这种表达能力。

### Q12: Redis 的内存淘汰策略有哪些？怎么选？

**高分回答：**

"内存不够用时，Redis 会按配置的策略清理 key，总共 8 种，我分成三类说：

**不淘汰类（1 种）：**
- `noeviction` — 满了直接报错。缓存绝对不能这么配。

**LRU 家族（3 种）：**
- `allkeys-lru` — 整个 key 空间里淘汰最近最少用的。最常用，大部分业务场景的最佳选择。
- `volatile-lru` — 只在设置了过期时间的 key 里淘汰。如果你有些 key 不想被淘汰，就用这个。
- `allkeys-lfu` / `volatile-lfu` — 淘汰使用频率最低的，适合访问模式有冷热区分的场景。

**TTL 家族（2 种）：**
- `volatile-ttl` — 淘汰剩余存活时间最短的。说实话，业务上用得少。
- `volatile-random` / `allkeys-random` — 随机淘汰。很少用。

**生产建议：**
80% 的场景 `allkeys-lru` 就够了。如果做热数据缓存比如排行榜、访问计数，用 `allkeys-lfu`。如果你在 Redis 里存了少量不能丢的关键数据，用 `volatile-lru` 并给这些 key 别设过期时间。

这里有个容易被忽略的点：**Redis 的 LRU 不是严格的 LRU。** 它是近似 LRU——内存不够时随机采样一批 key（默认 5 个），淘汰最老的。这是为了省内存，严格 LRU 得维护一个全局链表，内存开销太大。"

> 💡 面试官问："为什么 Redis 不用严格 LRU？"——答：严格 LRU 需要双向链表维护访问顺序，每个 key 被访问都要 O(1) 更新链表，大量 key 的内存开销太大。近似 LRU 牺牲一点精度换来内存节省和 CPU 省。Redis 官网说近似 LRU 和严格 LRU 在实际场景中差距很小。

### Q13: 你怎么用 Redis 设计一个实时的排行榜功能（比如游戏积分榜）？

**高分回答：**

"这个场景用 ZSet 做，代码很简单但想做好有几个关键设计。

**数据结构：**
```bash
# 玩家 ID 10086 加了 50 分
ZINCRBY game:leaderboard:20260521 50 player:10086

# 查询 Top 10
ZREVRANGE game:leaderboard:20260521 0 9 WITHSCORES

# 查询某玩家的排名
ZREVANK game:leaderboard:20260521 player:10086
```

ZINCRBY 是原子的——并发加分不用加锁。ZREVRANGE + WITHSCORES 拿到的就是实时排行榜。

**几个关键设计点：**

**按天分 key** — `game:leaderboard:20260521` 每天一个 key，第二天自动创建新 key。这样既能看今日排行，也能保留历史数据，而且单个 ZSet 不会无限膨胀。

**同分怎么排名？** 这是隐藏的坑。ZSet 同分时按 member 字典序排。如果想同分时先到的排前面，需要把时间戳编码到 score 里。比如分数占整数部分，时间戳用巨大的数减去当前时间戳做小数部分："100分后到"的 score = 100.99986，"100分先到"的 score = 100.99987，这样同分时先到的排前面。

**数据一致性：** 排行榜数据最好最终一致就行，别用事务。玩家看到的数据延迟几秒不影响体验。所以流程上可以：业务先扣分写入 DB → 异步更新 Redis 排行榜。Redis 挂了不影响核心业务，重启后从 DB 重建就行。"

> 💡 面试官追问："ZSet 在排行榜场景最大能支持多少元素？"——实测单个 ZSet 存几百万个元素没问题，ZRANK 还是 O(logN)。但要注意内存占用——每个 member 约 40+ 字节，100 万玩家约 50MB。

### Q14: 线上 Redis 突然变慢了，你怎么排查？

**面试官想听什么：** 面试官想看你有没有真正的排障体系和思路，不是猜原因。

**高分回答：**

"我有一整套排查流程，按优先级排：

**第一，看 slowlog。** `SLOWLOG GET 10` 看最近的慢查询。如果发现某个命令经常出现在 slowlog 里，那就是罪魁祸首。常见的是 KEYS *、HGETALL 大 Hash、大量 key 同时过期。

**第二，看 Redis 的 latency。** `redis-cli --intrinsic-latency 100` 测本机延迟。如果延迟大但 Redis 本身不慢，说明问题在机器层面——网络、内存带宽、CPU 争抢。

**第三，看 info 里的关键指标。**
- `instantaneous_ops_per_sec` — 突然飙高说明请求量暴涨
- `used_memory_rss` — 如果远大于 used_memory，说明内存碎片率高
- `connected_clients` — 是否超过预期
- `rejected_connections` — Redis 默认 maxclients 是 10000，超了会拒绝

**第四，看 fork 耗时。** `latest_fork_usec` 表示最近一次 fork 花了多久。如果这里显示几秒甚至几十秒——说明 RDB 或者 AOF 重写把进程卡住了。这是生产环境非常常见的变慢原因。

**第五，看机器层面。** 很多时候不是 Redis 自己的问题。用 `top` 看 CPU 是否有人抢——虚拟机/容器场景经常发生。用 `iostat` 看磁盘 IO——AOF 刷盘如果碰到磁盘 IO 高也会慢。

**踩过一个真实坑：** 有次 Redis 突然从 1ms 涨到 200ms，一查是 swap 开启了——内存不够被系统换到了磁盘。Redis 是内存数据库，一个缺页中断就是几十毫秒。解决方式：关 swap 或者限制 swap 使用倾向。"

> 💡 补充：Redis 6.0+ 可以配 `latency-monitor-threshold` 自动记录慢操作到日志，上线就开这个配置，别等出问题再排查。

### Q15（AI 应用开发）: 用 Python 实现一个 Redis 缓存 + AI 模型调用的 Demo：先查缓存，缓存命中直接返回，缓存没命中调 AI 模型并把结果写缓存。

**高分回答：**

```python
import redis
import time
import json

# 假设这是一个 AI 文本摘要模型的调用接口
def call_ai_summarize(text: str) -> str:
    """模拟调用 AI 模型生成摘要"""
    time.sleep(1)  # 模拟 AI 推理耗时
    return f"[AI摘要] {text[:50]}..."

def get_summary(text: str, ttl: int = 3600) -> str:
    """
    带缓存层的 AI 调用
    - 缓存 key 用文本的 MD5/SHA1 避免长 key
    - 缓存命中直接返回
    - 未命中调 AI 模型，结果写入缓存
    """
    import hashlib
    r = redis.Redis(host="localhost", port=6379, decode_responses=True)
    text_hash = hashlib.sha256(text.encode()).hexdigest()
    cache_key = f"ai:summary:{text_hash[:16]}"

    # 1. 先查缓存
    cached = r.get(cache_key)
    if cached:
        print("[缓存命中]")
        return cached

    # 2. 缓存未命中，调 AI 模型
    print("[缓存未命中] 调用 AI 模型...")
    result = call_ai_summarize(text)

    # 3. 写缓存 + 设置过期时间
    r.setex(cache_key, ttl, result)
    return result

# 使用
text = "Redis 是一个开源的 in-memory 数据结构存储系统..."
result = get_summary(text, ttl=1800)
print(f"结果: {result}")
```

> 💡 面试加分点：这段代码面试官看完通常会追问——"如果高并发下缓存没命中，所有请求都打到 AI 模型怎么办？" 答案：加分布式锁或使用互斥锁，第一个请求调 AI，其他请求等待。可以用 Redis 分布式锁实现：  
> ```python
> lock_key = f"ai:summary:lock:{text_hash[:16]}"
> if r.setnx(lock_key, "1"):  # 拿到锁
>     r.expire(lock_key, 10)  # 锁最多 10 秒
>     result = call_ai_summarize(text)
>     r.setex(cache_key, ttl, result)
>     r.delete(lock_key)
> else:
>     time.sleep(0.1)  # 等锁释放
>     return r.get(cache_key)  # 重试获取
> ```
