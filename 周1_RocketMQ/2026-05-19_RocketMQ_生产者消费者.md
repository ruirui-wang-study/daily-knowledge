### Q1（入门）: RocketMQ Producer 有哪几种发送方式？分别适用于什么场景？

**A1：**

三种发送方式：

| 方式 | 描述 | 适用场景 | 性能 |
|------|------|---------|------|
| **同步发送** | 发消息后等 Broker ACK | 重要业务（订单、支付） | 低（需等待） |
| **异步发送** | 发消息后回调通知结果 | 对延迟敏感但需可靠 | 中 |
| **单向发送** | 发完即忘，不关心结果 | 日志、监控（可容忍少量丢失） | 最高 |

```java
// 同步发送（可靠，最常用）
SendResult result = producer.send(message);

// 异步发送（高吞吐）
producer.send(message, new SendCallback() {
    @Override
    public void onSuccess(SendResult result) { }
    @Override
    public void onException(Throwable e) { }
});

// 单向发送（最快）
producer.sendOneway(message);
```

### Q2（入门）: Producer 的重试机制是什么样的？什么情况下会重试？重试可能导致什么问题？

**A2：**

默认配置：

- **重试次数：** 默认 2 次（总共发送 3 次）
- **重试间隔：** 默认 100ms
- **触发条件：** 网络异常、Broker 返回错误（如 `SLAVE_NOT_AVAILABLE`）

```properties
# Producer 重试配置
retryTimesWhenSendFailed=2         # 同步发送重试次数
retryTimesWhenSendAsyncFailed=2     # 异步发送重试次数
retryAnotherBrokerWhenNotStoreOK=true  # 存储失败时换 Broker 重试
```

**重试可能导致的坑：**
1. **消息重复：** 网络超时但 Broker 实际已写入 -> 重试导致重复消息
2. **消息乱序：** 重试时可能落到不同的 Queue 或 Broker -> 顺序消息必须设置 `setQueue`
3. **雪崩：** 大量重试压垮 Broker -> 建议开启退避策略

### Q3（基础）: Producer 怎么发顺序消息？实现原理是什么？

**A3：**

核心：**同一业务 key 的消息进入同一个 Queue**。

```java
// 关键：实现 MessageQueueSelector
producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        // arg 是业务 ID（比如订单号），保证同一个订单进同一个 Queue
        int index = Math.abs(arg.hashCode()) % mqs.size();
        return mqs.get(index);
    }
}, orderId);
```

**面试加分点：** 为什么用 `hashCode % Queue数量` 而不是直接指定 Queue？

> 这样即使 Queue 数量变化（扩容），hash 分布也会重新均衡。但如果直接指定 Queue，扩容后消息会乱序。

**注意坑：** 顺序消息不能用 `setRetryTimesWhenSendFailed`，因为重试后可能落到不同 Queue，破坏顺序。

### Q4（基础）: Consumer 有哪几种模式？集群消费和广播消费的区别？

**A4：**

两种消费模式：

```java
// 集群消费（默认）：每条消息只被 Group 内的一个实例消费
consumer.setMessageModel(MessageModel.CLUSTERING);

// 广播消费：每条消息被所有实例消费
consumer.setMessageModel(MessageModel.BROADCASTING);
```

**区别：**

| 维度 | 集群消费 | 广播消费 |
|------|---------|---------|
| 消息归属 | Group 内共享 | 每个实例各一份 |
| Offset 管理 | Broker 端管理 | 本地文件管理 |
| 适用场景 | 业务处理（每个消息处理一次） | 全局通知（每个实例都要处理） |
| 容错 | 某个实例挂了不影响其他 | 实例挂了会丢消息（Offset 在本地） |

### Q5（基础）: Concurrently 和 Orderly 两种 MessageListener 有什么本质区别？

**A5：**

```java
// 并发消费（默认）
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    // 多个 Queue 的消息可以并发处理
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});

// 顺序消费
consumer.registerMessageListener((MessageListenerOrderly) (msgs, context) -> {
    // 同一个 Queue 的消息串行处理
    return ConsumeOrderlyStatus.SUCCESS;
});
```

| 维度 | Concurrently | Orderly |
|------|-------------|--------|
| 消费速度 | 高（并发） | 低（串行） |
| 消息顺序 | 不保证 | 保证 |
| 消费失败处理 | 自动重试（默认 16 次） | 挂起，不断重试 |
| 内部实现 | 线程池并发处理 | 每个 Queue 一个锁，加锁处理 |

### Q6（进阶）: Consumer 的消费进度（Offset）是怎么管理和存储的？

**A6：**

**集群消费模式：**
- Offset 存储在 Broker 端，保存在系统 Topic `__consumer_offsets`
- Consumer 定期（默认 5s）上报 Offset
- Broker 重启后 Offset 不丢失

```java
// 手动设置 Offset 存储策略（一般不配置）
consumer.setOffsetStore(new RemoteBrokerOffsetStore(...));
```

**广播消费模式：**
- Offset 存储在 Consumer 本地文件
- 路径：`~/.rocketmq_offsets/{clientId}/{group}/{topic}/offset`
- **问题：** Consumer 本地文件损坏或机器更换会丢 Offset

**手动提交 Offset：**

```java
// 消费成功
return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;  // 自动提交

// 如果使用 PullConsumer，需要手动管理
pullConsumer.updateConsumeOffset(store, queue, offset);
```

### Q7（进阶）: Consumer 怎么处理消费失败？重试队列和死信队列是什么？

**A7：**

```java
// 消费失败，告诉 Broker 稍后重试
return ConsumeConcurrentlyStatus.RECONSUME_LATER;
```

**重试流程：**
1. 第一次失败 -> Broker 将消息放入**重试队列**（Topic 名：`%RETRY%{consumerGroup}`）
2. 重试间隔逐次增加：10s → 30s → 1m → 2m → … → 2h（共 16 个级别）
3. 重试 16 次都失败 -> 进入**死信队列**（Topic 名：`%DLQ%{consumerGroup}`）
4. 死信队列的消息需要人工处理（或单独写一个死信 Consumer）

**重试级别（时间间隔）：**

```
第1次: +10s    第5次: +3m     第9次: +20m   第13次: +1h
第2次: +30s    第6次: +4m     第10次: +30m  第14次: +2h
第3次: +1m     第7次: +5m     第11次: +40m  第15次: +2h
第4次: +2m     第8次: +6m     第12次: +50m  第16次: +2h
```

**面试加分点：** 死信队列监控很重要。推荐做法：单独建一个 Consumer 订阅 `%DLQ%` Topic，告警通知 + 自动重投或人工介入。

### Q8（进阶）: RocketMQ 怎么处理消息的幂等消费？有哪几种实现方案？

**A8：**

为什么不天生幂等：RocketMQ 没有 Kafka 的"Exactly Once"语义，重试/Rebalance/网络抖动都会导致**至少一次**消费。

**幂等方案（从简单到可靠）：**

| 方案 | 实现 | 优缺点 |
|-----|------|-------|
| 1. 数据库唯一索引 | 消费前 INSERT，冲突则跳过 | 简单可靠，依赖数据库 |
| 2. Redis 去重 | SET NX + 过期时间 | 高性能，但 Redis 挂了可能丢 |
| 3. 业务幂等设计 | "如果已处理则忽略" | 最优雅，但需要业务改造 |

```java
// 方案1：数据库唯一索引（推荐）
@Transactional
public void processOrderMessage(OrderMessage msg) {
    // 利用数据库唯一索引去重
    try {
        consumeRecordMapper.insert(new ConsumeRecord(msg.getMsgId()));
        // 执行真正业务逻辑
        orderService.process(msg);
    } catch (DuplicateKeyException e) {
        // 已经处理过，跳过
        log.warn("重复消息，跳过: {}", msg.getMsgId());
    }
}
```

### Q9（进阶）: Producer 端怎么保证不丢消息？说清楚从业务到 Broker 的全链路。

**A9：**

**全链路保不丢 checklist：**

| 阶段 | 措施 | 实现方式 |
|------|------|---------|
| **1. 业务生成** | 业务日志落盘 | 数据库记录消息状态 |
| **2. 发送** | 同步发送 + 重试 | `producer.send(msg)` + 3 次重试 |
| **3. Broker 存储** | 同步刷盘 | `flushDiskType=SYNC_FLUSH` |
| **4. Broker 复制** | 同步复制 | `brokerRole=SYNC_MASTER` |
| **5. 消费** | 手动 ACK | 消费成功再 `CONSUME_SUCCESS` |
| **6. 兜底** | 定期巡检 + 补偿 | 比对业务库和消息库的差异 |

**兜底方案示例（补偿机制）：**

```java
@Component
public class MessageCompensator {
    // 每 5 分钟扫描未确认的消息
    @Scheduled(fixedDelay = 300000)
    public void compensate() {
        List<BizMessage> pending = messageMapper.selectPending(5, TimeUnit.MINUTES);
        for (BizMessage msg : pending) {
            // 检查这条消息对应的业务是否已处理
            if (!bizService.isProcessed(msg.getBizId())) {
                // 重新发送
                producer.send(msg.toRocketMessage());
            }
            // 如果能查到业务已处理但消息状态还是 pending
            // 说明消息实际已消费但没回写状态，把数据库状态更新
        }
    }
}
```

**面试加分点：** 最推荐的方案不是全链路同步，而是"同步发送 + 异步补偿"——大部分消息 10ms 内搞定，极少数丢失的靠补偿兜底。

### Q10（源码级）: RocketMQ 的消息过滤机制有哪些？Tag 过滤和 SQL 过滤的区别？

**A10：**

**Tag 过滤（Broker 端过滤）：**
- 消息发送时设置 Tag，消费者订阅特定 Tag
- Broker 端直接过滤，不匹配的消息不推给 Consumer

```java
// Producer 设置 Tag
msg.setTags("order_created");

// Consumer 订阅特定 Tag
consumer.subscribe("TopicOrder", "order_created || order_paid");
```

**SQL 过滤（Broker 端过滤，需配置）：**
- 支持属性表达式的过滤
- 需要 Broker 开启配置 `enablePropertyFilter=true`

```java
// Producer 设置属性
msg.putUserProperty("region", "china");
msg.putUserProperty("amount", "100");

// Consumer 用 SQL 表达式过滤
consumer.subscribe("TopicOrder", MessageSelector.bySql(
    "region = 'china' AND amount > 50"
));
```

| 维度 | Tag 过滤 | SQL 过滤 |
|------|---------|---------|
| 性能 | 高（基于 hash 比较） | 中（需要解析表达式） |
| 灵活性 | 低（只能按 Tag） | 高（支持复杂条件） |
| 配置要求 | 不需要 | 需开启 `enablePropertyFilter=true` |
| 推荐 | 大部分场景 | Tag + 业务侧二次过滤 |

### Q11（源码级）: RocketMQ Consumer 在 Rebalance 期间发生了什么？怎么减少 Rebalance 的影响？

**A11：**

**Rebalance 流程：**
1. **触发：** Consumer 上下线 / Queue 数量变化
2. **释放：** 原持有 Queue 的 Consumer 暂停消费
3. **分配：** 所有 Consumer 重新分配 Queue
4. **接管：** 新分配的 Consumer 开始消费

**影响：**
- **重复消费：** 释放方还没提交 Offset -> 接管方会重复消费（约几秒到几十秒）
- **暂停：** 部分 Queue 的消费会短暂中断（毫秒级）

**减少影响的策略：**

```java
// 1. 设置 Consumer 的心跳超时（默认 120s，减少误判）
consumer.setConsumerTimeoutMillisWhenSuspend(60000);

// 2. 消费端做幂等（必须）
// 3. 减少 Consumer 实例的频繁上下线
//    - Web 应用每次部署都会造成 Rebalance
//    - 推荐用 K8s 的 PreStop Hook，先摘流量再下线

// 4. 调整 Rebalance 的等待时间
consumer.setAwaitTerminationMillisWhenShutdown(5000);
```

### Q14（综合）: 描述一次你用 RocketMQ 解决过的实际问题。

**A14：**

**问题背景：** 订单系统每分钟高峰 QPS 约 5000，大量调用库存/支付/物流服务。最初同步调用导致：
- 下单接口 RT 从 50ms 飙升到 1.2s
- 库存服务被突发的流量打挂过两次
- 一个服务故障牵连锁影响到整个链路

**解决方案：**

```java
// Before: 同步调三个服务
@Transactional
public void createOrder(OrderDTO dto) {
    orderDao.insert(dto);
    stockClient.deduct(dto.getSkuId(), dto.getCount());  // 同步
    paymentClient.charge(dto.getUserId(), dto.getAmount()); // 同步  
    logisticsClient.create(dto.getOrderId());  // 同步
}

// After: 消息队列异步解耦
public void createOrder(OrderDTO dto) {
    orderDao.insert(dto);
    // 发三个消息，各服务异步处理
    producer.send(buildOrderCreatedMsg(dto));
    producer.send(buildPayMsg(dto));
    producer.send(buildLogisticsMsg(dto));
}
```

**效果：**
- 下单接口 RT 从 1.2s 降到 80ms
- 库存服务挂了一次，消息积压，恢复后自动追平（零数据丢失）
- 新加通知服务只需要新增 Consumer，不改原有代码

**面试加分点：** 这个案例的核心价值是展示了 RocketMQ 的"削峰填谷"和"服务解耦"——面试官希望通过具体案例看你的架构思维，不是死记概念。

### Q15（AI 应用开发）: 用 Python + RocketMQ 实现一个简单的"订单超时自动取消"功能。

**A15：**

```python
# 利用 RocketMQ 的延迟消息实现超时取消

from rocketmq.client import Producer, PushConsumer, Message
import json, time

class OrderTimeoutHandler:
    """订单超时自动取消"""
    
    def __init__(self):
        self.producer = Producer("GID-order-producer")
        self.producer.set_name_server_address("127.0.0.1:9876")
        self.producer.start()
    
    def create_order_with_timeout(self, order_id: str, user_id: str, amount: float):
        """创建订单并发送超时检测消息（30分钟后）"""
        # 1. 订单落库
        self._save_order(order_id, user_id, amount, status="PENDING_PAYMENT")
        
        # 2. 发送延迟消息（30分钟 = delay level 14）
        msg = Message("order_timeout")
        msg.set_keys(order_id)
        msg.set_body(json.dumps({
            "order_id": order_id,
            "user_id": user_id,
            "created_at": time.time()
        }).encode("utf-8"))
        msg.set_delay_time_level(14)  # level 14 = 30分钟
        
        result = self.producer.send(msg)
        print(f"超时检测消息已发送, msgId: {result.msg_id}")
    
    def _save_order(self, order_id, user_id, amount, status):
        """模拟订单入库"""
        print(f"[DB] 订单 {order_id} 已创建, 金额: {amount}, 状态: {status}")

# 超时取消消费者
def start_timeout_consumer():
    consumer = PushConsumer("GID-order-timeout-consumer")
    consumer.set_name_server_address("127.0.0.1:9876")
    consumer.subscribe("order_timeout", "*")
    
    def on_timeout(msg):
        data = json.loads(msg.body.decode("utf-8"))
        order_id = data["order_id"]
        
        # 检查订单是否已支付
        if not is_order_paid(order_id):
            cancel_order(order_id)
            print(f"[超时取消] 订单 {order_id} 未支付，已自动取消")
        else:
            print(f"[跳过] 订单 {order_id} 已支付，无需取消")
        return 0  # CONSUME_SUCCESS
    
    consumer.register_message_callback(on_timeout)
    consumer.start()
    return consumer

def is_order_paid(order_id):
    """模拟查询订单支付状态"""
    return False  # 默认未支付

def cancel_order(order_id):
    """模拟取消订单"""
    print(f"[DB] 订单 {order_id} 状态更新为 CANCELLED")

# 测试
if __name__ == "__main__":
    consumer = start_timeout_consumer()
    handler = OrderTimeoutHandler()
    
    # 模拟创建2个订单
    handler.create_order_with_timeout("ORD001", "user_01", 99.9)
    handler.create_order_with_timeout("ORD002", "user_01", 199.0)
    
    time.sleep(5)
    print("\nDemo 结束（实际 RocketMQ 会在 30 分钟后触发超时）")
```
