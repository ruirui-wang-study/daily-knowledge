## 主题：RocketMQ 消息存储与高可用（承前）

> 之前聊了生产者和消费者的使用，今天深入 RocketMQ 的存储机制和高可用设计——这些是面试中区分"会用"和"真懂"的考点。

### Q1（入门）: RocketMQ 的存储文件有哪些？各自的作用是什么？

**A1：**

三个核心存储文件（都在 `${storeRoot}` 目录）：

| 文件 | 作用 | 特点 |
|------|------|------|
| **CommitLog** | 消息的物理存储 | 所有 Topic 共享，顺序写 |
| **ConsumeQueue** | 消息的逻辑索引 | 每个 Queue 一个，定长记录 |
| **IndexFile** | 消息的 key 索引 | 按 key 查消息时用 |

辅助文件：

```bash
$storeRoot/
├── commitlog/           # CommitLog 文件（默认 1GB 一个）
│   ├── 00000000000000000000
│   └── 000000000001073741824
├── consumequeue/        # ConsumeQueue 文件（每个 Queue 30000 条一个）
│   └── TopicA/
│       └── 0/
│           └── 00000000000000000000
├── index/               # IndexFile（按消息 key 查询用）
└── config/              # 配置、消费进度、订阅关系
    ├── consumerOffset.json
    ├── subscriptionGroup.json
    └── topics.json
```

### Q2（基础）: 为什么 RocketMQ 要设计成"CommitLog + ConsumeQueue"双层结构？

**A2：**

核心原因：**顺序写 + 快速读取的平衡**。

```
如果只有一个 CommitLog（不建索引）：
  写入：快（顺序写）✅
  读取：慢（需要扫描全文件）❌

如果每个 Queue 单独写文件（Kafka 模式）：
  读取：快 ✅
  写入：大量随机写，硬盘吃不消 ❌

RocketMQ 的方案（CommitLog + ConsumeQueue）：
  写入：所有消息顺序写 CommitLog（一次写）✅
  读取：从 ConsumeQueue 定位偏移量，CommitLog 随机读 ✅
```

**性能数据：**
- 顺序写磁盘：约 600MB/s（SATA SSD）
- 随机写磁盘：约 50MB/s
- ConsumeQueue 每条记录仅 20 字节（8B Offset + 4B Size + 8B TagHash），10万条消息才 2MB

### Q3（基础）: 消息刷盘机制有哪些？同步刷盘和异步刷盘的区别？

**A3：**

```properties
# Broker 配置
flushDiskType=SYNC_FLUSH  # 或 ASYNC_FLUSH（默认）
```

**同步刷盘：**
- Producer 发消息 -> Broker 写入内存 PageCache -> 立即刷到磁盘 -> 返回 ACK
- 保证不丢 ✅，性能较低（约降低 30-50%）

**异步刷盘：**
- Producer 发消息 -> Broker 写入内存 PageCache -> 返回 ACK -> 后台线程定期刷盘
- 高性能 ✅，断电可能丢最后几秒的数据 ❌

```java
// 代码中发送消息，这两种模式对 Producer 是透明的
producer.send(msg); // 刷盘策略由 Broker 配置决定
```

**面试加分点：** PageCache + 异步刷盘是大多数场景的推荐配置。同步刷盘通常只在对数据安全要求极高的场景（金融交易）。

### Q4（基础）: RocketMQ 的高可用是怎么实现的？Master-Slave 架构怎么工作的？

**A4：**

RocketMQ 的 Master-Slave 架构：

```
         ┌──────────────────┐
         │   NameServer      │
         └────────┬─────────┘
                  │
     ┌────────────┼────────────┐
     │            │            │
┌────▼────┐ ┌────▼────┐ ┌────▼────┐
│ Master  │ │  Slave  │ │  Slave  │  (Broker 集群)
│ BrokerA │ │ BrokerA │ │ BrokerA │
└─────────┘ └─────────┘ └─────────┘
     │            │            │
     └────────────┴────────────┘
              共享存储（或 Dledger）
```

**Broker 角色配置：**

```properties
# Master 配置
brokerId=0
brokerRole=SYNC_MASTER    # 同步复制

# Slave 配置  
brokerId=1                # 非 0 即为 Slave
brokerRole=SLAVE
```

**读写分离：**
- **写：** 只能写到 Master
- **读：** Master 优先，Master 挂了读 Slave

### Q5（进阶）: 同步复制和异步复制有什么区别？Dledger 又是什么？

**A5：**

```properties
# 同步复制
brokerRole=SYNC_MASTER
# 要求：Master + 至少一个 Slave 都写入成功才返回 ACK

# 异步复制（默认）
brokerRole=ASYNC_MASTER
# Master 写入成功就返回 ACK，异步复制到 Slave
```

| 维度 | 异步复制 | 同步复制 | Dledger |
|------|---------|---------|---------|
| 性能 | 高 | 中 | 低 |
| 数据安全 | Master 挂了可能丢 | 不丢 | 不丢（Raft 协议）|
| 自动选主 | ❌ 需手动切换 | ❌ 需手动切换 | ✅ 自动选主 |
| 集群要求 | 1M + 0~N S | 1M + 1~N S | 至少 3 节点 |

**Dledger（推荐的生产方案）：**
- 基于 Raft 协议实现自动选主
- 至少 3 个节点，过半写入成功才算成功
- Master 挂了自动选新 Master
- 不需要人工介入切换

### Q6（进阶）: Master 挂了怎么办？说一下 RocketMQ 的主从切换方案。

**A6：**

**没有 Dledger 时的切换（手动）：**

```bash
# 1. 检查哪个 Slave 的数据最新
# 2. 修改 Slave 配置
brokerId=0          # 改成 0
brokerRole=SYNC_MASTER  # 改成 Master

# 3. 重启 Slave（变成新 Master）
# 4. 修改 Producer/Consumer 配置指向新 Master
# 5. 修复原 Master，重新加入作为 Slave
```

**有 Dledger 时的切换（自动）：**

```
3 个 Dledger 节点：
Node-A (Leader/Master) → 挂了
Node-B (Follower) → 自动成为新 Leader（约 3-5 秒）
Node-C (Follower) → 继续当 Follower
Node-A (恢复) → 加入集群成为 Follower
```

**面试加分点：** 手动切换在生产中很危险——数据不一致是最常见的坑。**生产环境强烈建议用 Dledger。**

### Q7（进阶）: RocketMQ 的存储性能瓶颈有哪些？怎么优化？

**A7：**

| 瓶颈 | 原因 | 优化方案 |
|------|------|---------|
| 磁盘 IO | 消息量太大，磁盘写不过来 | SSD + RAID 10 |
| PageCache 不足 | 内存不够缓存大量消息 | 增大 JVM 内存 |
| CommitLog 文件锁 | 文件映射性能下降 | 调整 mappedFileSize |
| 刷盘阻塞 | 同步刷盘影响写入 | 改异步刷盘 + UPS 保护 |

**优化配置：**

```properties
# 内存相关
maxMessageSize=4194304           # 消息最大 4MB
mappedFileSizeCommitLog=1073741824  # CommitLog 文件 1GB
messageIndexEnable=false         # 不用 IndexFile 可关闭

# 刷盘相关
flushCommitLogTimed=true         # 定时刷盘
flushIntervalCommitLog=500       # 每 500ms 刷一次

# 线程相关
sendMessageThreadPoolNums=16     # 发送线程数
pullMessageThreadPoolNums=16     # 拉取线程数
```

### Q8（源码级）: RocketMQ 的零拷贝技术是怎么实现的？mmap 和 sendfile？

**A8：**

RocketMQ 在磁盘读写时使用了**零拷贝（Zero-Copy）技术**。

**写入时（mmap）：**
- 消息写入 CommitLog 时，使用 `MappedByteBuffer`（mmap 的内存映射）
- 数据直接从用户态写入内核态 PageCache，**不需要从内核拷贝到用户空间再拷回去**
- 传统 I/O：磁盘 → 内核缓冲区 → 用户缓冲区 → 内核套接字缓冲区 → 网卡（4 次拷贝）
- mmap：磁盘 → 内核缓冲区 → 用户共享映射 → ...（2 次拷贝）

**读取时（sendfile + 或 mmap）：**
- Consumer 拉取消息时，CommitLog 通过 mmap 直接读取
- ConsumeQueue 内容很小，常驻内存

```java
// RocketMQ 源码中的 mmap 使用
// MappedFile.java
this.mappedByteBuffer = fileChannel.map(
    FileChannel.MapMode.READ_WRITE,
    0,
    fileSize
);
```

**面试加分点：** mmap 有一个坑——一旦映射的文件损坏，JVM 会直接 Crash（`SIGBUS` 信号），无法捕获。所以 RocketMQ 在写入时加了 write-ahead 保护。

### Q9（源码级）: RocketMQ 的过期文件删除机制是怎么实现的？

**A9：**

RocketMQ 不会立即删除已消费的消息，而是**定期清理过期的 CommitLog 文件**。

```properties
# 文件保留配置
fileReservedTime=72           # 文件保留 72 小时（默认）
deleteWhen=04                 # 每天凌晨 4 点清理
diskMaxUsedSpaceRatio=75      # 磁盘使用超 75% 触发清理
deleteCommitLogFilesInterval=100  # 每次删除间隔 100ms
```

**清理逻辑：**
1. 检查文件的最后修改时间是否超过 `fileReservedTime`
2. 检查该文件对应的 ConsumeQueue 是否**所有 Consumer Group 都已消费完毕**
3. 两个条件都满足，删除
4. 如果磁盘使用超过阈值，**不管消费没消费，强制删除最老的文件**

**面试加分点：** 
> 这是很多人的知识盲区——RocketMQ 的存储是**"消息文件级别"**而不是"消息级别"的。如果消费速度慢，老文件一直被锁定不会被删除，最终可能撑爆磁盘。

### Q10（源码级）: RocketMQ 怎么保证写入性能不受随机读的影响？

**A10：**

核心设计思想：**写入路径和读取路径分离。**

```
写入路径：
  Producer → CommitLog（顺序写）→ 成功返回
  │ 这个过程只写一个文件，不需要关心 ConsumeQueue

读取路径：
  Consumer → ConsumeQueue（内存/缓存）→ CommitLog（随机读）
  │ ConsumeQueue 极小，可全缓存；CommitLog 读是异步的

刷盘路径（后台异步）：
  CommitLog 写入 → 异步构建 ConsumeQueue
  │ 写入 CommitLog 主线程就返回了，ConsumeQueue 由后台线程构建
```

**为什么 RocketMQ 写入不受读取影响：**
- 写入是**顺序写**（CommitLog），即使有大量读取也不影响写入性能
- ConsumeQueue 的构建是**异步的**，不阻塞写入
- PageCache 中同时缓存了 CommitLog（写缓存）和 ConsumeQueue（读缓存）

### Q11（源码级）: RocketMQ 有哪些消峰手段？限流和背压机制？

**A11：**

**Broker 端：**

```properties
# 1. 写入限流
osPageCacheBusyTimeOutMills=1000  # PageCache 忙超 1s 就限流
transientStorePoolEnable=true     # 启用堆外缓存池（写缓冲）

# 2. 发送限速
maxTransferCountOnMessageInMemory=1000  # 一次拉取最多 1000 条
```

**Consumer 端：**

```java
// 1. 拉取限流（超过阈值暂停拉取）
consumer.setPullThresholdForQueue(1000);    // 每个 Queue 最多积压 1000 条
consumer.setPullThresholdForTopic(10000);   // 每个 Topic 最多积压 10000 条

// 2. 消费限流（消费速率控制）
consumer.setConsumeThreadMin(10);
consumer.setConsumeThreadMax(40);

// 3. 消费超时（超时消息会被投递到重试队列）
consumer.setConsumeTimeout(15, TimeUnit.MINUTES);
```

**背压机制：**
```
Producer 生产快
    ↓
Broker CommitLog 写入（快，顺序写）
    ↓
ConsumeQueue 构建（快，异步）
    ↓
Consumer 消费（可能慢）
    ↓
Consumer 的 pullThresholdForQueue 积压到达阈值
    ↓
Consumer 暂停拉取，消费积压消化后再拉
    ↓
Broker CommitLog 继续写入（不受影响）
    ↓
最终：积压在 Broker，不反压 Producer
```

**面试加分点：** RocketMQ 采用的是**Consumer 端背压**，而不是 Producer 端背压。Producer 感知不到消费速度慢。如果积压到磁盘快满，Broker 会触发强制删除，可能导致丢消息。

### Q13（综合）: 说说你用 RocketMQ 踩过的一个存储相关的坑。

**A13：**

**经典坑：磁盘写满导致 Broker 挂掉**

现象：线上 Broker 突然挂了，错误日志 `Not enough space, maybe full of commitlog`

原因：
- 消息生产速度很快（10万/s），消费速度跟不上
- 默认 `fileReservedTime=72h`，老文件一直没被删除
- 磁盘满了，Broker 直接宕机

解决：
1. 扩容磁盘（从 500GB 到 2TB）
2. 调整文件保留时间：`fileReservedTime=12`（保留 12 小时）
3. 开启磁盘保护：`diskMaxUsedSpaceRatio=75`（使用超过 75% 清理老文件）
4. 增加消费者实例数，加速积压消费

**教训：** RocketMQ 的存储是"文件级别"的，不是"消息级别"。消费慢了文件就删不掉。建议加监控报警：磁盘使用 > 70% 就告警。

### Q14（综合）: RocketMQ 和其他 MQ 对比总结。

**A14：**

| 特性 | RocketMQ | Kafka | RabbitMQ |
|------|----------|-------|----------|
| 开发语言 | Java | Scala/Java | Erlang |
| 消息可靠性 | 高（同步复制+刷盘） | 中（异步复制） | 高 |
| 吞吐量 | 10万/s | 100万/s | 万级/s |
| 消息延迟 | 毫秒级 | 毫秒级 | 微秒级 |
| 顺序消息 | ✅ 分区有序 | ✅ 分区有序 | ❌ 基本不保证 |
| 事务消息 | ✅ | ❌ | ❌ |
| 延迟消息 | ✅ 18级别 | ❌ | ✅ 插件支持 |
| 消息回溯 | ✅ 按时间 | ✅ 按Offset | ❌ |
| 部署 | Namesrv+Broker | ZK+Broker | Erlang节点 |
| 运维复杂度 | 中 | 高 | 低 |

**选型建议：**
- 需要事务消息、延迟消息 → **RocketMQ**
- 需要超大规模吞吐、流处理 → **Kafka**
- 需要简单轻量、延迟低 → **RabbitMQ**

### Q15（AI 应用开发）: 写一个 RocketMQ Consumer 的健康检查脚本（Python）。

**A15：**

```python
#!/usr/bin/env python3
"""RocketMQ 消费者健康检查脚本"""
import subprocess
import json
import time
import requests

class RocketMQHealthChecker:
    """检查 RocketMQ Consumer 的健康状态"""
    
    def __init__(self, namesrv_addr: str, admin_port: int = 8080):
        self.namesrv = namesrv_addr
        self.admin_url = f"http://{namesrv_addr.split(':')[0]}:{admin_port}"
    
    def check_consumer_progress(self, group: str) -> dict:
        """检查 Consumer Group 的积压情况"""
        cmd = f"mqadmin consumerProgress -g {group} -n {self.namesrv}"
        result = subprocess.run(cmd, shell=True, capture_output=True, text=True)
        return {"raw_output": result.stdout, "error": result.stderr}
    
    def check_cluster_health(self) -> dict:
        """整体集群健康检查"""
        checks = {
            "namesrv_alive": self._check_namesrv(),
            "broker_alive": self._check_broker(),
            "disk_usage": self._check_disk(),
        }
        checks["overall"] = all(checks.values())
        return checks
    
    def _check_namesrv(self) -> bool:
        """检查 NameServer 是否存活"""
        try:
            # 发一个查询请求
            import socket
            host, port = self.namesrv.split(":")
            sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
            sock.settimeout(3)
            result = sock.connect_ex((host, int(port)))
            sock.close()
            return result == 0
        except:
            return False
    
    def _check_broker(self) -> bool:
        """检查 Broker 状态"""
        cmd = "mqadmin clusterList -n " + self.namesrv
        result = subprocess.run(cmd, shell=True, capture_output=True, text=True)
        # 正常集群应该能看到 Master 和 Slave
        return "Master" in result.stdout
    
    def _check_disk(self) -> bool:
        """检查磁盘使用率"""
        import psutil
        disk = psutil.disk_usage("/")
        usage_ratio = disk.percent / 100.0
        return usage_ratio < 0.85  # 低于 85% 算健康

# 使用示例
if __name__ == "__main__":
    checker = RocketMQHealthChecker("192.168.1.1:9876")
    
    print("=== RocketMQ 健康检查 ===")
    health = checker.check_cluster_health()
    for name, ok in health.items():
        status = "✅" if ok else "❌"
        print(f"  {status} {name}")
    
    print("\n=== 订单消费者积压 ===")
    progress = checker.check_consumer_progress("orderGroup")
    print(progress["raw_output"][:500])
```
