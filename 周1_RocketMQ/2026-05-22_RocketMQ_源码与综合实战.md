### Q2（基础）: DefaultMQProducer 的 send() 方法内部是怎么实现的？

**A2：**

```java
// send() 方法的内部流程（简化）
public SendResult send(Message msg) {
    // 1. 获取 Topic 的路由信息（TopicRouteData）
    //    如果本地缓存没有，就从 NameServer 拉取
    TopicRouteData route = this.tryToFindTopicRoute(msg.getTopic());
    
    // 2. 选择一个 Queue（默认轮询）
    MessageQueue queue = this.selectOneMessageQueue(route);
    
    // 3. 调用 Netty 发送
    SendResult result = this.mQClientAPIImpl.sendMessage(
        queue.getBrokerAddr(),  // Broker 地址
        msg,                    // 消息体
        timeout                 // 超时时间
    );
    
    // 4. 如果发送失败且需要重试
    if (result.getSendStatus() != SendStatus.SEND_OK && 
        this.retryTimes > 0) {
        // 选择一个不同的 Queue 重试
        queue = this.selectOneMessageQueue(route, queue);
        result = retrySend(queue, msg);
    }
    
    return result;
}
```

**关键点：**
- 路由信息有本地缓存（`topicRouteTable`），每 30s 刷新一次
- Queue 选择默认是**轮询**（`SendMessageQueuePoller`），顺序消息是**取模**
- 重试时选择**不同的 Queue**（防止同一个 Queue 的 Broker 挂了）

### Q4（进阶）: CommitLog 的写入和读取源码流程。

**A4：**

**写入流程：**

```java
// CommitLog.java
public class CommitLog {
    
    // 写入消息（核心方法）
    public AppendMessageResult putMessage(MessageExtBrokerInner msg) {
        // 1. 获取写锁（防止并发写）
        this.lock.lock();
        
        try {
            // 2. 获取当前写入的文件
            MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();
            
            // 3. 将消息追加到文件末尾
            AppendMessageResult result = mappedFile.appendMessage(msg);
            
            // 4. 写入 ConsumeQueue 和 IndexFile（异步）
            if (result.isOk()) {
                this.dispatcher.dispatch(result);  // 异步分发
            }
            
            return result;
        } finally {
            this.lock.unlock();
        }
    }
}
```

**读取流程：**

```java
// CommitLog.java
public SelectMappedBufferResult getMessage(long offset, int size) {
    // 1. 根据 Offset 找到对应的 MappedFile
    //    （MappedFile 按起始 Offset 排序）
    MappedFile mappedFile = this.mappedFileQueue.findMappedFile(offset);
    
    // 2. 从 MappedFile 的对应位置读取数据
    return mappedFile.selectMappedBuffer(
        (int)(offset % mappedFile.getFileSize()),  // 在文件内的偏移
        size                                         // 读取大小
    );
}
```

### Q5（进阶）: RocketMQ 怎么处理"拉模式"和"推模式"的源码实现？

**A5：**

**拉模式（PullConsumer）：**
```java
// PullConsumer 的工作方式——简单来说就是"不断轮询"
while (true) {
    PullResult result = pullConsumer.pull(queue, offset, maxNums);
    switch (result.getPullStatus()) {
        case FOUND:     // 拉到消息了
            process(result.getMsgs());
            offset = result.getNextBeginOffset();
            break;
        case NO_NEW_MSG:  // 没新消息
            Thread.sleep(1000);  // 等 1s 再试
            break;
        case OFFSET_ILLEGAL:  // Offset 非法
            offset = pullConsumer.fetchConsumeOffset(queue, true);
            break;
    }
}
```

**推模式（PushConsumer）——底层也是拉：**
```java
// PushConsumer 的本质就是 Pull + 自动调度
// 看源码中的 PullMessageService.run()
public void run() {
    while (!this.isStopped()) {
        // 从队列取 PullRequest（请求中包含了 Queue 和 Offset 信息）
        PullRequest request = this.pullRequestQueue.take();
        
        // 执行拉取（Long Polling，最长等 15s）
        this.pullMessage(request);
        
        // 如果还有更多消息，立即再发一次 PullRequest
        if (hasMore) {
            this.pullRequestQueue.put(request);
        } else {
            // 没有就等一会再拉（默认延迟 300ms）
            this.pullRequestQueue.putDelayed(request, 300);
        }
    }
}
```

**面试加分点：** PushConsumer 的"Push"是假象——底层是长轮询（Long Polling）。真正的区别不是推还是拉，而是"你自己管拉取循环"还是"框架帮你管"。

```java
// TransactionMessageServiceImpl.java
public class TransactionMessageServiceImpl {
    
    // 1. 准备阶段：存储半消息（对 Consumer 不可见）
    public PutMessageResult prepareMessage(MessageExtBrokerInner msg) {
        // 给消息打上"半消息"标记
        msg.setTransactionId(createTransactionId());
        msg.setProperty(MessageConst.PROPERTY_TRANSACTION_PREPARED, "true");
        
        // 写入 CommitLog（和普通消息一样写，但半消息不可见）
        return this.commitLog.putMessage(msg);
    }
    
    // 2. 提交/回滚：更新半消息状态
    public boolean commitMessage(EndTransactionRequest request) {
        // 把半消息标记改成可见
        // 后台线程检查到后，会添加到 ConsumeQueue
        updateMessageVisibility(request.getOffset(), VISIBLE);
        return true;
    }
    
    // 3. 回查定时任务（默认 60s 执行一次）
    @Scheduled(fixedDelay = 60000)
    public void checkTransaction() {
        // 找出"半消息已写 CommitLog 但超过 60s 没提交/回滚"的消息
        List<Long> pendingOffsets = getPendingTransactionOffsets();
        
        for (Long offset : pendingOffsets) {
            // 取出消息中的 Producer Group
            String producerGroup = getProducerGroup(offset);
            
            // 向 Producer 发起回查请求
            boolean needRedeliver = checkBackToProducer(producerGroup, offset);
            
            if (needRedeliver) {
                // 回查失败，等待下一次
                continue;
            }
        }
    }
}
```

### Q7（源码级）: RocketMQ 的定时/延迟消息是怎么实现的？

**A7：**

RocketMQ 的延迟消息不是真的"定时发"，而是**"定时去拉"**。

```java
// ScheduleMessageService.java
public class ScheduleMessageService {
    
    // 延迟级别映射表
    private static final int[] DELAY_LEVEL = {
        0,       // 1s
        1,       // 5s
        2,       // 10s
        ...
        17       // 2h
    };
    
    // 每个延迟级别对应一个 ConsumeQueue
    // 比如延迟 1s = SCHEDULE_TOPIC_XXXX/0
    //     延迟 5s = SCHEDULE_TOPIC_XXXX/1
    
    public void start() {
        for (int level = 1; level <= 18; level++) {
            long delay = computeDeliverAt(level);
            
            // 为每个延迟级别创建一个定时任务
            scheduledExecutor.scheduleAtFixedRate(() -> {
                // 检查该级别的队列，到时间的消息投递到目标 Topic
                deliverMessages(level);
            }, delay, 1000, TimeUnit.MILLISECONDS);
        }
    }
    
    private void deliverMessages(int level) {
        // 1. 从 SCHEDULE_TOPIC_XXXX/level 拉取到期的消息
        // 2. 把消息的 Topic 改回原始 Topic
        // 3. 重新写入 CommitLog（这时 ConsumeQueue 会添加到原始 Topic 下）
        // 4. Consumer 就能消费到了
    }
}
```

```java
// Master 端发送数据
public void sendData(SlaveConnection conn) {
    long masterOffset = commitLog.getMaxOffset();
    long slaveOffset = conn.getSlaveOffset();
    
    if (masterOffset > slaveOffset) {
        // 读取 CommitLog 中 Slave 还没同步到的数据
        SelectMappedBufferResult result = 
            commitLog.getData(slaveOffset, masterOffset - slaveOffset);
        
        // 发送给 Slave
        conn.getSocketChannel().write(result.getByteBuffer());
    }
}
```

### Q9（源码级）: RocketMQ 是怎么实现零拷贝的？源码级别解释。

**A9：**

```java
// MappedFile.java — 零拷贝核心实现
public class MappedFile {
    
    // 文件内存映射
    private MappedByteBuffer mappedByteBuffer;
    private FileChannel fileChannel;
    
    public void init(String fileName, int fileSize) {
        // 1. 创建文件通道
        this.fileChannel = new RandomAccessFile(fileName, "rw").getChannel();
        
        // 2. mmap 映射（零拷贝关键！）
        this.mappedByteBuffer = this.fileChannel.map(
            FileChannel.MapMode.READ_WRITE,
            0,              // 起始位置
            fileSize        // 映射大小（默认 1GB）
        );
        
        // 3. 映射完成，对 mappedByteBuffer 的读写直接操作内存
        //    系统在 PageCache 和磁盘之间自动同步
    }
    
    // 写入（利用 mmap 直接写内存）
    public AppendMessageResult appendMessage(MessageExtBrokerInner msg) {
        // 直接在 mappedByteBuffer 的当前位置写入
        this.mappedByteBuffer.position(currentPosition);
        this.mappedByteBuffer.put(msg.encode());
        // 返回写入结果
    }
    
    // 刷盘（强制将 PageCache 写入磁盘）
    public void flush() {
        this.mappedByteBuffer.force();  // 类似 fsync
    }
}
```

```python
        f"mqadmin consumerProgress -g {group} -n 127.0.0.1:9876",
        shell=True, capture_output=True, text=True

def parse_diff(output):
    total = 0
    for line in output.split("\n"):
        if "#" in line:
            parts = re.split(r'\s+', line.strip())
            if len(parts) >= 7:
                total += int(parts[-1])
    return total

    app.run(port=5000, debug=True)
```

| 错误答案 | 正确答案 | 为什么错 |

**Q15: 用自己话讲清楚 RocketMQ 的核心优势。**

**A15：**

> RocketMQ 的核心优势是"为业务而生"。Kafka 是为日志而生（追求吞吐量），RabbitMQ 是为简单而生（追求易用性）。RocketMQ 介于两者之间——比 Kafka 更容易保证消息不丢和事务一致，比 RabbitMQ 吞吐量更高。如果你的业务需要事务消息、延迟消息、顺序消息中的任何一个，RocketMQ 都是最自然的选择。如果你的场景只有海量吞吐（每天百亿级），选 Kafka。
