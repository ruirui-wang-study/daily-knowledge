## 主题：RocketMQ 基础篇 — 架构与核心概念

### Q1: RocketMQ 是什么？和 Kafka 比有什么核心区别？

**面试官想听什么：** 不是背定义，而是看出你有没有选型经验。

**高分回答：**

"RocketMQ 是阿里开源的消息中间件，现在属于 Apache。它的定位和 Kafka 不太一样——Kafka 本质上是个**流存储平台**，它的核心设计目标是大吞吐、日志类的流式处理；RocketMQ 的定位更偏向**企业级消息中间件**，它内置了很多业务场景需要的特性，比如事务消息、延迟消息、顺序消息，这些都是开箱即用的。

从存储架构上也有本质区别：RocketMQ 所有消息写到一个 CommitLog 文件，Kafka 是每个分区一个独立文件。所以 RocketMQ 的写入是严格顺序的，IO 更友好；Kafka 分区多了随机写就上来了。

选型上我的建议是：如果业务需要事务消息、延迟消息这些能力，RocketMQ 是自然选择。如果场景是海量日志、埋点数据、流计算，Kafka 更合适。**没有谁绝对好，看场景。**"

> 💡 面试官会追问："那你实际项目中用过吗？遇到过什么问题？"——建议准备一个真实案例。

### Q2: RocketMQ 的核心组件有哪些？画一下架构图。

**高分回答：**

"RocketMQ 有四大组件，我按数据流向说：

**Producer** 发消息 -> **NameServer** 提供路由 -> **Broker** 存消息 -> **Consumer** 拉消息。

这里有个容易被忽略的点：NameServer 之间**不互通**。每个 NameServer 独立维护全量路由，Broker 每隔 30 秒向所有 NameServer 发心跳。如果某个 NameServer 挂了，Producer 和 Consumer 本地有缓存，不影响运行——只是新 Topic 创建和 Broker 上下线暂时感知不到。

这个设计比 Kafka 依赖 ZK 要轻量，但也意味着 NameServer 的数据是**最终一致**的，存在短暂的不一致窗口。不过在生产中这个设计够用了——我们线上跑了两年的集群，NameServer 单节点重启过几次，业务零影响。"

> 💡 面试加分点：能说出"NameServer 无状态 + 最终一致性"这个设计哲学，说明你真的理解架构，不是背图。

### Q3: 什么是 Topic？什么是 MessageQueue？Topic 和 Queue 什么关系？

**高分回答：**

"Topic 是逻辑上的消息分类，比如订单 Topic、支付 Topic。MessageQueue 是物理上的存储单元，一个 Topic 对应多个 Queue。

关系可以用一个公式理解：**Topic 的并发能力 = Queue 数量**。因为每个 Queue 在同一个 Consumer Group 内最多只能被一个 Consumer 实例消费。所以如果你有 8 个 Queue，即使你起了 16 个 Consumer 实例，最多也只有 8 个在干活。

这个特性在生产扩容时很重要。比如线上突然消息量暴增，你加 Consumer 实例——但如果 Queue 数不够，加了也没用。所以建 Topic 时我习惯把 Queue 数设成预期 Consumer 实例数的 2 到 3 倍，预留弹性空间。"

> 💡 面试扣分点："RocketMQ 支持全局有序"——不对，它只支持分区有序。单一 Queue 保证有序，但全局有序你需要把所有消息塞到一个 Queue 里，那并发就归零了。

### Q4: RocketMQ 的消息模型是什么样的？说清楚 Producer、Consumer、Consumer Group 的关系。

**高分回答：**

"消息模型分三层：

**第一层，发送。** Producer 把消息发到 Topic，Broker 分配到 Topic 下的某个 Queue。

**第二层，消费。** Consumer 从 Queue 拉消息消费。这里的关键是 Consumer Group——同一个 Group 的 Consumer 实例共同消费 Topic 的消息，每条消息只被组内一个实例处理。不同 Group 之间独立消费，互不干扰。

**第三层，进度管理。** 集群模式下 Offset 存在 Broker 端，广播模式下存在 Consumer 本地文件。广播模式的一个坑是——如果你换机器或者本地文件损坏，Offset 丢了，Consumer 只能从头消费。"

> 💡 可以补充一个生产实践："我们线上所有消费逻辑都必须做幂等。因为 RocketMQ 不保证 exactly-once，Rebalance 或重试都会导致重复消费。幂等是刚需，不是可选项。"

### Q5: RocketMQ 的消息可靠性是怎么保证的？说清楚三个阶段的保证机制。

**高分回答：**

"消息不丢要管三个环节，每个环节都有不同的策略：

**生产阶段** — Producer 到 Broker。用同步发送 + 重试。默认重试 3 次，间隔 100ms。如果需要更高保障，用事务消息——两阶段提交加上 Broker 的回查机制，保证生产端和 Broker 的数据一致。

**存储阶段** — Broker 端。两个维度：刷盘和复制。刷盘分同步和异步，同步刷盘保证不丢但性能降 30% 左右。复制也分同步和异步，同步复制要求 Master 和至少一个 Slave 都写成功再返回。

**消费阶段** — Broker 到 Consumer。消费完成后手动返回 CONSUME_SUCCESS 提交 Offset，失败返回 RECONSUME_LATER 进入重试队列，重试 16 次还失败就进死信队列。

**但我要说一句实话：没有绝对的不丢。** 即使同步刷盘 + 同步复制，遇到磁盘物理损坏还是可能丢。所以我建议加一层业务补偿——定期比对业务数据和消息数据的差异，发现丢失就补偿重发。这叫"兜底机制"，面试官听到会很认可。"

### Q6: RocketMQ 支持哪几种消息类型？各自适用场景是什么？

**高分回答：**

"五种。我按使用频率排：

**普通消息** — 大部分场景。比如发个通知、写个日志。

**顺序消息** — 订单状态变更、操作日志这种必须按顺序处理的场景。注意 RocketMQ 只保证分区有序，不保证全局有序。

**事务消息** — 分布式事务场景。比如下单要同时扣库存，用事务消息保证最终一致性。核心是两阶段提交加回查。

**延迟消息** — 订单超时取消、定时任务。但注意 RocketMQ 只支持 18 个预设延迟级别，最长 2 小时，不支持秒级精度。如果需要自定义延迟，得改 Broker 源码或者自己在业务层实现时间轮。

**批量消息** — 大量小消息时提升吞吐。但要注意批量大小不要超过 4MB。"

> 💡 面试官可能会追问："你用过事务消息吗？遇到过什么坑？"——建议准备一个事务消息回查超时的实际案例。

### Q7: RocketMQ 怎么保证消息的顺序消费？和 Kafka 的顺序消费有什么异同？

**高分回答：**

"**先说结论：两个产品保证的都是分区有序，不是全局有序。**

实现方式上，RocketMQ 需要两件事配合：

Producer 端实现 MessageQueueSelector，根据业务 key 取模选 Queue——保证同一个订单的消息进同一个 Queue。Consumer 端用 MessageListenerOrderly，同一个 Queue 内的消息串行消费。

这里有个容易被忽视的点：**顺序消息不能开重试。** 因为重试时消息可能落到不同 Queue，顺序就乱了。所以顺序消息的可用性比普通消息低——一个 Queue 卡住了，后面的消息都得等着。

和 Kafka 的区别主要在 Consumer 端：Kafka 靠 Partition 内的 offset 顺序 + 单线程拉取保证顺序；RocketMQ 的 MessageListenerOrderly 加了锁机制，实现上更重一些。"

### Q8: RocketMQ 的 Push 模式和 Pull 模式有什么区别？RocketMQ 的"Push"是推吗？

**高分回答：**

"这是个很好的陷阱题。RocketMQ 的 Push 模式**本质上不是推，是长轮询（Long Polling）**。

真实流程是这样的：
1. Consumer 发起拉取请求
2. Broker 检查 Queue 里有没有新消息
3. 有 → 立即返回；没有 → 请求挂起最多 15 秒（长轮询）
4. 期间有新消息到达 → 立即返回；超时 → 返回空结果
5. Consumer 立刻发起下一次请求

所以它看起来像推——消息一到 Consumer 就收到了，延迟很低。但底层是靠 Consumer 不断拉 + Broker 挂起请求实现的。

那和真正的 Push 有什么区别？真正的 Push 是 Broker 主动推给 Consumer，Broker 需要维护推送状态和重试逻辑。长轮询把控制权交给了 Consumer——Consumer 按自己的节奏拉，Broker 不需要维护大量连接状态，资源消耗更低。"

> 💡 如果面试官深问可以补充：长轮询 vs 短轮询的区别——短轮询是固定间隔轮询，有延迟且浪费带宽；长轮询是 Broker 有消息再返回，接近实时且省资源。

### Q9: RocketMQ 的负载均衡是怎么实现的？Consumer 端 Rebalance 过程是怎样的？

**高分回答：**

"RocketMQ 的负载均衡**在 Consumer 端完成**，Broker 不参与分配。默认的分配算法是平均分配——把 Queue 平均分给每个 Consumer 实例。

Rebalance 的触发条件是 Consumer 上下线或 Queue 数量变化。流程是：
1. 某个 Consumer 挂了或新加入
2. 所有 Consumer 重新分配 Queue
3. 原持有 Queue 的 Consumer 暂停消费
4. 新分配的 Consumer 接管

这里有个必知的问题——**Rebalance 期间会重复消费**。因为释放方还没提交 Offset 就停下来了，接管方从 Broker 拿到的 Offset 是旧的，会把最近几条消息再消费一遍。所以我说消费端幂等是刚需，这是原因之一。

减少 Rebalance 影响的方法：不要在高峰期重启 Consumer 实例，用优雅关闭让 Consumer 先提交 Offset 再下线。"

### Q10: RocketMQ 的消息存储是怎么设计的？CommitLog 和 ConsumeQueue 的关系是什么？

**高分回答：**

"这是 RocketMQ 存储架构最核心的设计。简单说：**CommitLog 是物理存储，ConsumeQueue 是逻辑索引。**

CommitLog 存所有 Topic 的消息，所有消息顺序写入一个文件。这就意味着写入永远是顺序 IO——这是 RocketMQ 高性能的基础。SSD 顺序写能到 600MB/s，随机写只有 50MB/s 左右，差了十几倍。

ConsumeQueue 是每个 Queue 一个的索引文件，每条记录只有 20 个字节——8 字节偏移量、4 字节消息长度、8 字节 Tag 哈希。10 万条消息才 2MB，完全可以全部缓存到内存。

读取时先查 ConsumeQueue 拿到偏移量，再从 CommitLog 随机读。因为 ConsumeQueue 小且常驻内存，这一步很快；CommitLog 的随机读因为有 PageCache，命中率也很高。

和 Kafka 的对比：Kafka 每个分区一个独立文件，分区多了就是随机写。RocketMQ 所有分区写一个 CommitLog，永远是顺序写。这是两种不同的 trade-off。"

> 💡 面试加分点：能说出"CommitLog 写、ConsumeQueue 读"这个读写分离设计，以及"PageCache 作为读缓存"的机制。

### Q11: RocketMQ 怎么处理消息积压？有哪些监控和排查手段？

**高分回答：**

"积压排查三板斧：

**第一，看 mqadmin consumerProgress。** 这个命令告诉你每个 Consumer Group 在每个 Queue 上的积压量。如果总积压在涨但单个 Queue 积压不明显，说明 Queue 数不够，加 Queue。

**第二，看消费速度和生产速度。** 如果消费慢，先看消费逻辑——是不是调外部 API 超时？是不是有 Full GC？如果消费速度和 Queue 数匹配但总量还在涨，加 Consumer 实例。

**第三，用 Dashboard 看趋势。** 积压量是涨还是降比绝对值更重要。偶发积压是正常的，持续上涨才是问题。

扩容的正确姿势：先加 Consumer 实例——如果 Queue 数不够 Consumer 数，再加 Queue。但注意 Queue 扩容后**已存在的消息不会重分配到新 Queue**，新消息才会走新 Queue。所以建 Topic 时 Queue 数要预留余量。"

### Q12: RocketMQ 的事务消息是怎么实现的？说清楚两阶段提交 + 回查的完整流程。

**高分回答：**

"事务消息的核心机制叫**两阶段提交加回查**。

第一阶段：Producer 发一条半消息到 Broker。半消息对 Consumer 不可见——不会写入 ConsumeQueue，只写 CommitLog。

第二阶段：Producer 收到半消息的 ID 后，执行本地事务（比如扣库存）。如果成功，向 Broker 发送 COMMIT，消息变为可见；如果失败，发送 ROLLBACK，消息被丢弃。

这里的关键是：**如果 Producer 发完半消息后挂了，没来得及提交或回滚怎么办？** 这就是回查机制——Broker 会定期扫描那些超过 60 秒还没确定状态的半消息，回调 Producer 的 checkLocalTransaction 方法询问事务状态。

回查默认最多 15 次，间隔 60 秒，全部失败就回滚。所以 Producer 端的 checkLocalTransaction 实现一定要可靠——通常直接查数据库判断本地事务是否成功。

用的时候有个容易被忽略的点：**事务消息只保证生产端的原子性，消费端照样可能重复消费。** 消费端还是要做幂等。"

### Q13: 假如你有一个订单系统，下订单后需要：1）扣库存 2）发短信通知 3）更新物流状态。你会怎么用 RocketMQ 设计这个架构？

**高分回答：**

"我会用三种不同的消息类型处理这三个需求：

**扣库存用事务消息。** 因为库存扣减和订单创建是原子操作——库存扣成功了订单才有效，库存扣失败了订单要回滚。事务消息的最终一致性在这里刚好合适，比强一致的分布式事务（TCC/Seata）更轻量。

**发短信用普通消息加死信队列。** 短信偶尔失败问题不大，重试几次就行。重试 16 次还失败就进死信队列，每天人工看一眼。

**物流状态更新用顺序消息。** 一个订单的状态变化（已发货 -> 运输中 -> 已签收）需要有序。用订单号作为 MessageQueueSelector 的参数，保证同一个订单的消息进同一个 Queue。

整体架构的容错设计：每个消费端都必须幂等——不能因为重复消费就多扣一次库存、多发一次短信。这是整个架构的底线。"

### Q14: 你们公司用 RocketMQ 遇到过什么坑？怎么解决的？

**高分回答：**

"说一个我们线上踩过的坑吧。

**问题：** 有次促销活动流量预估不足，消息生产速度远大于消费速度。Broker 磁盘快写满了，我们收到告警才发现。

**排查：** 发现是消费端有一个外部 API 调用超时——上游接口 RT 从 50ms 飙到 3 秒，Consumer 被卡住了，整个消费链堵死了。

**解决：** 先把消费端的外部调用改成异步 + 超时熔断，保证消费线程不被阻塞。然后临时加了 3 个 Consumer 实例消化积压。

**教训：** 一是消费端一定要有超时和熔断机制，二是一定要监控积压量——我们后来加了一个告警规则，积压超过 1 万条就报警。三是建 Topic 时 Queue 数要留余量，方便临时扩容。"

> 💡 如果面试官追问："消费者怎么加熔断？"——"我们用的 Sentinel，消费方法上加 @SentinelResource，超过阈值直接 fallback 到 RECONSUME_LATER。"

### Q15（AI 应用开发）: 用 Python 实现一个简单的 RocketMQ 消息生产-消费 Demo。

**高分回答：**

```python
# 这是一个快速验证 RocketMQ 连通性的最小 Demo
# 生产环境需要考虑异常处理、重试、幂等

from rocketmq.client import Producer, PushConsumer, Message
import time

# 生产者
producer = Producer("GID-producer-demo")
producer.set_name_server_address("127.0.0.1:9876")
producer.start()

msg = Message("Topic-Demo")
msg.set_body("Hello RocketMQ".encode("utf-8"))
# 同步发送——生产环境尽量用同步，重试机制才有意义
result = producer.send(msg)
print(f"OK, msgId: {result.msg_id}")
producer.shutdown()

# 消费者
consumer = PushConsumer("GID-consumer-demo")
consumer.set_name_server_address("127.0.0.1:9876")
consumer.subscribe("Topic-Demo", "*")

def callback(msg):
    print(f"[消费] {msg.body.decode('utf-8')}")
    return 0  # 0 = CONSUME_SUCCESS

consumer.register_message_callback(callback)
consumer.start()
time.sleep(5)
```
