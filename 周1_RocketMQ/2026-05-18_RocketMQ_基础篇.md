### Q1（入门）: RocketMQ 是什么？和 Kafka 比有什么核心区别？

**A1：**

RocketMQ 是阿里巴巴开源的分布式消息中间件，2016 年捐给 Apache 基金会。核心定位是**高可用、高可靠、低延迟**的消息队列。

和 Kafka 的核心区别：

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| 设计定位 | 消息中间件（事务、可靠性优先） | 流处理平台（吞吐量优先） |
| 消息模型 | 队列模型 + 广播模型 | 分区日志模型 |
| 消息可靠性 | 同步刷盘 + 同步复制，默认保证不丢 | 异步刷盘，可能丢消息 |
| 事务消息 | ✅ 原生支持 | ❌ 需额外实现 |
| 延迟消息 | ✅ 原生支持（18 个级别） | ❌ 不支持 |
| 顺序消息 | ✅ 分区有序 | ✅ 分区有序 |
| 消息回溯 | ✅ 按时间回溯 | ✅ 按 offset 回溯 |
| 部署复杂度 | 较轻（Namesrv + Broker） | 较重（依赖 ZK） |

**面试加分点：** 能说出"RocketMQ 的刷盘机制有同步刷盘和异步刷盘两种，同步刷盘保证消息不丢但吞吐量下降约 30%"

### Q2（入门）: RocketMQ 的核心组件有哪些？画一下架构图。

**A2：**

RocketMQ 有四大核心组件：

```
Producer → NameServer → Consumer
                ↓
            Broker (存储消息)
```

- **NameServer：** 轻量级的注册中心，维护 Broker 的路由信息。每个 NameServer 节点之间不互通（不像 ZK 有选举机制）
- **Broker：** 消息存储服务器，负责消息的接收、存储、投递
- **Producer：** 消息生产者
- **Consumer：** 消息消费者

**面试加分点：** NameServer 的"无状态 + 最终一致性"设计——Broker 每隔 30s 向所有 NameServer 发送心跳，NameServer 10s 内没收到心跳就认为 Broker 挂了。这个设计比 ZK 更轻量，但存在短暂的不一致窗口。

### Q3（入门）: 什么是 Topic？什么是 MessageQueue（消息队列）？Topic 和 Queue 什么关系？

**A3：**

- **Topic：** 消息的逻辑分类。比如"订单Topic"、"支付Topic"
- **MessageQueue：** 物理存储单元，一个 Topic 由多个 Queue 组成

关系：**Topic 是逻辑概念，Queue 是物理概念。** 一个 Topic 对应多个 Queue，消息发送时轮询分配到不同 Queue，消费时多个 Consumer 可以并发消费不同 Queue。

```
Topic "Order"
  ├── Queue-0 (Broker-A)
  ├── Queue-1 (Broker-A)
  ├── Queue-2 (Broker-B)
  └── Queue-3 (Broker-B)
```

**面试加分点：**

> 一个 Topic 的 Queue 数量决定了它的并发能力。Producer 端轮询发消息到各个 Queue，Consumer 端每个 Queue 只能被一个 Consumer 实例消费（同一个 Consumer Group 内）。所以：**Queue 数量 = 最大并发消费数**。建议 Queue 数 = Consumer 实例数 × 2~3，留有余量。

### Q4（基础）: RocketMQ 的消息模型是什么样的？说清楚 Producer、Consumer、Consumer Group 的关系。

**A4：**

消息模型：

1. **Producer** 发消息到 **Topic**
2. **Broker** 将消息分配到 Topic 下的某个 **Queue**
3. **Consumer** 从 Queue 拉取消息消费

Consumer Group 的要点：

- 同一个 Consumer Group 内的 Consumer 实例**共同消费** Topic 的消息（每条消息只被组内一个实例消费）
- 不同 Consumer Group 之间**独立消费**（每条消息可以被多个 Group 各消费一次）
- Consumer Group 的消费进度（Offset）由 Broker 管理，保存在 `__consumer_offsets` 这个系统 Topic 中

**面试加分点：** "集群消费"和"广播消费"的区别——集群消费是 Queue 分配模式（每条消息只被消费一次），广播消费是每个 Consumer 实例都消费所有消息。

### Q5（基础）: RocketMQ 的消息可靠性是怎么保证的？说清楚三个阶段的保证机制。

**A5：**

消息可靠性分为三个阶段：

**① 生产阶段（Producer → Broker）**

- **同步发送：** Producer 发消息后等待 Broker 的 ACK，超时或失败则重试（默认重试 3 次）
- **事务消息：** 先发半消息，执行本地事务，提交/回滚。Broker 没收到提交/回滚时会回查 Producer

**② 存储阶段（Broker 端）**

- **同步刷盘：** 消息写入内存 PageCache 后立即刷到磁盘（`FlushDiskType=SYNC_FLUSH`）
- **异步刷盘：** 定期刷盘（默认每 500ms），性能高但断电可能丢数据
- **同步复制：** Master 收到消息后等 Slave 也写入成功才返回 ACK
- **异步复制：** Master 返回 ACK 后再复制到 Slave

**③ 消费阶段（Broker → Consumer）**

- Consumer 消费完成后**手动提交 Offset**（不像 Kafka 自动提交）
- 消费失败可以重试（默认 16 次），超过次数进入**死信队列**

```java
// 同步发送示例
SendResult result = producer.send(message);
if (result.getSendStatus() == SendStatus.SEND_OK) {
    // 发送成功
}

// 消费时手动提交
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    try {
        process(msgs);
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS; // 签收
    } catch (Exception e) {
        return ConsumeConcurrentlyStatus.RECONSUME_LATER; // 稍后重试
    }
});
```

### Q6（进阶）: RocketMQ 支持哪几种消息类型？各自适用场景是什么？

**A6：**

| 消息类型 | 说明 | 适用场景 |
|---------|------|---------|
| **普通消息** | 无特殊语义 | 大多数场景 |
| **顺序消息** | 同一 Queue 内严格有序 | 订单状态变更、日志流水 |
| **事务消息** | 两阶段提交 + 回查 | 分布式事务（如订单+扣库存） |
| **延迟消息** | Broker 延迟投递 | 订单超时取消、定时任务 |
| **批量消息** | 一批消息打包发送 | 大量小消息时提升吞吐 |

**面试加分点：** RocketMQ 不支持任意秒级的延迟，只有 18 个预设级别：1s/5s/10s/30s/1m/2m/3m/4m/5m/6m/7m/8m/9m/10m/20m/30m/1h/2h。如果需要任意延迟，需要修改 Broker 代码。

### Q7（进阶）: RocketMQ 怎么保证消息的顺序消费？和 Kafka 的顺序消费有什么异同？

**A7：**

RocketMQ 的**分区有序**（和 Kafka 一样）：保证同一 Queue 内的消息有序。

**实现方式：**

```java
// Producer 端：保证相同业务 key 的消息进同一个 Queue
producer.send(message, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        // 订单号 hash 取模，确保同一个订单的消息进同一个 Queue
        int queueIndex = (arg.hashCode() & Integer.MAX_VALUE) % mqs.size();
        return mqs.get(queueIndex);
    }
}, orderId);

// Consumer 端：使用 MessageListenerOrderly（单线程消费）
consumer.registerMessageListener((MessageListenerOrderly) (msgs, context) -> {
    // 这个 Queue 的消息会被串行消费
    process(msgs);
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
```

和 Kafka 的异同：

- **相同：** 都是分区（Partition/Queue）内有序，全局无序
- **不同：** RocketMQ 的 Consumer 端有专门的 `MessageListenerOrderly`，保证消费时加锁；Kafka 靠 Partition 内的顺序和 Consumer 单线程拉取实现

**面试最高频坑：** 很多人说 RocketMQ 支持"全局有序"，但那是建一个单 Queue 的 Topic——此时性能和可用性都大打折扣。

### Q8（进阶）: RocketMQ 的 Push 模式和 Pull 模式有什么区别？RocketMQ 的"Push"真的是服务器主动推吗？

**A8：**

RocketMQ 的 **"Push"模式本质是 Long Polling（长轮询）**，不是真正的服务器推送。

**真实流程：**
1. Consumer 向 Broker 发起拉取请求
2. Broker 检查 Queue 里有没有新消息
3. 有 → 立即返回；没有 → 挂起请求，最多等 15s（长轮询）
4. 期间有新消息到达 → 立即返回；超时 → 返回空结果
5. Consumer 收到结果后立即发起下一次请求

```java
// 这看起来像 Push，实际上是长轮询
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    // 底层是不断 Pull + 长轮询
});
```

**Pull 模式：** 需要自己控制拉取频率和 Offset 管理：

```java
DefaultMQPullConsumer pullConsumer = new DefaultMQPullConsumer("group");
pullConsumer.start();
// 需要自己管理 Offset、自己控制拉取频率
```

**面试加分点：** 长轮询既实现了接近实时的效果，又避免了真正的 Push 模式下 Broker 端维护大量长连接的资源消耗。

### Q9（进阶）: RocketMQ 的负载均衡是怎么实现的？Consumer 端 Rebalance 的过程是什么？

**A9：**

RocketMQ 的负载均衡在 **Consumer 端**进行，Broker 不参与分配。

**Rebalance 触发条件：**
1. 有新的 Consumer 加入或退出
2. Topic 的 Queue 数量发生变化

**分配算法（默认的 `AllocateMessageQueueAveragely`）：**

```
假设 Topic 有 8 个 Queue，有 3 个 Consumer：
- Consumer-1: Queue-0, Queue-1, Queue-2  (8/3 向上取整 = 3 个)
- Consumer-2: Queue-3, Queue-4, Queue-5  (3 个)
- Consumer-3: Queue-6, Queue-7             (剩余 2 个)
```

**Rebalance 的问题：**
- **重复消费：** Rebalance 期间 Offset 还没来得及提交的消息会被重复消费（需要业务方做幂等）
- **暂停消费：** Rebalance 过程中部分 Queue 的消费会短暂暂停

**面试加分点：** 应用中应该实现**消费幂等**来应对 Rebalance 导致的重复消费。

### Q10（源码级）: RocketMQ 的消息存储是怎么设计的？CommitLog 和 ConsumeQueue 的关系是什么？

**A10：**

**CommitLog：** 消息的物理存储文件。所有 Topic 的消息都在一个 CommitLog 里顺序写。

**ConsumeQueue：** 消息的逻辑索引文件。每个 Queue 对应一个 ConsumeQueue，记录消息在 CommitLog 中的偏移量。

```
                ┌─────────────────────────────────┐
  Producer ──►  │          CommitLog              │
                │   (所有消息顺序写入一个文件)       │
                └──────────┬──────────────────────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
   ConsumeQueue-0   ConsumeQueue-1   ConsumeQueue-2
   (TopicA/Queue0)  (TopicA/Queue1)  (TopicB/Queue0)
```

**为什么这么设计？**
- **顺序写 CommitLog：** 利用磁盘顺序写的高性能（比随机写快 10 倍以上）
- **ConsumeQueue 作为索引：** 很小（每条记录 20 字节：Offset + Size + TagHash），可以全部加载到内存
- **读取时：** 先查 ConsumeQueue 拿到偏移量，再从 CommitLog 随机读

**面试加分点：** 这和 Kafka 的"分区 = 物理文件"设计不同。Kafka 每个分区一个文件，RocketMQ 所有分区共享一个 CommitLog。RocketMQ 的设计在 Broker 端更简单，但读取时多了一次 ConsumeQueue 的查询开销。

### Q11（源码级）: RocketMQ 怎么处理消息积压？有哪些监控和排查手段？

**A11：**

**积压的原因：**
1. Consumer 消费速度 < Producer 生产速度
2. Consumer 实例数 < Queue 数（没足够的消费者）
3. Consumer 消费逻辑有瓶颈（如调外部 API 太慢）
4. Rebalance 导致的短暂停

**排查手段：**

```bash
# 1. 查看 Consumer 积压情况
mqadmin consumerProgress -g consumerGroupName

# 2. 查看 Broker 的存储情况
mqadmin status -b 127.0.0.1:10911

# 3. RocketMQ-Console 监控
# Dashboard 能看到每个 Consumer Group 的积压量（Diff Total）
```

**扩容方案：**
1. Consumer **扩容**：加机器（但注意 Queue 数 >= Consumer 数才有意义）
2. Queue **扩容**：增加 Queue 数（但已存在的消息不会自动分配到新 Queue）
3. **跳过积压**：如果业务允许，可以重置 Offset 到最新

**面试加分点：** 核心操作是"加 Consumer + 加 Queue"，但 Queue 扩容后已有的消息不会重新分配——新消息才会走新 Queue，积压消息只能靠原 Queue 的 Consumer 慢慢消化。这是 RocketMQ 的一个设计局限，和 Kafka 一样。

### Q12（源码级）: RocketMQ 的事务消息是怎么实现的？说清楚两阶段提交 + 回查的完整流程。

**A12：**

事务消息的核心是**两阶段提交 + 事务回查**：

```
第一阶段（发送半消息）：
Producer ──发送半消息──► Broker (半消息对Consumer不可见)
     │
     │  返回半消息ID
     ◄───────────
     │
     │  执行本地事务（如扣库存）
     │
第二阶段（提交/回滚）：
Producer ──提交/回滚──► Broker
     │
     │  如果没收到提交/回滚请求
     │  Broker 会定时回查 Producer
     │
     └──► Producer 检查本地事务状态
          └──► 告诉 Broker：COMMIT / ROLLBACK / UNKNOWN
```

```java
// Producer 端实现 TransactionListener
public class OrderTransactionListener implements TransactionListener {
    
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 执行本地事务（比如扣库存）
        try {
            deductStock(arg); // 本地数据库操作
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // Broker 回查：检查本地事务是否成功
        String orderId = msg.getKeys();
        if (orderExistsInDB(orderId)) {
            return LocalTransactionState.COMMIT_MESSAGE;
        }
        return LocalTransactionState.ROLLBACK_MESSAGE;
    }
}
```

**面试加分点：** 回查机制是 RocketMQ 事务消息的精髓——当半消息已提交但事务状态不明时，Broker 会主动回查 Producer。回查间隔默认 60s，最大回查次数 15 次，超过会回滚。这保证了分布式事务的**最终一致性**。

### Q13（综合）: 假如你有一个订单系统，下订单后需要：1）扣库存 2）发短信通知 3）更新物流状态。你会怎么用 RocketMQ 设计这个架构？需要考虑哪些异常情况？

**A13：**

**推荐架构：**

```
用户下单 ──► 订单服务
                │
                ├──► (事务消息) RocketMQ ──► 库存服务（扣库存）
                │
                ├──► (普通消息) RocketMQ ──► 通知服务（发短信）
                │
                └──► (普通消息) RocketMQ ──► 物流服务（创建物流单）
```

**设计要点：**

1. **扣库存用事务消息：** 如果扣库存失败，整个下单流程应该回滚
2. **发短信用普通消息 + 重试：** 短信偶尔失败没关系，重试即可
3. **更新物流状态用顺序消息：** 同一个订单的状态变更需要有序

**需要考虑的异常：**
- 库存扣了但订单没创建成功 → 用事务消息的回查机制兜底
- 短信发送失败 → 重试 16 次后进死信队列，人工处理
- 物流服务挂了 → 消息堆积，恢复后自动消费
- 幂等处理：**所有消费端都必须幂等**，防止重复扣库存/重复发短信

**面试加分点：** "最终一致性"是面试官最爱听的词。别追求强一致（下订单到扣库存之间可以差几秒），但不能丢消息、不能多扣库存。

### Q14（综合）: 你们公司用 RocketMQ 遇到过什么坑？怎么解决的？

（这是一道开放题，面试官想看你有没有**实战经验**。如果没有真踩过，下面几个经典坑可以准备）

**A14：**

经典坑 1：**消息重复消费**
- 原因：Rebalance、Broker 重启、手动重复投递
- 解决：消费端做幂等（唯一键去重 / 数据库唯一索引）

经典坑 2：**消息顺序错乱**
- 原因：用了 MessageListenerConcurrently + 并发消费
- 解决：使用 MessageListenerOrderly（单线程）
- 但注意：Orderly 模式会降低消费速度

经典坑 3：**消息积压导致 OOM**
- 原因：消费速度跟不上，Consumer 的拉取线程还在不断拉
- 解决：设置 `pullThresholdForQueue`（默认 1000），超过阈值暂停拉取

经典坑 4：**定时消息误差大**
- 原因：RocketMQ 的延迟级别是预定义的，不支持秒级精度
- 解决：如果需要精确的定时，可以考虑 Redis ZSet + 轮询 或 时间轮算法

### Q15（AI 应用开发）: 用 Python 实现一个简单的 RocketMQ 消息生产-消费 Demo。

**A15：**

```python
# 需要安装 rocketmq-client-python
# pip install rocketmq-client-python

from rocketmq.client import Producer, Message, PushConsumer
import time

# ====== 生产者 ======
def send_messages():
    producer = Producer("GID-producer-demo")
    producer.set_name_server_address("127.0.0.1:9876")
    producer.start()
    
    for i in range(10):
        msg = Message("Topic-Demo")
        msg.set_keys(f"KEY_{i}")
        msg.set_tags("demo")
        msg.set_body(f"这是第 {i} 条消息".encode("utf-8"))
        
        # 同步发送
        send_result = producer.send(msg)
        print(f"发送结果: {send_result.status}, msgId: {send_result.msg_id}")
    
    producer.shutdown()

# ====== 消费者 ======
def consume_messages():
    consumer = PushConsumer("GID-consumer-demo")
    consumer.set_name_server_address("127.0.0.1:9876")
    consumer.subscribe("Topic-Demo", "*")  # 订阅所有 Tag
    
    def callback(msg):
        print(f"收到消息: {msg.body.decode('utf-8')}")
        # 消费成功
        return 0  # 0 = CONSUME_SUCCESS
    
    consumer.register_message_callback(callback)
    consumer.start()
    
    # 保持运行
    while True:
        time.sleep(1)

if __name__ == "__main__":
    # 先启动消费者
    import threading
    t = threading.Thread(target=consume_messages, daemon=True)
    t.start()
    time.sleep(2)
    
    # 再发消息
    send_messages()
    
    print("Demo 运行结束，等待消费...")
    time.sleep(3)
```
